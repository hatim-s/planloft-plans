Theo's setup puts account authentication on one always-on home computer and sends requests from his other computers to that hub over Tailscale. CLIProxyAPI supplies the common endpoint. The hub, rather than each client, makes the upstream provider requests.

Proxying model requests does not move agent execution. Claude Code, shell commands, repository reads and tests still run on the client or selected T3 environment host. For example, a laptop can run Claude Code against its local checkout while the home hub forwards only model requests. To execute tools on the hub, launch the agent there explicitly.

This guide describes that architecture and a cautious way to reproduce it. It is a research guide, not a verified deployment. No installation, login, configuration change, or live request was performed for this document.

A working proxy is not evidence that a subscription provider permits this use. Read the current provider terms before enrolling accounts.

What the hub does

The supplied local copy of Theo's guide describes a home hub running CLIProxyAPI, with Claude and Codex accounts enrolled on the hub. Clients connect to the hub's HTTPS endpoint through Tailscale. Theo reports using multiple accounts and computers; his public sources give different counts, so treat the counts as a snapshot, not a current inventory. See his post and T3 Code FAQ.

The proxy exposes compatible API interfaces, keeps provider credentials on the hub, and can route requests across enrolled credentials. It does not run model inference locally, create more provider quota, guarantee failover, make incompatible clients automatically compatible, or establish permission to use subscription credentials this way. A hub outage interrupts clients pointed at it. Tailnet access also makes the hub a valuable target: a caller with access to the endpoint and its client key can spend the accounts' capacity.

Useful cases include accessing the same endpoint from several personal machines, reducing repeated account setup, and testing multiple enrolled accounts from a supported client. A separate Claude configuration is a useful escape hatch: it keeps the normal configuration available and makes selection deliberate. This does not itself pool accounts.

Theo says centralizing auth reduces login churn and changing IPs, warns against a VPS and VPN, and reports his own ban experience. These are his observations and recommendations, not verified provider enforcement rules. His claims about refresh intervals, IP-related bans, power consumption and websocket speed are not independently established here. A residential IP is not a compliance guarantee.

Policy and trust boundaries

Anthropic's authentication and credential-use policy distinguishes consumer subscription OAuth for Claude Code and native Anthropic apps from API credentials. It restricts products and services that collect, store, intermediate, or route Claude.ai credentials on behalf of users, while separately describing conditions for an end user signing into unmodified Claude Code in a product. Its text does not explicitly decide this exact single-user, self-hosted proxy arrangement. It does not approve it either. Ask Anthropic about the intended arrangement if the risk matters; enforcement may include account action. Theo himself warns of bans and says not to serve other people's traffic or use Claude subscriptions outside Claude Code.

For a documented business integration, consider the Anthropic API or a supported cloud provider with its own billing and API rate limits. Separate subscriptions do not automatically confer a right to combine capacity. Check OpenAI's current terms separately before using Codex subscription OAuth through a proxy.

Routing is not affinity

The upstream v8 example configuration describes round-robin, weighted-round-robin, and fill-first. Session affinity binds a session to a credential for a configured period, with failover described when the credential becomes unavailable. This can help retain account-specific cache locality, but it does not prove behavior under every quota error or retry. Observe actual requests and cache metrics without exposing prompts or credentials.

Theo says his soonest-reset-first policy required his fork. Upstream priority, weights, round robin, and affinity do not implement that policy. The supplied material does not identify a verifiable fork revision or provide an implementation. Do not claim it is enabled by the example below, or promise a particular account will be chosen next. Affinity can also keep an existing session on an account even when a different routing preference would choose another one.

Before starting

Use a personal, trusted home hub that stays awake, a private tailnet, and clients authorized to reach it. This guide assumes macOS with Homebrew on the hub, Claude Code already installed on the client, and that the user personally completes each account login. Linux is an alternative below. Choose which accounts and devices to enroll, review their terms, and decide who can access the tailnet before changing anything. Make a private backup of existing configs, never publish them, and record how to restore them.

The Homebrew formula listed stable 8.0.55 on 2026-11-05 and names the executable cliproxyapi. The v8 config below comes from the supplied guide and the upstream example at the linked commit. The research did not prove the exact release in which each v8 field first appeared or test 8.0.55 against that example. Before use, compare the installed release's own example, help and release notes; stop if the layout or flags differ. config-version: 8 is a schema marker, not a promise that all major-version-8 binaries accept every later field. Pin and record the exact installed version and matching config reference. Don't silently apply this YAML to an older v6/v7 layout.

Setup steps

1. Install and inspect the macOS hub

These commands are for the reader to run, not commands executed in this research:

brew install cliproxyapi
brew list --versions cliproxyapi
command -v cliproxyapi
cliproxyapi --help
brew info cliproxyapi
lsof -nP -iTCP:8317 -sTCP:LISTEN

Homebrew documents brew services start cliproxyapi and the binary at $(brew --prefix)/opt/cliproxyapi/bin/cliproxyapi. Its documented service config path is $(brew --prefix)/etc/cliproxyapi.conf; confirm it with the installed quick start and service definition. Do not paste the Linux ./cli-proxy-api command into a Mac shell. Check pmset -g and choose an appropriate sleep policy so the hub stays reachable. Check whether the port is already in use before starting.

2. Configure local listening and secrets

Back up the existing config and compare it to the version-matched example. Use two independent, long random values generated locally: one downstream access key and one management secret. Do not paste actual values into chat, shell history, screenshots, source control, or shared tickets. Protect the config and auth directory with user-only permissions. The following is a partial configuration, not a replacement for other fields in the installed example:

config-version: 8
server:
  host: "127.0.0.1"
  port: 8317
  trusted-proxies: ["127.0.0.1", "::1"]
management:
  allow-remote: true
  secret-key: "<independent-management-secret>"
access:
  api-keys: ["<independent-client-access-key>"]
routing:
  strategy: "round-robin"
  session-affinity: true
  session-affinity-ttl: "1h"
  retry:
    request-retry: 3
    max-retry-interval: 30

The local bind prevents direct LAN exposure. allow-remote: true is needed for the gist's remote management approach, but exposes a powerful administrative interface through the same proxy endpoint. Prefer leaving remote management off when it is unnecessary and administer locally. If enabled, constrain access with tailnet grants or ACLs and protect the management key separately. The supplied config trusts loopback proxies; verify the installed release and Tailscale forwarding behavior before relying on forwarded client identity. Tailnet membership alone is not a complete authorization policy.

Before login, confirm the service's config path and effective auth directory from its definition and version-matched configuration. The gist uses ~/.cli-proxy-api; do not assume that path if your configuration overrides it. On macOS, inspect the confirmed paths with ls -ld and stat -f '%Su %Sp %N'. The service user must own or have the intended access to them. For files and directories owned by your service user, use chmod 600 <config-file> and chmod 700 <auth-directory>, then restrict individual credential files to mode 600. Replace placeholders with the confirmed paths; do not recursively change a shared Homebrew directory. Check ACLs with ls -le if access remains broader than expected. Apply the same restrictions to backups. Stop before login if ownership or the service's paths are unclear.

Start only after reviewing the configuration:

brew services start cliproxyapi
brew services list
lsof -nP -iTCP:8317 -sTCP:LISTEN

Confirm the listener is on 127.0.0.1, not 0.0.0.0 or a public interface. Service startup and config parsing must be checked in the installed service's logs. Stop and correct errors before exposing the endpoint.

Before enrolling accounts, complete step 4 and test transport. This macOS service-to-Serve arrangement has not been runtime tested here. On the hub run curl -i --max-time 10 http://127.0.0.1:8317/v1/models without a key. From an authorized second machine run curl -i --max-time 10 https://<hub>.<tailnet>.ts.net:8317/v1/models. With client authentication configured, both should return an authentication rejection from CLIProxyAPI. A timeout, TLS failure, or Serve gateway error does not pass. An unauthenticated success requires checking access-key enforcement. Matching rejections establish basic forwarding only; after enrollment, perform the authenticated model-list and inference checks below.

3. Enroll accounts on the hub

The gist gives -claude-login, -codex-device-login, -codex-login, and -no-browser flags. Verify each against cliproxyapi --help for the installed version first. For example, if the help confirms them:

cliproxyapi -claude-login
# Optional Codex, if permitted for your account and confirmed by --help:
cliproxyapi -codex-device-login

Ensure the command uses the same config and auth directory as the service; check --help and the service definition for the supported config flag and working directory. Do not assume the CLI and service share paths. The user completes the browser login. Repeat the appropriate login flow once for each intended account, explicitly selecting the correct account in the browser. Then use the local management UI or supported management tooling to confirm each expected account is present without disclosing token contents. Repeating a login is not proof that a second distinct account was added; verify account identity in the supported UI.

For a headless hub, the gist describes -no-browser and forwarding the Claude callback on port 54545 from a client: ssh -L 54545:localhost:54545 <hub-ssh-host>. Start the tunnel first and follow the login command's actual instructions. The gist identifies port 1455 for Codex browser login; device login avoids that callback when supported. Treat callback URLs and codes as secrets and close the tunnel after login. Validate current flags and callback ports rather than assuming they are stable.

4. Publish privately through Tailscale

Install and sign into Tailscale on the hub and each intended client, then check tailscale status and the tailnet's device access rules. With MagicDNS and HTTPS available, the gist uses:

tailscale serve --bg --https=8317 http://127.0.0.1:8317
tailscale serve status

Check the actual generated hostname and port in status. The intended URL is https://<hub>.<tailnet>.ts.net:8317. Tailscale Serve exposes the service to authorized tailnet peers, subject to tailnet policy; it is distinct from public Funnel. Confirm HTTPS certificate and client authorization behavior using the current Tailscale Serve documentation. Do not enable Funnel or router port forwarding. A client key remains necessary even on a private network.

5. Configure Claude Code on the execution machine

Prefer an isolated directory. Create ~/.claude-hub/settings.json with the following, substituting the actual hub URL and client key privately:

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://<hub>.<tailnet>.ts.net:8317",
    "ANTHROPIC_AUTH_TOKEN": "<client-access-key>"
  }
}

The downstream key is stored in this client file and grants access to the hub, so protect it like other credentials. Run chmod 700 "$HOME/.claude-hub" and chmod 600 "$HOME/.claude-hub/settings.json" after creating them. Keep it out of synced public folders and source control. Then run CLAUDE_CONFIG_DIR="$HOME/.claude-hub" claude. A separate directory may require its own onboarding or preferences; it is not a substitute for verifying credential isolation or current Claude Code behavior. Keep the normal ~/.claude configuration intact. If the directory already exists, back it up and merge settings rather than overwriting it. See T3's separate configuration guidance.

T3 Code runs providers on the selected environment's host. Configure that host, not merely the phone or browser displaying T3. The supplied gist describes a separate Claude provider instance with its own config directory, or instance environment variables with the token marked sensitive. Confirm the current UI and launch context before relying on them. A standalone terminal test on another machine does not prove the T3 provider inherited the settings.

6. Optional Codex client

Use a separate CODEX_HOME, preserve an existing config.toml, and check the installed Codex version's current configuration documentation before applying this gist-supplied example:

model_provider = "cliproxy"

[model_providers.cliproxy]
name = "CLIProxyAPI"
base_url = "https://<hub>.<tailnet>.ts.net:8317/v1"
wire_api = "responses"
requires_openai_auth = false
supports_websockets = true
experimental_bearer_token = "<client-access-key>"

Run with CODEX_HOME="$HOME/.codex-hub" codex. The bearer token in this file is sensitive. After creating the directory and file, use chmod 700 "$HOME/.codex-hub" and chmod 600 "$HOME/.codex-hub/config.toml". Config field names and websocket support are version-dependent and were not tested here. Theo reports a performance benefit from websockets; no benchmark was independently verified. For T3, the gist says select Use existing CLI on the execution host; Continue with ChatGPT uses a different authentication path. The optional usage-provider integration needs a management key and therefore expands the exposure of that powerful secret. Check the current T3 version and its permissions before enabling it.

Linux alternative

The supplied gist recommends its Linux installer and says it creates ~/cliproxyapi, config.yaml, and a user service. Inspect the installer and its version before running any remote script. On that particular installer, the gist uses cd ~/cliproxyapi and ./cli-proxy-api; verify the actual installed binary and help. It suggests systemctl --user enable --now cliproxyapi and loginctl enable-linger to keep the service running without an interactive login. Service names and config locations differ for other packages, including Arch. Review sleep settings and security consequences before changing them; masking sleep targets affects the whole machine. Apply the same loopback bind, secrets, and tailnet restrictions as on macOS.

Validation, troubleshooting and rollback

  1. On the hub, verify the service is healthy, the port listens only on loopback, the configured auth directory is the one used by the service, and each intended account is visible. Inspect logs without sharing tokens, prompts, or account files.
  2. From an authorized second machine, confirm MagicDNS and tailscale serve status. Use a client that supplies the access key privately to request /v1/models. A JSON model list establishes endpoint reachability and client-key acceptance only; it does not prove a particular upstream account or model request works. Avoid putting the key in shell history or a process command line.
  3. Make one small, permitted request in the isolated Claude configuration. Confirm the actual model, response and expected account in supported provider/proxy views. Test the T3 environment separately. Check logs and usage without assuming a successful response proves affinity, failover or terms compliance.
  4. A 401 can mean a wrong downstream key or expired upstream grant. Identify which layer returned it before rotating a key or repeating login. The gist says a Codex token_invalidated grant requires re-enrollment. Rate limits, a disabled account, a single available credential, or a model mismatch may prevent a request even when /v1/models works. Do not repeatedly retry an unknown failed operation as if it were free.
  5. For DNS or TLS failures, check tailnet membership, access rules, MagicDNS, Serve status and the exact hostname first. The gist proposes a macOS resolver override for a specific DNS issue; do not apply it blindly because it changes system DNS configuration. For unexpected account switching, inspect the installed version's affinity settings and safe usage metrics; cache writes alone cannot conclusively diagnose routing.
  6. To roll back, point clients back to their previous configs or stop launching with the separate config directories. Remove the hub base-URL/token overrides from any T3 provider instance and shell startup files you edited. If using isolated configs, return to your normal launcher without CLAUDE_CONFIG_DIR or the alternate CODEX_HOME; retain the isolated files privately until rollback is confirmed. If you edited normal config files, restore the private pre-change backups to those exact paths after preserving any subsequent changes. Stop and unregister the Homebrew-managed service with brew services stop cliproxyapi, verify it is stopped with brew services list and that lsof -nP -iTCP:8317 -sTCP:LISTEN shows no proxy listener, remove only the relevant Serve mapping using the syntax shown by tailscale serve --help, and verify tailscale serve status. Restore backed-up files if edited. Revoke or remove proxy credentials and keys through supported account and management controls if retiring the hub, and securely dispose of its auth files and backups according to your retention needs. Do not delete unrelated Serve mappings or existing configs.
