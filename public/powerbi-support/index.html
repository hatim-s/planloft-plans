Build a native UnifyApps reporting experience from Power BI definitions, using the existing Solution Builder to provision and assemble the application. Start by retaining Power BI as the calculation engine. Add complete backend replacement only after extraction, identity, and numerical parity are established.

This plan consolidates five independent Terra cross-checks of vendor documentation and platform source. It describes engineering to add, not an already working migration feature. Source was inspected and rechecked at uacode/main commit dbee333b3483095061456383defbaa029af431df, with a clean checkout. No live tenant conversion, benchmark, security test, or migration acceptance has run. Prepared 30 October 2026.

A rebuilt chart is accepted only when its values, filters, access rules, and refresh behavior have an explicit source-to-target contract and supporting evidence.

Context

Product outcome

A user selects a published Power BI report or supplies an inspectable export package. The platform inventories the report, its semantic model, and its upstream dependencies; explains what it can reproduce; and proposes a native application. The user can review conversion gaps before building. The resulting app uses authenticated backend workflows for data access and supports focused regeneration without losing unrelated edits.

There are two delivery modes. Bridge mode replaces the report interface and continues querying Power BI. Native mode also replaces ingestion, transformations, semantic calculations, refresh, and security enforcement. The interface must state which mode applies. Bridge mode does not remove the Power BI dependency or establish a licensing saving.

Approach

Phase 1: a bounded, verified bridge

Accept a published report through an authorized connection, or a zipped PBIP package containing PBIR and TMDL. Preserve raw definitions, normalize their meaning into a migration specification, then generate the existing Solution Builder contracts. The app calls typed backend workflows that query the original Power BI model. Dataflow definitions are inventoried and captured where authorized, but their execution remains upstream during bridge mode.

Initially support explicitly mapped native visuals such as KPI cards, tables, ordinary bar/line charts, and basic slicers. Report actual supported mappings from the implemented compatibility registry. Do not promise all standard visuals merely because they share a name. Matrix semantics, Top N ties, drill-through, cross-highlighting, bookmarks, field parameters, custom visuals, calculation groups, and paginated reports require their own support decisions and checks.

PBIP is a directory project; a lone .pbip pointer is insufficient. A live-connected report may reference a remote model instead of including it. Report exports do not include upstream dataflow definitions. PBIX download remains available as a source acquisition option, but arbitrary PBIX parsing is outside the first importer contract.

Phase 2: selected native models

Add analytical storage provisioning, original-source ingestion, a supported subset of Power Query M transformations, reusable metric definitions, server-side row/column policies, and refresh/recovery. Migrate a bounded model and compare it with Power BI before cutover. Keep unsupported constructs in bridge mode or block native conversion with an actionable reason.

Do not create a Mongo object for every fact table or compute governed totals in the browser. Operational metadata and user-managed records can use Storage objects; analytical facts belong in an explicitly provisioned analytical database or the existing warehouse.

Import specification

Introduce a versioned PowerBiMigrationSpec schema and durable import-run record. Store raw files in the platform blob capability and retain references, hashes, source paths, source IDs, retrieval time, and the source model/report version when available. Raw source remains the authority; indexed summaries support discovery.

The specification must represent:

  • Reports, pages, visuals, field bindings, filters at each scope, sort order, interactions, navigation, and resources.
  • Tables, columns, native types and precision, measures, calculated columns, partitions, M expressions, and source references.
  • Relationships including cardinality, active state, filter direction, and security propagation; hierarchies and calculation groups when present.
  • Roles, RLS/OLS definitions, dynamic identity usage, and the target identity/policy mapping.
  • Upstream dataflows, connection references, refresh order, parameters, freshness, and missing dependencies.
  • For every source element: target mapping, support state, reason, source provenance, and acceptance evidence reference.

Use separate import and build state. A useful sequence is discovered → extracted → analyzed → awaiting_review → approved → provisioned → built → validating → accepted, with explicit failed, blocked, and partial outcomes. A builder's completion event cannot set the import to accepted.

New skill

Add powerbi-migration as a platform agent skill, registered for the Solution Agent and discoverable for Power BI import/rebuild requests. Author it in the existing e_skill_ai_agent asset mechanism and include it in configs/platform-features/ai-agents/platform/ai-sdlc/solution-builder-assets.json. Use platform-generated asset IDs rather than inventing a concrete record ID in this plan.

The skill must instruct the agent to:

  1. Establish bridge or native scope, chosen report/package, selected connection, and permission boundary.
  2. Use verified extraction actions, preserve incomplete or stale results, and retain raw definitions.
  3. Read the normalized specification and compatibility report; never infer absent model logic from screenshots.
  4. Distinguish report-local Power Query from upstream dataflows and external SQL/API implementations.
  5. Produce requirements, source mappings, app/workflow briefs, and required objects using existing planning and approval rules.
  6. Bind real IDs before dispatch and route integration calls through managed backend connections.
  7. Require identity, numerical, interaction, freshness, and deployment evidence before accepting the conversion.
  8. Resume by import-run and task identity, preserving successful assets and reconciling uncertain writes.

Bundle references for supported constructs, artifact inventory, exact connector operation names, specification schema, error taxonomy, and acceptance checks. The skill coordinates implemented tools; it must not describe missing actions as available. Extend the existing plan/data/app/workflow/build skills only with the routing and handoff guidance they need. The current app-brief skill should preserve the source report's requested identity instead of inventing a new palette or font system during faithful migration.

Steps

1. Repair Power BI extraction and query contracts

Modify configs/connectors/power_bi/power_bi_get_semantic_model_definition.json, its workflow-node schema, the operation helpers, and the consuming extraction workflows.

Return the definition on immediate HTTP 200. On HTTP 202 preserve status, operation ID, Location, and Retry-After; poll the documented operation state until terminal, with bounded retries, deadline, throttling, and explicit failure. Replace the fixed ten-second delay in 69e36af3abd5811312ec446b.json. Do not retry an unknown external mutation as part of generic retry logic.

Fix DAX result handling in power_bi_execute_query.json and 698e2e36c96e8877f249f272.json. Preserve query errors even with HTTP 200; distinguish empty results, failures, and incomplete results. Do not invent API pagination. Discovery must follow available continuation and retain per-item failures, scan freshness, schemaRetrievalError, and schemaMayNotBeUpToDate.

Stage a complete validated extraction before replacing the prior index. The current join workflow deletes indexed records before rebuilding, so a later parse failure can discard useful context.

Acceptance: immediate and asynchronous definitions both work; timeout/throttle/failure are explicit; empty and truncated DAX results differ; incomplete scans cannot pass completeness; prior valid index survives a failed refresh. Validate API contracts with controlled fixtures, then a separately authorized tenant read.

2. Add connector actions for source capture

Names below are proposed resource names, not existing capabilities. Register both connector definitions and workflow-node schemas, expose intended agent operations, and cover lookup, authentication audience, permission requirements, and output contracts.

Proposed action API or behavior Output and acceptance
power_bi_get_report_definition Fabric POST /v1/workspaces/{workspaceId}/reports/{reportId}/getDefinition Raw PBIR/PBIR-Legacy parts, resources, model reference, and complete operation status. Handle label/permission restrictions.
power_bi_fetch_dataflows Power BI workspace dataflow listing IDs, type, workspace, and completeness evidence. Gen1 listing must not imply complete Gen2 discovery.

Reuse existing model-definition, operation-state/result, report-download, scan, and DAX actions after repair. Add any missing scan-status action only after confirming the current catalog gap. Expose connection/refresh metadata needed for inventory through narrowly scoped read actions where existing scans do not supply it. Credentials are rebound through managed connection selection and are never exported into the document or app.

Acceptance: an authorized package captures the report, model, Gen1/Gen2 dependencies and resources; missing access produces a named gap. Each definition can be decoded and linked to its origin without guessing filenames or source identity.

3. Implement package validation, parsers, and the gap report

Create an importer service/module following repository ownership conventions rather than embedding the migration in prompt text. Accept bounded zipped PBIP/PBIR/TMDL packages and authorized API extraction outputs. Reject unsafe paths, excessive expansion, malformed definitions, unsupported payload types, and missing required parts. Establish and publish actual file/count/size limits before launch.

Use schema-aware PBIR/PBIR-Legacy readers and a TMDL-aware parser or supported parser library. Preserve unknown constructs and original text. Replace regex-only semantic projection; extract all table measures rather than only a Key Measures path. Parse Gen1 JSON and Gen2 M definitions into dependency-aware transformation descriptions while retaining the original scripts.

Generate a report with counts and per-element statuses supported, manual, or blocked. Make omissions navigable to the original source. Separate missing input from unsupported logic. The report should support reviewing bridge mode even when native translation is blocked.

Acceptance: fixture packages cover remote model references, multiple tables of measures, inactive/many-to-many/bidirectional relationships, missing dataflows, unsupported custom visuals, and malformed parts. Every source element is accounted for. No silent drops or fabricated sample records.

4. Wire the migration skill into Solution Builder

Create the import entry flow: select report or upload package → capture/validate → inspect compatibility → choose mode → approve scoped plan. Persist the import ID and specification version in the solution's linked context using a declared schema extension. Do not add arbitrary undeclared fields to Populate Plan.

Implement a deterministic adapter from the approved specification to objectSpecs, workflowBriefs, and appBrief. Include source references and exact query/visual contracts. Reuse Provision Plan Assets, Bind Plan, Generate App, and Generate Workflows. Separate plan approval, successful provisioning, workflow deployment, solution publication, and migration acceptance.

For bridge mode, do not seed copies of Power BI tables. Create typed callable workflows for supported chart queries. Inputs represent allowed filters and pagination/selection behavior; outputs include typed columns, units, rows, freshness, completeness, and errors. Keep metric definitions reusable across charts rather than generating unrelated calculations per screen.

Acceptance: two different attachments arrive intact through the app handoff; all asset placeholders resolve; generated app calls deployed workflows with the agreed signatures; a failed lane is resumable without recreating successful assets. Verify multi-file behavior at runtime rather than treating index-zero mapping syntax as a confirmed bug.

5. Enforce identity and serve bridge queries safely

Trace the full caller → callable workflow → selected managed connection → Power BI principal path. Use a declared per-user OAuth design when per-user Power BI RLS must apply. A service principal may query only supported models; this connector's Execute Queries endpoint excludes service-principal use for RLS/SSO models. A shared privileged account is not a per-viewer security design.

Validate report/model allowlists and filter inputs server-side. Scope caches by tenant, effective identity/security context, model/version, normalized query, and filter values. Handle result limits and request quotas explicitly. UI filters cannot substitute for authorization predicates. Never expose connector credentials or arbitrary unauthenticated DAX endpoints in browser code.

Acceptance: allowed users see their intended results; unauthorized and cross-user calls fail; viewers cannot select another model or remove mandatory restrictions; caches and exports cannot leak another identity's rows. Verify Viewer/Build access and elevated workspace roles separately because elevated roles can bypass RLS.

6. Add differential validation and release evidence

Reuse the existing Text2DAX comparison components where appropriate, including .../WORKFLOW_DEFINITION/69f5ab465f077f7ce703af2c.json, after inspecting their actual comparison semantics. Store the expected side independently from the generated implementation and bind both to the same filters, snapshot/freshness boundary, timezone, and effective identity.

Compare detail rows, totals, subtotals, ratios, distinct counts, BLANK/NULL behavior, date calculations, formatting/units, slicers, ties, navigation, drill-through, cross-filtering, and role combinations for the supported scope. Use justified precision tolerances and deterministic ordering; do not hide semantic differences through loose thresholds.

Require deployed workflow versions and real callable responses, successful ingestion/reconciliation counts where applicable, visible browser journeys, and negative access checks. Record blocked/failed/unverified cases. Reconcile partial publication explicitly; current linked deployment is not a transaction that automatically rolls back every earlier success.

Acceptance: one representative bridge report has a signed-off compatibility inventory, numerical comparisons, user-isolation checks, working interactions, and deployment receipts. Test load/latency and refresh behavior against the chosen scope before making scale or cost claims.

7. Add native conversion as a separate capability

Provision an analytical target through supported APIs, including ownership, quotas, schema lifecycle, indexes/materialization, retention, recovery, and monitoring. Integrate this lifecycle into solution assets and deployment. Existing internal StarRocks provisioning alone does not provide this user-facing contract.

Reconnect original sources. Define snapshot/backfill and incremental processing, stable keys, deduplication, deletes, schema changes, checkpointing, retries, and freshness. Stream load must reconcile total, loaded, filtered, and unselected rows; a request accepted by the platform is not proof all data landed.

Implement an explicit subset of M operators and DAX semantics. Start with bounded transformations and simple aggregates; handle ratios at the correct grain. Relationship direction, inactive relationships, CALCULATE, time intelligence, calculation groups, dynamic identity, BLANK, and privacy/query-folding behavior require separate compatibility rules. Agents may propose SQL/workflow equivalents; execution and differential validation determine whether they are accepted.

Create a reusable metric layer and mandatory server-side RLS/OLS for every query and export path. Customer database isolation is not per-user row security. Keep native conversion blocked where policy equivalence cannot be established.

Acceptance: one bounded model runs from original sources without Power BI execution, meets its refresh/recovery contract, enforces mapped security, and passes differential checks before cutover. Maintain a reversible routing decision and original definitions while native acceptance remains incomplete.

Risks and mitigations

Risk Required handling
A successful response contains partial data or a query error Preserve completeness/error state and block acceptance.
Screenshot similarity hides different numbers Use source definitions and independent numerical oracles.
A regex parser silently loses semantics Preserve raw parts, parse structurally, and account for unsupported elements.
Privileged shared connections expose another viewer's data Establish effective identity and verify negative access across queries, cache and exports.
A generated metric changes filter context Keep Power BI execution in bridge mode; differential checks gate native translation.
Ingestion reports success after dropping rows Reconcile counts and reject unexpected filtered rows; retain diagnostics.
Deployment partially succeeds Record asset versions and outcomes, resume in place, and never assume automatic global rollback.
Vendor claims become product promises Label claims, define our support matrix, and publish only measured results.

Open questions and implementation entry criteria

Select a representative report, its owner, permitted read access, and acceptance users. Inventory its model size, storage mode, dataflows, visual types, RLS/OLS, source topology, refresh expectations, and custom constructs before sizing delivery. Establish the target app runtime and actual chart capabilities through the generated application's source and browser evidence.

Confirm the per-viewer identity strategy and tenant API settings. Confirm ownership and provisioning API for native analytical storage before committing to phase 2. Decide whether faithful layout preservation or deliberate redesign is requested; default to preserving the report's stated structure and visual identity.

The first engineering milestone is a reliable extraction package and compatibility report. The first product milestone is one accepted bridge report. Native replacement is complete only when source ingestion, metric semantics, access policy, refresh/recovery, and user journeys pass their own acceptance checks.
