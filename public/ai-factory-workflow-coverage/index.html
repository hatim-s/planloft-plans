7. How we plan to increase adoption

Rather than asking engineers to open AI Factory manually for every task, adoption scales through two high-frequency entry points already embedded in daily workflow—backed by hard write-scope guards and a shared rollout tracker.

1. Slack mention bot relay (AOA-style intake and thread bridge)

Bring Factory directly into Slack threads using the same pattern proven by the AOA Slack bridge: explicit mentions and scoped watchers, allowlist and relevance gating, durable thread-key deduplication, and explicit reply posting back to the originating thread.

  • Explicit trigger & allowlist: Engineers mention @AI Factory inside an approved Slack thread (or register a scoped channel/thread watcher). Bot messages, top-level noise, and unauthorized channels or callers are filtered out before dispatch.
  • Stable thread-key deduplication: Each thread maps to a deterministic key (slack:<workspace>:<channel>:<thread_ts>) paired with its accepted Factory run ID so retries and follow-up mentions reuse the same session instead of spawning duplicates.
  • Read-only Diagnose first: Every Slack-triggered run starts in read-only Diagnose with a pinned QA run or trace link and treats thread text as evidence rather than write instructions. Repair loops start only after an owner approves the diagnosis and write scope.
  • Pilot proof & next step: A retrospective 5-case Slack debugging pilot (Nov 16–23) produced 3 new Factory diagnosis reports (4 of 5 cases involved Factory, including 1 prior investigation; 1 HTTP 402 billing issue stayed with the quota owner). The local event mapper and fixture tests are complete; next step is binding the Slack connector to a Factory WATCH trigger in QA shadow mode.

2. Moving PR review and CI triage into AI Factory by default

Make AI Factory the default review and CI triage layer across team PRs as soon as the merged #36564 advisory guards are live in QA.

  • 2–3 independent passes on the exact same GitHub head:
    1. Author pass — verifies diff hygiene, scope compliance, and focused test evidence before requesting review.
    2. Intermediary developer pass — checks correctness, edge cases, and regression risk.
    3. Tech lead pass — audits unresolved findings and release risk before human approval and merge (two passes suffice only when the lead explicitly combines intermediary and final review for low-risk changes).
  • Strict safety invariants: Advisory review runs can never push branches or open PRs; any new commit invalidates earlier receipts; CI triage compares red checks against the pinned base with at most one bounded retry for transient failures.
