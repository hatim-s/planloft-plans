A workflow can be valid enough to save and still deserve a second look. This integration gives the Workflow Agent that second look through best-practice lint warnings, while clearly confirming that the current version was saved.

The workflow is saved. A warning is advice for a possible improvement, not a failed save or a demand to fix everything.

The change in one glance

Before this integration With best-practice lint
Valid workflow → saved ID and version Valid workflow → saved ID and version, plus advisory findings
Agent sees that the save succeeded Agent sees that the save succeeded and which design choices deserve review
Best-practice concerns may go unnoticed Findings carry a category, rule ID, impact in the message, and a source location when available
Agent moves on after saving Agent can apply a relevant improvement in another save, or explain why the design is intentional

The four scenarios below assume that compilation, backend validation and storage requirements pass. Best-practice lint does not make an otherwise invalid workflow saveable. “Before” means a successful save without this integration's best-practice feedback; other validators may already flag some problems.

01 · An integration credential is embedded in an HTTP step

Security · CHECK_39 · critical impact · warning severity

A nightly supplier sync sends a password as a literal input to its HTTP step. The request can be structurally valid, and the workflow may save successfully, even though changing environments now means editing that credential in the workflow.

{
  "inputs": {
    "password": "SYNTHETIC_EXAMPLE_ONLY"
  }
}

Previously, the save could succeed without best-practice feedback. Now it still succeeds, with this warning title:

Hardcoded critical input detected [critical]

The warning explains that critical inputs appear to contain hardcoded text and recommends mapping them to variables, pills or configuration. The agent should move an actual credential to the platform's supported secure configuration or connection mechanism and save the improvement. It should not interpret the finding as evidence that the first save failed.

A useful judgment call: a fixed API URL can also match the evaluator's broad heuristic. If an endpoint is intentionally constant, the agent should assess that context rather than rewrite it automatically. This check is a heuristic, not proof of a leaked secret.

02 · A lookup runs, but nothing uses its result

Usability · CHECK_1 · medium impact · warning severity

An invoice workflow fetches a customer's profile, then calculates the invoice entirely from the trigger payload. No later step reads the profile lookup's output. That extra request adds latency without contributing to the result.

Invoice received
  → Fetch customer profile
  → Calculate total from invoice payload
  → Return invoice total

The new warning title is:

Remove unused node outputs to prevent unnecessary delays [medium]

The agent can remove the lookup if it has no purpose, then save the leaner version. But unused output is not the same as an unnecessary action. A notification or write can matter for its side effect even when nothing reads its output. The agent should keep such a step when the requested behavior needs it.

What changed: a successful save now starts a design review. It does not authorize deleting every step with an unused return value.

03 · A connector is configured to retry too aggressively

Performance · CHECK_4 · medium impact · warning severity

An order-export workflow retries a supplier request ten times, starting with a five-second delay. That may help a flaky endpoint occasionally, but it can also leave orders waiting much longer than intended.

{
  "retryConfig": {
    "enabled": true,
    "count": 10,
    "initialDelay": 5000,
    "maxDelay": 60000,
    "backOffFactor": 2
  }
}

The warning title is:

Configure node level retries optimally to prevent slowdown [medium]

In the inspected evaluator, enabled retries pass this check when count is 0–5, initial delay is 0–1,000 ms, maximum delay is 0–30,000 ms, and backoff factor is 1–5. The example exceeds several of those thresholds.

The agent should weigh the supplier's recovery behavior against the user's latency requirements. It can reduce the retry settings in a later save. A deliberately longer retry policy may be appropriate, but the agent should explain that choice instead of changing it solely to silence lint.

04 · A status poll runs every 30 seconds

Performance · CHECK_55 · high impact · warning severity

A shipment tracker polls a carrier every 30 seconds even though the business only needs minute-level updates. The workflow is valid, but the polling interval can waste requests and increase rate-limit pressure.

{
  "cron": "INTERVAL",
  "interval": 30,
  "frequency": "SECONDS"
}

The new warning title is:

Scheduler frequency below 1 minute [high]

The evaluator flags explicit interval schedules below 60 seconds. It does not claim to analyze every custom CRON expression. The agent can move to one minute if that meets the requirement. If the user explicitly needs faster polling and the platform permits it, the agent should preserve that requirement and explain the tradeoff.

What the agent actually receives

The adapter turns evaluator results into diagnostics. This example illustrates the returned shape for the hardcoded-input scenario. The node ID, source line, saved ID and version are illustrative; the rule name and message formatting come from the implementation and platform rule metadata.

{
  "ok": true,
  "workflowId": "example-supplier-sync",
  "version": 7,
  "message": "Workflow saved successfully at version 7. Best-practice lint warnings are advisory. The current workflow is saved. Apply relevant improvements in a later save; not every warning needs a change.",
  "warnings": [
    {
      "severity": "warn",
      "rule": "bestPractices.CHECK_39",
      "stage": "bestPractices/security",
      "nodeId": "example-http-step",
      "line": 12,
      "message": "Hardcoded critical input detected [critical]: Critical inputs (passwords, secrets, tokens, IDs, or API URLs) appear to contain hardcoded text values. This reduces scalability (hard to change environments) and poses a security risk. You should map these fields to variables, pills, or configuration objects (e.g. {{ variable }}).",
      "suggestion": "Critical inputs (passwords, secrets, tokens, IDs, or API URLs) appear to contain hardcoded text values. This reduces scalability (hard to change environments) and poses a security risk. You should map these fields to variables, pills, or configuration objects (e.g. {{ variable }})."
    }
  ]
}

This is an excerpt, not the entire success response. Other response fields can include the workflow summary, creation status, changes and test-case information. Line and column information come from the compiler's source map when it can locate the returned node. A workflow-level finding may have no source line.

Critical is the platform rule's impact label. The diagnostic severity remains warn. It does not become a save error because its message contains “critical.”

Three outcomes the agent must keep separate

Tool outcome What it means What the agent should do
ok: true, with lint warnings The current version was saved successfully Confirm the save. Review warnings and apply relevant improvements in another save.
ok: false, with validation errors This attempt did not save successfully Fix blocking findings. Review advisory warnings where relevant, then try again. Infrastructure or uncertain-save outcomes require their own recovery guidance.
Save succeeds, but a best-practice check is unavailable Saving succeeded; lint coverage is incomplete Confirm the save and name the coverage gap. Do not claim that the unavailable check passed.

An appropriate agent reply is:

Saved version 7 successfully. The lint check flagged a hardcoded credential in the HTTP step. I recommend replacing it with secure configuration. The saved version is available; that improvement would be a follow-up save.

If the agent makes the improvement immediately, it should confirm the new save as well. The first version was already persisted; the later version records the enhancement.

What these warnings do not cover

The integration explicitly returns advisories for three skipped evaluator groups. Storage depends on index recommendations for persisted workflows. Recursion writes reports for referenced workflows. LLM can invoke paid providers, independently of the requested check IDs. Save-time lint skips those effects.

A missing or failed evaluator result is also reported. For example:

{
  "severity": "warn",
  "rule": "bestPractices.CHECK_3",
  "stage": "bestPractices/performance",
  "message": "Best-practice check unavailable: CHECK_3 produced no result. This advisory does not block saving."
}

That message describes a gap in the check, not a defect the agent should try to repair in the workflow.

Evidence and scope

This guide describes PR #31495, at the reviewed integration revision 85666bb18fd. It is not a claim that this behavior is deployed everywhere today.

During the October 19 integration audit, the independent Luna review inspected the 88-rule Orbit UAT catalogue and 14 deployed evaluator graphs. Live probes verified the repaired adapter's security and usability warnings, including CHECK_39 and CHECK_1. The retry and scheduler examples above are grounded in evaluator source and rule metadata; they were not live-executed for this document. The original temporary probe files are no longer present, so the live findings are reported from that session's recorded results.

These are representative business scenarios, not recovered customer workflows or a claim that a particular historical agent session emitted these exact messages. The examples contain synthetic values only. Local pipeline tests verified that warnings do not prevent saving; the earlier audit did not perform a live save through the combined pipeline.

A quick reading guide

  1. Look at ok, the saved workflow ID and version first.
  2. Separate blocking errors from advisory warnings.
  3. Read the rule, category, message and available source location.
  4. Fix findings that matter for the user's requested workflow. Keep intentional choices with a reason.
  5. Treat unavailable checks as incomplete coverage, not as passed checks or required workflow edits.

The useful outcome is a saved workflow and a better-informed agent, with room for judgment about the next improvement.
