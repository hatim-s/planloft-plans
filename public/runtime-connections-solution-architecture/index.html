The platform already has authentication, user connection storage, builder connection selection, and an engine that can run a workflow with substituted connections. The proposed feature should join those capabilities around a published solution. Its main new responsibility is deciding which account a particular app may use for a particular person.

A connection is a reusable credential-backed account. A solution dependency, a user's link to that account, and the account selected for execution are different records of intent.

Build-time architecture

The source-defined AI FDE agent owns the conversation and dispatch. Solution Planner defines the data model, workflows and app brief. Workflow Agent builds TypeScript DSL workflows and compiles/saves them. Generate App crosses into the code-app engine, whose source and build lifecycle live in agent-platform. These are builder agents; they are not the identity under which a published user's Outlook operation should run.

The relevant chain is:

  1. Create e_solution and associate the conversation case with it.
  2. AI FDE resolves connector keys and asks for accounts through Request Connection.
  3. Solution Planner writes a solution_builder_plan through Populate Plan.
  4. Publish Plan handles plan approval. This is separate from publishing the finished application.
  5. Provision Plan Assets creates objects and workflow stubs, records temporary-to-real ID mappings, and invokes Bind Plan.
  6. Bind Plan resolves references and produces the manifest and builder briefs.
  7. Generate Workflows dispatches Workflow Agent tasks. Generate App dispatches the code-app engine. Their completion paths register assets through Update Solution Record.
  8. The finished solution's deployment publishes its app/workflow assets and records a release.

Builder connection selection is already solution-aware

Request Connection, deployed V125, resolves the case and calls the solution assets resolver. It supports add, update and remove, exact named-account selection, ambiguous-account handling, and a connection picker interface. It passes mode: builder to that interface. Automatic selection is available for a single active account in auto mode.

Its no-card paths register a selected account as a CONNECTION asset or mark an old link REMOVED. Its card path publishes the standard runtime-auth interface and returns pending state. The source Capture Connection workflow 67f8b9e584efea167932f811 separates builder mode from ordinary copilot mode: builder mode records the choice for the caller and updates solution assets; ordinary mode writes run_time_connection_store.

Resolve solution assets, deployed V73, reads solutionId from the case's runtime context, reads solution_linked_assets, excludes REMOVED, and returns assets keyed by class and ID. Its read is capped at 5,000 rows. The function label still mentions a union, but the inspected body reads only the ledger.

Update Solution Record, deployed V135, upserts the asset ledger with a stable row identity, carries version and source commit hash, marks missing assets removed after appropriate existence reads, and calculates solution completion. It also inspects completed workflow nodes for literal connection IDs and links previously unknown connections. Explicitly removed connections stay removed.

That literal-ID discovery is useful dependency bookkeeping. It cannot express that Outlook must use each viewer's account, nor distinguish a builder test credential from a published account requirement.

Current runtime connection behavior

Authentication and storage

Shared frontend forms read connection schemas, test credentials, create/update connections, authorize OAuth, handle callback completion, and notify the opener. /runtime-auth/new/[appName] and the embedded ConnectionFormModal reuse that machinery. A completed OAuth flow produces a real Connection ID; a subsequent workflow records how it is bound.

Create Runtime Connection | ES, deployed V129, accepts integration, agent, optional topic and connection ID. In the topic-aware branch it uses the explicit connection or newest owned active account, checks integration, owner, active status and ID, replaces the previous binding for the agent/user/app/topic, and creates a runtime store row. This is an existing selection-binding mechanism, not an OAuth implementation. It models one chosen account per binding scope, not a list of app-linked candidate accounts with an independent active pointer. The current graph deletes old binding rows before its successful-connection condition; it should not be copied as an atomic selection operation.

Fetch User Connections, deployed V158, reads the agent's connector topics, derives integration names, reads current-user runtime store rows, reads actual Connection records, joins active status, and excludes orphan bindings. It carries topic IDs and synthesizes topic-specific entries from older app-wide bindings for eligible personal OAuth topics. Custom OAuth registration topics are excluded from that inheritance. Default binding-page size is 30; the frontend requests 500. Connector-topic reads are capped at 100.

This is agent-centric. A solution ID or published app ID is not part of the inspected runtime store schema.

Execution has several paths

The source configuration workflow Execute Custom AI Agent Action 66e4c220f82132609342c11f reads run_time_connection_store by agent/user/app. It constructs a map for callable workflows and a context connection for direct actions, with clarification when a required connection is absent.

The pinned Java code also contains newer native paths. ConnectorToolConnections resolves a per-call override first, an explicitly opted-in invoking user's account second, then an agent binding for non-runtime tools. Its runtime lookup queries owned active provider connections newest-first; it does not read the same runtime store selection. LookupToolExecutorImpl does read the store by agent/user/app. RoutineAppTriggerBinder resolves the routine principal's store row. These are distinct resolution policies. No single current resolver can be assumed to govern every call.

For generated applications, the SDK's workflow mutation hook sends /api/workflow/execute/node with app metadata and the existing authentication/routing layer. A callable execution carries connection overrides in inputs.runtimeConnections, keyed by connector app name, beside parameters.

The pinned engine's DeployedWorkflowDefinitionMappingServiceImpl validates that supplied IDs exist and match their app names. It derives a transient workflow mapping from workflow ID, version and the connection map; creates it with an override configuration and a seven-day lifetime; and reuses it subsequently. WorkflowDefinitionServiceImpl replaces node context.connectionId values by app mapping and resolves connection-dependent inputs again. The original saved workflow need not be rewritten for every user.

There are two material limits. An invalid supplied map can be filtered to empty and use the normal deployed mapping, so Personal mode must fail before that fallback. The map is keyed by app name, so one workflow cannot use two independently chosen Outlook accounts through that map alone. Either constrain the first release to one account per integration per operation or introduce explicit node/requirement binding for that case.

Disconnect is currently broader than the requested behavior

Delete Runtime Connection | ES, deployed V122, is not an app-only unlink. Its explicit-connection branch reads a runtime store row by current user and connection ID, calls standard_entities_delete_connections, deletes related knowledge, and removes current-user runtime rows for that connection ID. Those removal filters are not restricted to one solution or topic. The legacy branch also deletes the actual connection.

This corrects the earlier frontend-only description of the operation as unlinking. The PDF promises that other apps keep working, so this workflow must not back that button unchanged. Disabling the connection is also too broad.

Deployment boundary and source drift

The local SolutionServiceImpl deploys linked assets, records their deployed versions, then deploys the solution. Its handlers publish workflows, app code and agents through their existing owners. The Connection handler is a no-op for deploy and restore, because it does not have a versioned connection release to publish.

However, that Java checkout still reads e_solution.linkedEntities; the live object no longer has that field. The local Update Solution Record snapshot is V24 versus UAT V135, and its runtime creation snapshot is V32 versus UAT V129. The duplicated configs/ and internal/src/main/resources/configs/ files inspected have identical bytes for these samples. Implementation must start from a reconciled backend/configuration baseline, not those older resource snapshots. The effective deployed SolutionService binary and its ledger handling remain unverified.

Reuse the workflow engine's account substitution. Add explicit published-app policy and selection before that substitution happens.

Proposed architecture

Keep actual credentials in Connection. Keep solution_linked_assets as the solution asset inventory. Add two narrowly scoped data models, with final names to follow platform conventions.

Versioned integration requirements

solution_connection_requirement describes what a published solution needs. Give each requirement a stable requirementId, plus solutionId, connector appName, display label, purpose text, Enterprise/Personal mode, required/optional status, enterprise connection reference when applicable, and allowed execution targets. Targets identify the workflows/actions that consume the requirement, not merely any workflow the client names.

Requirements must be versioned with the solution release. A publish should not silently change the account policy of an already running old release. The deployment integration needs to pin or materialize the complete requirement set with the release and restore it with that release. Merely adding an object type to the asset ledger is insufficient, because that would deploy its schema rather than its configuration records.

Keep the builder test account in maker-specific preview bindings. It must not become the enterprise default, a published personal fallback, or a shared requirement field used by runtime calls.

Per-user account bindings

solution_user_connection_binding stores one row per tenant, solution/app scope, authenticated user, requirement and execution scope. The row contains the linked Connection IDs and selected Connection ID. An array plus active pointer in one version-checked record is enough initially; separate candidate-account rows can be introduced if volume requires them. Preview bindings use a distinct scope from published bindings.

The selected account must belong to the linked set and remain usable by that user for the required connector and OAuth registration. The backend derives user identity from the session/run. It must not accept arbitrary user IDs or expose stored OAuth client secrets through the requirements response.

Removing an app link updates only this binding. If it was selected, the operation validates an explicit replacement or applies a documented deterministic policy atomically. With no replacement, return needsConnection; do not select the builder's account. Credential deletion and provider revocation remain separate account-management actions.

A shared server-side resolution step

Add one solution execution boundary that derives the solution and release from the authenticated application, verifies the requested operation is part of that release, reads requirements, and resolves Enterprise or Personal bindings. It validates account ownership/access, connector, active state and registration compatibility before delegating to the existing workflow executor with the resulting runtimeConnections map.

The frontend should request an operation, not be the authority for which credential it may execute. App-scoped headers identify context; they do not by themselves establish the account policy. Reject missing/invalid Personal bindings before the engine can fall back onto a statically configured node credential.

Most configuration, status listing and binding operations can be platform workflows. A small Java/service integration is appropriate wherever needed to enforce application identity, release ownership, fail-closed execution and atomic updates. A workflow wrapper is viable only if existing backend authorization ensures generated code cannot bypass the same policy by calling the underlying operation directly.

Connect the published-app UI and generated SDK operation helper to this boundary. Agent tools used inside the same app should resolve through it as well; do not leave agent, lookup, callable and routine paths with contradictory selected-account rules. Async work needs an explicit execution principal and captured binding policy, not an assumption that a browser session still exists.

Build and publish integration

Extend planner output with structured connection requirements. Carry stable requirement IDs through Populate Plan, Bind Plan, workflow briefs and the generated app manifest. Preserve explicit Enterprise/Personal choices; do not infer the mode from the owner of whichever Connection ID was picked.

The workflow builder can use the maker's test account to discover schema and verify inputs, while marking the requirement's consuming operations for runtime resolution. First publish validates completeness, pins requirements and workflow/app targets, then uses the existing deployment and Enterprise Brain flow. New-user preview uses empty synthetic binding state, not impersonation or deletion of real user bindings.

The first-open screen reads a sanitized requirement/status response and blocks only on required Personal integrations. Account management reuses the same read model and binding operations. Connect reuses the existing auth form and popup protocol, then links the returned account. Selection persists an explicit account; it must not be implemented by rearranging whichever account the current row helper picks first.

Implementation sequence

  1. Reconcile deployed configuration and backend source, especially ledger-based deployment and current runtime store schema. Retain deployed node IDs and semantics while making intentional changes.
  2. Define the two data contracts, requirement release snapshot and execution target mapping. Decide required/optional behavior, final-account disconnect, and explicit replacement ordering.
  3. Build read, link, select and app-only unlink operations, with current-user identity, ownership checks, unique binding identity and optimistic concurrency. Return business failures explicitly, including HTTP-200 failure envelopes.
  4. Implement the secure execution resolver and adapt one read-only callable operation. Demonstrate two users using different personal accounts with the same enterprise account, before building the whole interface.
  5. Extend planner/manifest/generation contracts and publish validation. Verify requirement snapshots restore consistently with workflow and code versions.
  6. Build builder cards, publish connection review, first-open gate, account manager and new-user preview using the shared frontend auth components.
  7. Verify the complete journey with two users and two apps, expired credentials, removal of the selected/last account, popup abandonment, stale selection writes, release changes, and nested/async workflows. Confirm that app-only disconnect leaves the Connection and other app bindings intact.
