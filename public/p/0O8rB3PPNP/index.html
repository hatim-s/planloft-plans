Six Orbit solutions were built in a single 25 minute window on 28 Sep 2026, producing 21 backend workflows between them. This report breaks down how many workflows each solution produced, how long each one took to go from its first deployed version to its last, and where the build actually broke. Durations over eight minutes are called out in red.

The measurement is deliberately narrow. For every workflow we pull the full deployment history from DeployedWorkflowDefinition and measure the gap between the earliest and latest deploy timestamps. In practice almost every workflow follows the same two-step shape: v1 is a stub that ships the moment the solution scaffolder creates it, and v2 is the real implementation once the agent has written the SQL and Groovy. The gap between those two deploys is the honest measure of how long the work took.

17 of 21 workflows shipped a working v2. The 4 that did not split cleanly into two failure modes, and the more embarrassing one is not the failed workflow.

What the red rows tell us

The long workflows are the ones doing real work, and the correlation is close to perfect. Run Sync Now is a 52 node graph that syncs two Snowflake masters into local objects and takes 19 minutes to assemble. Sync daily emails chains Outlook fetch, GPT-4o analysis, and a bulk upsert across 12 nodes and runs 23 minutes, the single longest build in the set. Filter Lookup Options, at 3m 21s, is a three node lookup that barely needed building.

Node count is a decent but imperfect predictor. The two Store Operations Assistant workflows invert it: Sync SharePoint Documents at 9 nodes takes 16 minutes, while Ask Store Operations Assistant at 4 nodes takes 12. Both are bottlenecked on SharePoint document retrieval rather than on graph size.

Time tracks the external systems a workflow has to reason about, not the number of nodes in it.

The two failure modes

The 4 single-version workflows are not the same problem, and treating them as one number hides the useful half.

Store Performance List Table and Update item status are genuine failures. Their definitions contain nothing but n_StubStart and n_StubResponse, the stub pair the scaffolder emits before any agent has touched the workflow. No SQL was ever written. There is no work to recover, only work to redo.

Store Detail Profile and Sales Pivot Explorer are a different animal, and the more annoying one. Both have complete, working graphs sitting in the draft. Store Detail Profile has seven nodes with real Snowflake SQL and Groovy transforms, written 6m 51s after its v1 deploy. Sales Pivot Explorer has seven nodes, written 8m 12s after its v1. In both cases the implementation exists, was written by the agent, and simply never got deployed. Both still show the orange Undeployed Changes badge in the Automations view with an active Deploy button, and both still document themselves as returning a stub response.

The Advance Auto Parts solution chat says this out loud. Its implementation notes flag Store Performance List Table as reporting no SQL found and describe the fix as ready for node reconnection. The agent knew. It reported the gap rather than closing it.

Steps to close the gap

  1. Deploy the two finished drafts. Open Sales Pivot Explorer and Store Detail Profile in Orbit, confirm the graph still looks right, and hit Deploy. That is the whole fix for 2 of the 4.
  2. Rebuild the two real failures. Store Performance List Table needs its Snowflake query written against V_STORE_WEEKLY_SCORECARD; Update item status needs the storage write for Outlook digest items. Neither has a starting point to salvage.
  3. Add a deploy gate before a solution is called done. Every workflow in this set had a working v2 available. The gap is that nothing checked for undeployed drafts, so 2 complete workflows sat idle. A check on modifiedTime against deploymentState.deployedAt at the end of a build would have caught both.
  4. Flag long builds rather than treating them as slow. Nine of 17 workflows crossed eight minutes, and the ones that did are the ones doing genuine multi-system work. That is the expected cost, not a regression.

Once the two undeployed drafts are shipped, this set is 19 of 21 built and live, with only the two stub-only failures left to redo from scratch.
