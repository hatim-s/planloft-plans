The CORS block, and why CSP isn't the problem

The error Manikya posted:

Access to XMLHttpRequest at 'https://api.mypurecloud.de/api/v2/users/me?expand=station'
from origin 'https://yoda-qa.chargepoint.teleport.sh' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.

CSP and CORS control different things, and only one of them is ours.

CSP (connect-src) CORS
Set by Us, in the response headers of our page Genesys, in the response headers of api.mypurecloud.de
Decides Whether our page may send a request to that host Whether our page may read Genesys' response
Current state Allows https://*.mypurecloud.de and wss://*.mypurecloud.de (packages/network/src/utils/cspHeaders.ts, in the deployed tag …-6fb9419) Genesys doesn't send Access-Control-Allow-Origin for our origin

CSP is fine. If CSP were blocking, Chrome would print Refused to connect to … because it violates the following Content Security Policy directive: "connect-src …" and the request would never leave the browser. Instead we got a CORS error, which means:

  1. The request left the browser and reached Genesys.
  2. Because it carries an Authorization header, the browser sent a preflight OPTIONS first.
  3. Genesys answered without Access-Control-Allow-Origin: https://yoda-qa.chargepoint.teleport.sh.
  4. The browser hid the response from our JavaScript.

Only Genesys can fix that. Its Platform API only returns CORS headers for origins its org allows. The only allow list mentioned in the thread is the Authorized redirect URIs on the OAuth client that issued the token. I couldn't load Genesys' CORS docs page to confirm whether that is the only list.

Why we need it unblocked. The WebRTC SDK runs in the agent's browser and calls api.mypurecloud.de directly. The calls in order:

  1. users/me?expand=station (the request that failed).
  2. Org and station lookups.
  3. The notifications channel.
  4. Our own Get call data fetch to /api/v2/conversations/calls/{id}.

Every one of them is a cross-origin request from our domain. While Genesys refuses our origin, Initialize fails at the first step, so On Ready never fires and no call can be placed. We can't proxy around it, because the SDK owns these requests and the streaming WebSocket.

On the call, check in DevTools: open the Network tab, select the blocked request, and look at its status code. If the code is 401 rather than 200 or 204, the token is still bad and Genesys may simply leave CORS headers off error responses. That would put us back at the 401, not at CORS.

2. What to check with Chargepoint

The Genesys admin items are for Shahid, or whoever administers Genesys at Chargepoint. Vaibhav's draft (thread, 4:32pm) already asks for items 1 to 4. Confirm on the call that each one is done, because the test call fails without them.

  1. Allowed origins (CORS).

    • Check that the OAuth client's Authorized redirect URIs include every origin the softphone runs on:
      • https://yoda-qa.chargepoint.teleport.sh (builder preview, what Manikya tested)
      • https://yoda-qa.internalcp.com
      • https://matrix.unifyapps-qa.internalcp.com (published Outreach app)
    • The existing callback https://webhook.unifyapps-qa.internalcp.com/api/connector-auth-callback/oauth must stay.
    • CORS matches on origin only (scheme plus host), so the /a path in the Slack draft's matrix link doesn't matter.
    • Ask whether their org has a separate CORS allowlist setting besides redirect URIs. If it does, add the same origins there.

  2. Scopes on the same Code Authorization client.

    • Add authorization, organization, notifications, user-basic-info and stations.
    • Confirm conversations is already on the client. Our Get call data event needs it.

  3. A WebRTC phone per calling agent. This means a Base Settings entry with make/model "Genesys Cloud WebRTC Phone", and a phone on an outbound-capable site assigned to the agent. Our integration leaves station selection to the SDK. If the agent's station isn't a WebRTC phone, Start Call has nothing to dial from.

  4. Role permissions for calling agents.

    • Conversation > Communication > View and Disconnect
    • Conversation > Conference > Add
    • Telephony > User's phone associations > View and Edit
    • Telephony > Station > Disassociate Self
    • The licence's default role, such as "Communicate - User"

  5. Reconnect after the changes. Someone has to click Reconnect on the Yoda QA Genesys connection and sign in again, so the token carries the new scopes. Ask who will do it and when.

  6. Token Duration on the OAuth client. Ask what it is set to. The softphone gets its token once at Initialize and must receive a fresh one through Set Access Token before that token expires. The duration decides how often the Outreach page has to refetch the token mid-shift.

  7. How agents sign in. One connection signs in one Genesys user, and every call made through it goes out as that user. Ask:

    • Will each agent authorise their own connection?
    • Is a shared Genesys user acceptable for QA only?

    #58607 left out both the per-agent connection lookup and the permission for agents to create connections.

  8. Region. Confirm the org is on mypurecloud.de (EU Frankfurt). Our interface setting defaults to mypurecloud.com, so the Outreach interface must have Genesys region set to mypurecloud.de.

  9. Where agents run the app. This is the only network-adjacent item, and it's here because it changes how the SDK behaves.

    • A local Chrome or Edge, or a VDI session? VDI needs the WebRTC Media Helper.
    • Does their browser policy allow microphone access on our origins (AudioCaptureAllowedUrls)? If not, the mic prompt never appears and the call has no audio.

  10. Test agent and order. Agree on one named agent who has a WebRTC phone and their own Genesys sign-in. Run the test in this order, so a failure points at one layer:

    1. Initialize fires On Ready. This covers token, CORS and the streaming WebSocket. The patched SDK gives up after 3 streaming attempts and fires On Error.
    2. The agent's station is the WebRTC phone and the browser has mic access.
    3. Start Call connects with two-way audio.
