Gaps to raise on the call

Destinations are not named. The message says "Genesys Cloud and AWS" but lists no domains. For the Frankfurt org (eu-central-1, mypurecloud.de):

  • *.mypurecloud.de and *.euc1.pure.cloud: the regional domains. The softphone calls the Platform API at api.mypurecloud.de and opens a streaming WebSocket in the same region. Our CSP allows wss://*.mypurecloud.de and https://*.mypurecloud.de for this.
  • *.mypurecloud.com: Genesys UI for all regions. Agents and admins need it.
  • dhqbrvplips7x.cloudfront.net (static content) and api-downloads.mypurecloud.de.
  • Only if they use BYOC: *.byoc.euc1.genesys.cloud.
  • Our own hosts, which have to pass the same proxy: yoda-qa.chargepoint.teleport.sh, yoda-qa.internalcp.com, matrix.unifyapps-qa.internalcp.com, and webhook.unifyapps-qa.internalcp.com (OAuth callback).

IP allowlisting. If IT insists on IPs instead of "ports to any", they need all of these:

  • Genesys media ranges 52.129.96.0/20, 169.150.104.0/21, 167.234.48.0/20, 136.245.64.0/18.
  • AWS ranges from ip-ranges.amazonaws.com/ip-ranges.json. Genesys says the AWS GLOBAL region "must ALWAYS be included".
  • Google STUN ranges from gstatic.com/ipranges/goog.json, if they keep UDP 19302.

My suggestion is to open the ports to any destination and use the domain list for proxy and SSL-inspection exceptions.

Netskope / SSL inspection. Our internalcp hosts already need Netskope, so agent machines probably run the Netskope client. Ask:

  • Which steering mode: web only, or all traffic? Does it tunnel UDP?
  • Can the Genesys domains above go on the steering and SSL-decryption bypass list? I haven't seen inspection break this setup, but it's the first thing to rule out if the WebSocket fails. UDP media can't pass through a web proxy at all.

No TCP-only fallback to count on. The Genesys pages don't say that WebRTC media falls back to TURN over TCP 443 when UDP is blocked. The WebRTC phone has a TURN Behavior setting ("Only use TURN when necessary" by default), but the page gives no transport or port. If UDP 3478 and 16384-65535 stay closed, plan on calls failing.

VDI. The thread mentions VDI only as a way for Manikya to reach an internal host. We don't know whether calling agents use one. Ask where agents run the Outreach app: a local browser or a VDI session (Citrix, VMware, Azure Virtual Desktop)? If it's VDI, Genesys' WebRTC phone page covers it through the WebRTC Media Helper, which falls back to streaming through VDI when it disconnects. On AVD or Windows 365 with Microsoft Multimedia Redirection, the same page says "Require WebRTC Media Helper" must be Disabled.

Browser policy. Ask whether their Chrome or Edge enterprise policy sets:

  • WebRtcIPHandling to disable_non_proxied_udp. That forces media over the proxy and kills UDP audio.
  • AudioCaptureAllowed / AudioCaptureAllowedUrls. These can block the microphone prompt on our origin.

On our side, the Outreach interface's Security settings must not set microphone to off (the Permissions-Policy header comes from properties.security.permissionsPolicy).

4. Gaps on our side (internal, not for the client call)

  1. The 401 bad.credentials is unexplained. A missing scope or permission comes back as 403. A 401 means Genesys didn't accept the token at all. Rule these out before blaming the network:

    • The interface's Genesys region must be mypurecloud.de. The code default is mypurecloud.com (DEFAULT_GENESYS_ENVIRONMENT in packages/defs/src/types/interface/index.ts on feat/genesys-integration). A token from .de sent to .com fails. Changing the region tears down the softphone, so the page has to run Initialize again. Set Access Token doesn't change region.
    • Stale token. #58607 notes that the action reads authInput before the request, so if the token expires during that call it can return the old one.
    • The connection's refresh may have failed. Check the connection's last refresh on Yoda QA.

  2. One connection signs in one Genesys user. The Yoda QA connection is signed in as whoever authorized it, so every call placed through it goes out as that Genesys user. Each calling agent needs their own connection, and the Outreach automation has to look up the signed-in agent's own connection. #58607 lists that lookup as out of scope ("No automation step does that lookup today"), and so is giving agents permission to create a connection. The thread doesn't say whether anyone built either since. Worth asking before more agents go live.

  3. Token expiry during a shift. The connector refreshes the connection's token on the backend, but that doesn't reach the running softphone. The softphone gets its token once at Initialize. Before that token expires, the page has to fetch a fresh one through the token action and pass it to Set Access Token (the page event's own description says "call this before the current one does"). The integration has no refresh timer of its own, and the thread names no owner for building this into the Outreach app. Ask Shahid what Token Duration is set to on the OAuth client. I couldn't load the Genesys page with the default.

  4. Raw user token in automation run history. #58607 accepts this, as the SAML2 action already did. Chargepoint's security team may ask about it.

  5. Production. Everything above is QA. Production needs:

    • its own callback and app-origin redirect URIs, probably on a separate OAuth client;
    • the frontend branch reviewed and merged (Manikya: test, fix, dev review, then merge).

    The OAuth path is already on uat and live (#59687, #59688). The live pick left out the SAML2 hunk because live doesn't carry #57161. That only matters if someone promotes the SAML2 action later.
