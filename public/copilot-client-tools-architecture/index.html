How Copilot client tools work

Say you open Copilot inside a spreadsheet and ask, “What’s the total of the cells I selected?” The model can ask for the selection, but only the add-in can read the active spreadsheet. Copilot sends the add-in’s tool declaration with your message. The model chooses the tool by name. The backend resolves that name to a client-executed tool, records what it is waiting for, and sends the call down the chat’s existing response stream. The add-in reads the cells, Copilot posts the result back, and the same agent turn continues with the data.

Three actors make three decisions. The model chooses what to call. The backend’s tool registry and dispatcher determine where it runs. The host owns how it runs, including any host-side permissions. The engine still owns the turn, its timeout, and the next model step.

This walkthrough is based on the Copilot frontend at www@c74eb434a69e and the backend source and workflow assets at uacode@189a8b6d5a40. It follows the streaming Copilot path, with a separate section for the older no-code engine. The spreadsheet example is illustrative. The deployed tenant’s engine selection and an actual spreadsheet round trip were outside this source review.

SSE is the downstream half of the chat send. The browser already has an HTTP response open when the backend publishes the tool request. The return trip uses a new POST because the SSE response carries data in one direction.

1. How the engine learns which tools exist

The embedding host owns the implementation. A host using the reference channel calls setTools with the tool name, description, input schema, optional confirmation settings, and an execute(input) function. For the spreadsheet example, that function can access the document through the add-in. The channel keeps it in a name-to-tool map and strips it from the registration.

The bridge connects a host to one Copilot. ClientToolsProvider mounts under the chat message store for a chat with a copilotBlockId. The bridge announces Ready with that ID. If the host loads first, its unaddressed Register acts as a request for Ready. An addressed Register supplies the actual declarations. A remount emits Ready again so the host can repopulate the registry. In iframe mode, the Copilot bridge accepts messages from its parent window and pins the origin, and the reference host checks the iframe’s window and configured origin. In same-page mode, both ends use window events.

The send path copies the declarations into the request. useClientToolsController registers them locally and calls onClientToolsChange. useChatPage mirrors them into Copilot block state. getCreateCaseParams forwards the three model-facing fields shown below. The chat send path spreads those parameters into the request for a new or existing case. An empty registry omits clientTools. The optional clientName identifies the surface, such as EXCEL, separately from execution routing. The browser keeps execute, requiresApproval, and confirm on its side of the server boundary.

{
  "clientTools": [
    {
      "name": "get_selection",
      "description": "Read the values in the active spreadsheet selection.",
      "input_schema": { "type": "object", "properties": {} }
    }
  ]
}

The backend builds both a model definition and a dispatch entry. In the streaming create-case automation, the agent-core branch copies the incoming list into session variables before entering the Java Invoke Agent node. ClientToolFactory reads clientTools, builds enabled AgentTool entries with the client flag, and carries the input schemas alongside them. ToolCatalogueServiceImpl adds the entries to the turn’s catalogue. The model sees ordinary structured tool definitions in the provider request. The engine keeps the resolved entries and their execution metadata by name. This is how “get_selection exists” gets to the model and “get_selection runs on the client” gets to the dispatcher.

2. Who decides where a tool runs

The model produces a function call with a name and arguments, usually with a provider call ID. It chooses a capability from the advertised tool definitions. The engine parses the arguments and resolves the name against the turn’s catalogue. In Java agent-core, ClassifiedCall.clientTool() checks that the call is valid and resolves to a custom entry marked isClientTool(). AgentToolDispatcherImpl sends that entry to prepareClientTool. A standard server handler or an automation follows its own dispatch path. A client tool is also excluded from code-mode stubs and marked for direct model calls.

This means the same model-facing function-call shape can lead to different executors. Ownership follows the resolved entry. Agent-core ordinarily preserves an existing server tool on a name collision and withholds the conflicting host offer. The backend also supports an explicit host offer for a compatible connector action via implements, which is a separate capability from a plain name collision. The standard Copilot registration shown above sends only the three basic fields. ClassifiedCall · Dispatcher · Catalogue · ClientHostedRows

3. How agent-core delivers the request and parks the turn

  1. ClientToolDispatch.prepare creates a pending record keyed by tool_<toolCallId>. The record identifies the tool, arguments, client execution lane, and wait budget. When a provider omits the ID, agent-core generates a correlation ID for the host and handles provider pairing separately. The wire name is the host’s registered name, even when the catalogue had to sanitize the function name.
  2. The dispatcher publishes one internal THOUGHT message per client call. StreamingResponseSink persists the row and emits a message frame on the live stream. The pending record retains the thought’s messageId so the backend can update the exact row later.
  3. The Invoke Agent node saves the turn’s wait state and registers the awaited signals and their deadlines. The turn can yield while waiting, and the chat's response stream can remain open. A fast host can answer before the park is visible. ClientToolEarlyResults gives that final result a short-lived place to wait, keyed by tenant, case, and call ID. The park drains it after save.

Stripped-down message after Copilot applies the stream frame:

{
  "messageId": "msg_42",
  "additional": {
    "internalMessageType": "THOUGHT",
    "thoughtType": "CLIENT_TOOL_REQUESTED",
    "clientToolCalls": [
      { "toolCallId": "tc_7", "name": "get_selection", "input": {} }
    ]
  }
}

caseId identifies the chat, toolCallId identifies an invocation, messageId identifies the thought row, and copilotId identifies the browser bridge instance. The tool name picks the host function. It cannot distinguish two invocations of that same function. ClientToolDispatch · StreamingResponseSink · Invoke Agent runtime · Early results

4. How Copilot runs the call on the client

useSubmitUserMessageSSE routes frames through handleSSEChunk. That handler applies message deltas to the chat store, which the client-tools hook subscribes to. The controller scans both arriving messages and the store as it exists at mount. It recognizes a pending call by the combination of CLIENT_TOOL_REQUESTED and clientToolCalls. Rendering the “Executing” row and dispatching the call both read this state. Dispatch also works when the thought is already in fetched history.

The controller matches the call name against the local registration and claims its ID once within that controller. Calls observed before their tool registers wait for the next registration and rescan. requiresApproval: false skips the generic gate. Other calls go through requestClientToolApproval, which currently auto-approves with a warning in this source. That hook is a stub. Desktop approval and OS permissions are handled by the desktop host and its permission UI. If a gate returns denial, the controller can construct an error result without invoking the host.

The bridge emits Invoke with the name, input, and call ID. The reference host looks up the function, runs it, and emits Result with the same ID. A plain string becomes a text content item. A thrown error becomes isError: true. Matrix Desktop uses the same chat protocol. Its host adapter takes Invoke through callDesktopTool and the window.unifyDesktop.agent API into Electron’s local process. Results can include typed text or image content. 5. How the result wakes the same turn

Copilot accepts results for calls its controller claimed. It submits once per pending thought after all of that thought’s calls have answers. In the observed Java and legacy producer paths, parallel client calls normally arrive in separate thoughts, so each thought can submit as soon as its own call finishes.

{
  "caseId": "case_123",
  "toolResults": [
    {
      "toolCallId": "tc_7",
      "isError": false,
      "content": [{ "type": "text", "text": "Selected values: 10, 20, 30" }]
    }
  ]
}
  1. useSubmitClientToolResults resolves the platform automation of type Submit_Client_Tools on demand. It invokes the automation synchronously through the normal workflow endpoint. The automation’s own tenant gate directs the payload to SubmitClientToolsAction for agent-core.
  2. The Java action checks for a case ID and usable call results and announces them through Redis pub/sub. This crosses the pod boundary. The HTTP submit may land on a different pod from the one holding the turn. HTTP success confirms the submission path ran and cannot establish that the waiting turn took the result.
  3. ParkedTurnWakerImpl checks the indexed durable park and local in-memory candidates. It matches the case, pending tool_<id>, and the client lane. It emits the completion signal to the matching execution. Other waits can share the signal naming scheme, so checking the client lane matters. A cancelled turn drops the result. A supported step: running or approved report can update a wait without completing it.
  4. The delivery path flips the existing thought to CLIENT_TOOL_SUBMITTED after signaling. Resume ingestion also patches it and handles the deadline case. The dispatcher records the tool output against the original model call and the turn consumes it in its next model step. For this example the model now has the selected values and can answer “60”. A host error or deadline also settles the call with an error result, so a submitted thought is a lifecycle marker and can represent a failed tool.

The older no-code engine

The streaming entry automation chooses the engine using a tenant rollout gate. The legacy branch calls the generic create-case workflow, which populates session variables including clientTools. Both engines expose the same browser-facing request and result contracts. The internal mechanics differ.

It signals that wait with a received payload. The child updates the thought and returns its output through the tool wrapper.

The collision rule changes with the engine: the legacy wrapper routes by a matching client name, while agent-core ordinarily preserves the previously offered server entry. What happens outside the happy path

Situation What the code does
Reload during a wait The fetched conversation can carry the persisted request thought. The controller scans at mount and after registration, so a pending call can run again after reload. Host writes should use toolCallId for idempotency.
Parallel calls or duplicate events The controller tracks claimed calls, first results, and submitted thoughts. Desktop also shares per-window call promises and submitted-call state across the foreground and background controllers. These measures apply within their lifetime. A page reload can reset local state.
Switch desktop chats The background runner takes over a generating chat and polls its conversation for pending requests. It runs and submits under that chat’s own case ID, then releases desktop turn state when the turn finishes.
The host stays silent or the submit fails The thought can stay pending until the deadline. Agent-core defaults to a configurable 240-second client wait, with additional handling for hosts that declare their own wait and report approval progress. The current generic controller surfaces submit errors, and its in-memory submission bookkeeping does not implement a general retry loop.
Stop or late response The frontend stops dispatching deleted requests and tracks stopped desktop runs. The backend checks cancellation on delivery and only accepts results for a matching pending call. A local operation that has already taken effect can outlive the chat’s wait.

Tools discovered during the turn

The pinned backend also supports a host search tool returning extra declarations in a final result’s tools field. Agent-core merges new names, invalidates its turn catalogue, and persists the definitions on the case. The very next model request can include the newly discovered tool, and future turns can restore it. The legacy engine merges them into the session variable for the current turn. The standard reference host and Copilot result type shown here carry toolCallId, content, and isError. Treat the extra field as a backend contract for hosts that implement dynamic loading and can execute the loaded names. Backend tool-loading design

How to trace one call yourself

Checkpoint Evidence to look for
Does the model know about it? The outgoing streaming request has parameters.clientTools. In the backend trace, the model request includes the function definition.
Did the engine route it to the host? Find the model’s tool call and the corresponding client dispatch. Look for CLIENT_TOOL_REQUESTED on the SSE response or in the fetched conversation, with the original host name and call ID.
Did the host execute it? Follow that ID through local Invoke and Result. If there is no Invoke, check that the addressed registration included the same name. On desktop, follow the local agent call.
Did the result reach the wait? Look for Submit_Client_Tools with that caseId and toolCallId, then the same thought row’s CLIENT_TOOL_SUBMITTED patch. Check the result or timeout in the backend trace before treating the patch as evidence of success.
Did the model use the result? In the next model step, find the tool result paired with the original call. The final reply streams through the same chat flow.
