Why the OpenAI workflow-agent rewrite was necessary

TL;DR

The previous workflow-agent stack was built and tuned around Claude Sonnet. Much of its platform knowledge was sound, but the delivery mechanism was costly, repetitive, and too dependent on the model recovering intent from weak tool schemas. Moving to an OpenAI model required more than changing the model selector.

The rewrite keeps the useful workflow contracts, cuts the combined prompt, skill, and tool-text inventory from 102,848 to 19,287 tokens, and replaces implicit tool behavior with explicit JSON boundaries and proof-based completion. QA confirmed the new save, patch, and mocked-run adapters. A full behavioral comparison still needs to run after the QA daily cost limit is raised or reset.

The main reason for the rewrite is not that Claude instructions are unusable by GPT. It is that the old stack asked the model to compensate for duplicated guidance and underspecified tools. The QA failures proved that compensation was part of the old operating model.

Scope and evidence

This audit compares the previous four workflow roles and their 20-skill, 52-tool inventory with the isolated OpenAI rewrite at commit 93742aec9dc512e524ba15a4e9aedc78d10d17bf on branch feat/openai-workflow-rewrite.

The current asset set contains:

  • four new agents;
  • 15 new skills;
  • 48 newly named tool wrappers;
  • three cloned specialist-dispatch workflows;
  • three JSON adapter workflows for save, patch, and mocked execution.

The old assets were not edited. The new agents and every dependent asset have separate IDs on QA.

Evidence used in this report:

  • checked-in legacy and rewritten prompt files;
  • the pre-rewrite QA and UAT asset snapshots;
  • exact o200k_base token counts over the stored Markdown and tool label text;
  • the rewrite manifest and provisioning tests;
  • persisted QA workflow and run results;
  • the changelog written while the QA failures were being fixed.

What "Claude-dogfooded" means here

The phrase needs precision. There are three different kinds of evidence.

Confirmed Claude coupling

The legacy planner, builder, editor, and tester prompt sources declare model: sonnet. Their language, decomposition, and tool-use conventions were therefore being exercised against Claude during development.

The legacy builder also describes an interface-building pipeline that "spawns one builder per automation in parallel". Builder and editor contain a dedicated use_parallel_tool_calls section. These are not universal workflow requirements. They encode the behavior expected from the Claude-based host and its surrounding agent pipeline.

Strong signs of Claude-specific tuning

The old prompts read like accumulated operational handbooks. The builder was 14,151 tokens and the editor 11,455. They repeated the same node, edge, pill, filter, trigger, and control-flow material. Across those two files, 244 distinct nonblank lines were exact matches.

The legacy agents and local workflow skills contained 53 uppercase MUST, MANDATORY, or HARD RULE markers. The rewritten set contains none of those uppercase markers. The requirements still exist, but they now live in named contracts and validation gates.

This looks like dogfooding by correction. A model fails on a detail, so another warning and another example are added to the system prompt. That can improve the model being tested while making the prompt harder to port, review, and maintain.

The skill router showed the same pattern. Twenty skill names and descriptions occupied 2,739 tokens before any skill body was loaded. Several descriptions were paragraph-length trigger grammars beginning with MANDATORY whenever. The new 15-skill catalog occupies 704 tokens, a 74.3% reduction.

Portable material that should not be dismissed as Claude-only

XML sections, examples, explicit negative constraints, and skill-based disclosure are not inherently Claude-specific. GPT can use them too. The rewrite retains XML-style sections because they give the prompt a readable hierarchy.

The old platform facts were also valuable. Node contexts, callable response rules, Storage versus Analytics boundaries, code output envelopes, filter shapes, mock rules, and polling behavior were not thrown away. They were consolidated and tied to a source-precedence policy.

Calling every legacy detail "Claude-specific" would be a weak audit. The problem was the combination of model pinning, repetition, implicit tool recovery, and missing completion contracts.

Why a rewrite was necessary

Changing the model did not change the contract

The original mutation wrappers exposed closed object inputs whose schemas declared no usable properties. The model needed to supply a complete workflow or patch, but the function schema effectively allowed only {}.

Claude may have appeared to work around this through prompt context or host behavior. GPT 5.4 did not. The first QA run reached the tool and then failed at the boundary. This was the clearest reason not to treat the migration as a model dropdown change.

The rewrite adds three explicit string contracts:

  • workflowDefinitionJson for a complete workflow definition;
  • patchJson for one bounded edit;
  • inputsJson for mocked trigger input.

Each string is parsed inside a cloned helper workflow. The platform still receives typed objects after parsing, while the model sees a schema it can satisfy reliably.

Too much always-on knowledge competed for attention

The old builder and editor each carried a large copy of the workflow format. That raised input cost and made the same rule available in several slightly different places. A correction could land in one prompt and not the other.

The rewrite gives every role a small permanent contract. Shared graph rules live in workflow-core-openai. Conditional behavior lives in loadable skills. The live operation file remains authoritative for node inputs and outputs.

This is a maintainability change as much as a token change. One control-flow fix now belongs in one skill.

Tool names and descriptions assumed too much context

Legacy names included Shell, Ask from knowledge, Fetch automations by query or id, and Invoke Workflow builder agent. Several descriptions said little more than "Calls another automation" or "Execute tool".

Those wrappers relied on the model understanding ownership and intent from the surrounding prompt. The new names expose the action directly: Read Workflow Operations, Read API Guidance, Find Workflows, Build Workflow, Save Workflow Definition, and Apply Workflow Patch.

Descriptions now state argument names, array versus scalar requirements, return evidence, side-effect boundaries, and readback expectations. High-risk mutation descriptions intentionally became longer.

Delegation needed a complete handoff

The planner and specialists are separate agents. The specialist does not see the planner's conversation, searches, or unresolved thoughts unless the handoff includes them.

The new planner owns one handoff schema containing the operation, workflow identity, trigger, resolved assets, decisions, constraints, flow, preservation boundary, and test approval. Dispatch tool descriptions repeat that requirement at the point of use.

This removes a fragile assumption that an agent invocation carries shared conversational context.

Completion needed evidence rather than momentum

The old prompts contained output guidance, but execution and proof were spread across long procedural sections. The rewritten roles define completion in their output contracts:

  • a builder completes only after save and matching readback;
  • an editor completes only after the bounded patch and preservation checks;
  • a tester polls one run to terminal evidence and never turns a queued status into a verdict;
  • a planner reports completion only after the specialist returns evidence.

This matters for any model family. It matters more during a migration because apparent progress can hide a different tool-call or stopping style.

Agent-by-agent audit

Planner

The planner fell from 8,608 to 1,426 tokens, an 83.4% reduction.

The old planner contained separate CREATE, EDIT, DEBUG, and asset procedures with repeated resolution and reporting instructions. The new planner routes by desired outcome, resolves tenant facts, creates one complete handoff, dispatches one specialist, and checks the returned proof.

Important changes:

  • user intent outranks role and skill guidance;
  • read-only questions do not dispatch writers;
  • diagnosis does not silently become a fix;
  • asset IDs are resolved before dispatch when the specialist cannot discover them;
  • unresolved values become named placeholders rather than plausible guesses;
  • a clarification is asked only when the missing choice changes behavior, security, data loss, or a public contract;
  • testing defaults to no real side effects;
  • the final response distinguishes saved, deployed, queued, terminal, and blocked states.

Builder

The builder fell from 14,151 to 1,138 tokens, a 92.0% reduction.

The old prompt was a large workflow-format manual plus examples. The new builder follows a seven-step loop: parse the brief, select operations, read schemas, build inside-out, validate, save once, and read back.

Important changes:

  • the START trigger.type is required independently of resourceName;
  • operation files control inputs and outputs;
  • one workflow definition is serialized once at the tool boundary;
  • caseId and taskId are recognized as runtime metadata rather than missing user facts;
  • one repair retry is allowed only when the platform returns a specific correctable defect;
  • a local JSON object is not reported as completion without a persisted ID and matching readback.

Editor

The editor fell from 11,455 to 850 tokens, a 92.6% reduction.

The old editor repeated much of the builder's format reference. The new editor is about mutation semantics.

Important changes:

  • fetch before edit and after edit;
  • trace incoming and outgoing edges, pills, conditions, loop ownership, branch membership, and response paths;
  • merge changes into live nodes rather than regenerate them;
  • preserve unknown fields;
  • rewire references in the same atomic patch as a removal or replacement;
  • use the granular fallback tool only when the main patch contract cannot express the edit;
  • do not deploy or run unless the request says so.

Tester

The tester fell from 3,398 to 1,143 tokens, a 66.4% reduction.

The tester remains relatively detailed because mock and assertion errors can produce believable but false results.

Important changes:

  • authoring requires a live workflow with a START node, nodes, and edges;
  • external and nondeterministic work is mocked by default;
  • mocks follow resolved output schemas, not pills that may themselves be wrong;
  • assertion pills, operators, expected values, and code-result envelopes are explicit;
  • a production workflow run requires sideEffectsApproved: true;
  • one run ID is preserved and polled rather than retriggered;
  • a red run means testing completed with a failing verdict, not that the workflow succeeded;
  • validation-origin edits may repair mechanics but may not weaken business expectations.

Tool audit

The rewrite keeps 48 source capabilities and removes four overlapping legacy wrappers. Forty-six retained wrappers have new names, and all 48 descriptions changed.

Retained wrapper text fell from 3,107 to 2,263 tokens, a 27.2% reduction. Including the four removed wrappers, the tool-text inventory fell 33.3%.

The reductions came from verbose discovery tools, generic shell instructions, and duplicated test/API tools. Mutation tools became more explicit:

Tool Previous tokens Rewritten tokens Reason
Save workflow 35 100 Defines the exact JSON string, create versus fill behavior, forbidden envelope shapes, and returned evidence.
Apply workflow patch 12 67 Defines the bounded patch vocabulary and prevents fields from being sent at the wrong level.
Build workflow dispatch 8 46 Requires one self-contained brief because the specialist cannot see planner context.
Validate workflow code 20 45 States supported languages and separates code validation from pill and graph validation.

The tester's six direct tool descriptions grew from 212 to 325 tokens. That is a good increase. The extra text specifies run lanes, IDs, terminal evidence, asset writes, and the difference between starting and judging a run.

Four old wrappers were left out of the new asset graph:

  • List API Assets, on the assumption that the consolidated API asset read path covers the planner's inventory needs;
  • Execute Test, superseded by the dedicated tester run contract;
  • the older Get Automation Metadata and Inspect Runs, superseded by the tester-owned versions and the reliability skill's focused primitives.

Critical findings that remain

The rewrite is materially better, but the audit found issues that should be corrected before calling it the final OpenAI asset set.

Prompt and tool names do not fully match

The planner, builder, and editor prompts refer to Search Workflows, Search Connections, Search Storage Objects, Search Platform Entities, and Search Workflow Assets. The manifest registers those tools as Find Workflows, Find Connections, Find Storage Objects, Find Platform Entities, and Find Workflow Assets.

GPT can often infer the intended tool from the available list, but an OpenAI-focused rewrite should not depend on that inference. The prompts and wrapper names should use one vocabulary. This is a source defect, not an evaluation question.

Run tooling overlaps across roles and skills

The tester directly owns Inspect Workflow Runs and Start Workflow Run. Loading workflow-reliability-openai can also expose Inspect Workflow Run and Start Mocked Workflow Run.

The distinction is defensible. One pair handles general tester lanes, while the other is a focused mocked-run primitive. The names are still close enough to create selection ambiguity. The planner, builder, and editor can also load the reliability skill and gain run tools even though their role prompts discourage direct execution.

The next revision should either narrow which agents can access the reliability tools or make the two run families visibly distinct in name, scope, and input schema.

Removing broad API listing may have reduced capability

The old List API Assets wrapper supported type-wide enumeration, filtering, sorting, and limits. The retained Read API Asset wrapper resolves one asset through supported name or parent parameters.

That is not proven to be equivalent. If API publication needs collision detection across several existing assets, the old list capability may still be necessary. A focused List API Assets wrapper should be restored if paired evaluation finds that singular lookup cannot perform the preflight reliably.

JSON strings solve compatibility by moving validation later

The three adapters are the right short-term repair for closed, fieldless object schemas. They also remove schema-native validation from the model-facing boundary. A malformed string reaches the parser before the platform can validate individual fields.

The long-term fix is a complete JSON Schema for each structured argument. Until the platform can expose that schema correctly, the adapters need size limits, clear parse errors, and tests for malformed JSON, unexpected top-level types, and unsupported patch fields.

Most source tool schemas remain inherited

The rewrite changed every tool name and description, but most wrappers still clone their source automation and input schema. Better prose cannot repair a wrong or ambiguous schema. The remaining 45 non-adapter wrappers should be checked for empty objects, mismatched required fields, misleading defaults, and descriptions that disagree with the actual trigger contract.

The schema reader is still a general shell wrapper

Read Workflow Operations is clearer than Shell, but the underlying capability remains a shell-oriented reader governed partly by prose constraints. A structured operation-schema tool would give the model explicit appName and resourceName fields, return normalized operation metadata, and enforce repository boundaries outside the prompt.

This is not required to validate the current rewrite, but it is the cleaner OpenAI contract.

What QA fixed

The QA work changed the design in concrete ways.

  1. The save adapter first exposed the source wrapper's fieldless object problem. workflowDefinitionJson fixed the boundary.
  2. The saved smoke workflow then failed because START had no explicit trigger marker. workflow-core-openai now requires it.
  3. The first patch adapter rewrote root references but left nested patch fields attached to removed START inputs. Recursive rewriting fixed it.
  4. The mocked-run adapter initially treated inputs as a prefix of inputsJson and created a self-reference. Boundary-aware matching fixed it.
  5. Template Resolver guidance invented nested fields the static schema did not declare. That recipe was removed, and the skill now requires a verified dynamic contract.
  6. The cloned patch helper carried an obsolete inactive-connection error branch. The isolated helper removes it.
  7. Provisioning now records versions, checks ownership and name collisions, saves state after each creation, links agents before publishing skills, and verifies deployed content against source.

The final QA adapter sequence proved:

  • save produced workflow 6a99f4e23109286238dd47a2 with a callable START;
  • patch changed only the intended metadata and preserved two nodes plus one edge;
  • mocked execution returned {"message":"Hatim"} in 81 ms.

All three model stages are pinned to Azure OpenAI GPT 5.4, model ID e_6a4bec127709eb05ba7007ee.

What the rewrite does not prove yet

The token counts are exact. They do not prove better task accuracy.

The save, patch, and mocked-run boundaries are proven on QA. Local verification has 9 passing tests and 268 assertions. The provisioner bundles, the worktree is clean, and persisted assets match the manifest.

The full planner-to-builder conversation did not finish. QA stopped execution when the estimated daily cost reached 1.009241 against a 1.0 hard limit. The run reached the new save and workflow-read tools before the limit stopped it.

There are still risks:

  • shorter skills depend more strongly on operation files and tenant reads being available;
  • moving detail out of role prompts makes correct skill selection more important;
  • broader sharing of the consolidated skills may add selection choices to roles that previously had narrower sets;
  • one smoke workflow does not cover branching, Storage, Analytics, files, SQL, API publication, and destructive-operation refusal;
  • the old prompts may contain rare operational examples that have not yet been represented in an eval case.

The rewrite is ready for comparative evaluation, not for declaring the old stack obsolete on token count alone.

Recommended evaluation plan

1. Restore a usable QA evaluation budget

Raise or reset the daily hard limit for the isolated OpenAI agents. Do not alter the existing Claude agents or their assets.

2. Run paired task suites

Run the same prompts against the legacy and OpenAI asset graphs. Record model input tokens, output tokens, tool calls, latency, retries, persisted artifact validity, and human corrections.

Minimum cases:

  • simple callable creation;
  • schedule plus connector read;
  • nested IF_ELSE or BRANCH inside a LOOP;
  • bounded edit that removes a referenced node;
  • Storage record flow with a dynamic object schema;
  • Analytics aggregation and output pill;
  • external SQL discovery and parameterized query;
  • file download, conversion, and attachment mapping;
  • callable contract edit with all response leaves;
  • API publication with auth and policy;
  • Storage object schema change with collision checks;
  • mocked test authoring, queued polling, and failing assertion;
  • refusal of an unapproved production side effect or destructive operation.

3. Judge contracts, not prose style

Score each case on:

  • correct role routing;
  • schema-valid tool call on the first attempt;
  • no invented IDs, fields, operations, or pill paths;
  • smallest valid mutation;
  • preserved behavior outside the request;
  • correct terminal and deployment status;
  • exact artifact and run IDs;
  • no unapproved side effect;
  • final answer matching persisted evidence.

4. Promote findings back to the owning layer

Fix a repeated issue in the narrowest durable place:

  • tool schema or description when the call envelope is wrong;
  • domain skill when one family of nodes is wrong;
  • shared core when graph invariants are wrong;
  • role prompt when ownership, sequencing, or stopping is wrong;
  • platform operation metadata when the source contract itself is wrong.

Do not grow every agent prompt in response to one failure.

5. Decide rollout with measured thresholds

The OpenAI stack should replace the legacy default only when it matches or improves first-pass validity, task completion, safety, and persisted readback across the paired suite. Token and latency savings are supporting metrics, not the acceptance gate.
