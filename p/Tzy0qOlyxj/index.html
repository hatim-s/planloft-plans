What changes when an agent changes models

I checked 17 coding agents, app builders, and workflow tools to see whether they swap only the model or also change its instructions, tools, and context.

The answer

Coding agents often change the prompt, edit format, tool definitions, and message handling for each model. App and workflow builders usually change the model assigned to a job, the tools it may use, or the role it plays. Most products keep skills reusable across models.

Main finding

The product changes the request. It does not retrain the model.

The model weights do not change. The product changes the request sent to the model. That can include the system prompt, tool schema, message order, available context, or reasoning setting.

OpenCode, Cursor, Factory, Cline, and Aider publish code or technical notes that describe these changes. Amp bundles the model, prompt, tools, and reasoning setting into a mode. Lovable says it rewrites instructions, tools, and context for each model it uses to build apps.

n8n, Make, and Zapier usually adapt at a different level. They qualify models for certain jobs, restrict tools by capability, use fallback models, or give each agent role its own instructions. Public sources reveal less about prompt changes inside these workflow products.

Do not lump these together

Five ways a product can adapt to a model

Each method solves a different problem. Reformatting an API request proves provider compatibility. It does not prove that the product changes the agent's behavior.

01

Provider format

Converts system messages, tool calls, reasoning state, cache fields, images, and schemas into the format each API accepts.

02

Capability checks

Checks whether a model supports native tools, images, parallel calls, patch edits, or structured output before enabling them.

03

Model instructions

Changes prompt wording, tool names, examples, edit syntax, context order, or verification rules for a model family.

04

Agent role

Gives a planner, implementer, reviewer, or researcher its own instructions, permissions, tools, and context.

05

Model routing

Picks a model based on task difficulty, cost, speed, context size, input type, or the reason a previous attempt failed.

If you are building this

Keep one agent. Change only what the model needs.

Start with common instructions and tools. Add a model-specific change only after a test shows that the common version fails.

Keep skills model-neutral

A skill should describe the job, the capabilities it needs, and the tools it may use. If the job needs a specialist model, state that requirement or delegate the job. Do not maintain copies of the same skill for Claude, GPT, and Gemini without a measured reason.

Fix the actual failure

If a model misuses an edit tool, change the tool instructions or edit syntax. If it forgets earlier work, fix the message history. If it keeps stopping, change the action rules. Do not make every model carry prompt text written for one model's mistake.

Score the finished result

A coding agent should leave a correct patch that passes its tests. An app builder should leave a working app. A workflow builder should leave a valid workflow that runs. A polished response does not make up for a broken result.

Write down why each exception exists

For every model-specific rule, keep the failing test, the rule that fixed it, and the condition for removing it. Without that record, old workarounds pile up and nobody knows which ones still matter.

request = common agent rules + provider API format + model capability checks + tested model-specific changes + instructions for this agent role + project context + relevant skills + model chosen for this job

How I judged the evidence

Source code first. Unknown stays unknown.

Rules I used

  • Use source code and the company's own technical writing where possible.
  • Do not call model routing a model-specific prompt.
  • Do not call role-specific tools model-specific tools.
  • Mark private implementation details as unknown.

What "not public" means

It does not mean the product lacks the feature. It means I could not support the claim with public material. A closed product may run detailed internal tests without publishing its prompts or tool definitions. Open-source products are simply easier to check.
