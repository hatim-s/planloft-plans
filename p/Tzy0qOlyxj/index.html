How agents tune the system around the model

A source-backed comparison of coding agents, UI builders, and workflow products. The question is simple: when the model changes, what else changes with it?

The short answer

Coding agents often change prompts, editing protocols, tool definitions, and context handling per model. UI and workflow builders usually rely more on model routing, capability gates, and role-specific agents. Skills tend to stay portable.

Central finding

This is tuning, but it is not fine-tuning.

The model weights stay untouched. The product changes the inference-time contract: instructions, tools, schemas, message shape, context order, and reasoning settings.

OpenCode, Cursor, Factory, Cline, and Aider expose direct evidence of model-aware behavior. Amp packages the same ingredients into modes. Lovable now describes equally deliberate model-specific adaptation for app building.

Workflow products sit on a different part of the spectrum. n8n, Make, and Zapier lean more on provider compatibility, role prompts, standardized action schemas, user-selected tools, fallback models, and model tiers. The public evidence for a distinct prompt-and-tool contract per model is thinner.

A useful taxonomy

Five layers that people call “model-aware”

These mechanisms solve different problems. Treating them as one thing makes product claims sound stronger than the evidence supports.

01

Protocol adapter

Serializes system messages, tool calls, reasoning state, cache metadata, images, and provider-specific schema rules.

02

Capability adapter

Chooses native or prompted tools, vision support, parallel calls, patch editing, and structured output.

03

Model profile

Changes prompt wording, tool names, examples, editing grammar, context order, and verification rules by model family.

04

Role profile

Gives planners, implementers, reviewers, and researchers different instructions, permissions, tools, and context.

05

Router

Assigns work to a model based on difficulty, cost, latency, context size, modality, or failure recovery.

What each product actually shows

“Confirmed” means a direct public statement or visible implementation. “Strong” means the mechanism is clear but its per-model depth is partly inferred or user-configured. “Limited” means product behavior is public while the internal contract is not.

Design recommendation

Build deltas, not parallel products

The strongest pattern is a shared agent core with small, measured overrides at the layer where a model actually differs.

Keep skills portable

A skill should describe a task procedure, required capabilities, and allowed tools. If it needs a specialist model, let it declare a capability or delegate to a role. Do not fork the skill body for Claude, GPT, and Gemini by default.

Tune the concrete failure

If a model misuses an edit tool, change the tool contract or editing grammar. If it loses state, fix message and reasoning continuity. If it stalls, adjust action policy. Avoid adding generic prompt text that every model must carry.

Route by completed work

Judge the result at the product level. For a coding agent, that means tests and a correct patch. For a UI builder, it means a working app. For a workflow builder, it means a valid, runnable workflow.

Record the evidence

Every override needs a failing evaluation, the change that fixes it, and a retirement condition. Otherwise, the profile becomes a pile of folklore that no one can safely remove.

final request = shared agent core + provider protocol adapter + capability profile + small model-family delta + role or mode profile + workspace context + relevant portable skills + task-level model routing

Method and limits

What this report can prove

Evidence rules

  • Prefer source code and first-party engineering posts.
  • Separate model routing from model-specific behavior.
  • Separate role-specific tools from per-model tools.
  • Treat undisclosed implementation details as unknown.

Reading the gaps

A “not shown” label does not mean the product lacks the mechanism. It means the public material does not support the claim. Closed products can run sophisticated private evaluations without publishing their prompt or tool matrices. Open-source projects make the same claim easier to verify.
