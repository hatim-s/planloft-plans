Provet — Product Plan (v1)

CLI: vet · Local-first agentic evals · Status: spec settled, pre-build

What is it

Provet is a local-first CLI tool for evaluating AI agents. You define eval cases and graders in files (or via the CLI), point Provet at the agent under test — Claude Code, Codex CLI, or any HTTP endpoint — and it runs the suite on your machine, grades the results, and tells you whether your latest change made the agent better or worse.

It is a ground-up rebuild of an earlier project (attest, an all-in-one eval platform spanning configuration, local runs, cloud, and CI). Provet deliberately narrows scope: v1 is local machine + CLI only. No web UI, no cloud execution, no CI integration. The thesis is that the core loop — define → run → grade → compare — has to be excellent before anything else matters.

The core loop

vet init      # scaffold config + a working example eval
vet run       # run the suite, live progress in the terminal
vet report    # inspect the last run (or any run by id)
vet diff      # compare two runs — did my change help?

Everything in v1 exists to feed this loop. vet diff is the daily-driver command: change a prompt or agent config, re-run, and see per-case regressions and improvements with cost deltas.

North-star metric: zero to first green run in under 5 minutes.

Philosophy

  1. Local-first. Your evals, transcripts, and results live in your repo and filesystem. Plain files in v1 — greppable, diffable, no database, no server.
  2. Agentic evals are not unit tests. Agents are nondeterministic and take trajectories, not single outputs. First-class support for repeated trials (--repeat N with pass@k-style aggregation), trajectory assertions ("called tool X", "never touched these files", "≤ N steps"), and per-case cost and latency tracking.
  3. Agents are users too. The vet CLI is designed so coding agents can author and run evals without a human: structured JSON output on every command (including errors), no interactive prompts, schema dumps, and a validation loop. A repo's agent should be able to add an eval case as easily as its developer.
  4. One adapter layer, two consumers. Invoking the agent under test and invoking an LLM judge are the same problem. Both go through the same adapter system (claude-code / codex / http / command), so a judge can itself be a CLI agent.
  5. Boring formats, sharp tools. YAML for structure, Markdown for prose-heavy cases, TypeScript for escape hatches. A single eval can mix all three.
  6. Cut ruthlessly, design for the sequel. v1 stores runs as JSON designed so the v1.1 SQLite migration is a single import. The HTML report's view-model is the same object the v1.1 dashboard will consume.

Feature set (v1)

Targets — the agent under test

Three first-class adapters plus a generic escape hatch:

Adapter Invocation Trajectory
claude-code Spawns claude -p … --output-format stream-json Full (native stream parsed)
codex Spawns codex exec --json … Full (native stream parsed)
http POSTs case to a URL Optional (response contract)
command Any shell command, {{input}} templating raw or vet-events JSONL

The claude-code and codex presets know their spawn arguments, event formats, and cost extraction. Both normalize to the same internal trajectory model, so trajectory assertions work identically across them.

Eval authoring — three ways, freely mixed

An eval is a directory with a manifest; case files can be any mix of YAML and Markdown:

evals/
  refunds/
    eval.yaml            # manifest: defaults, target overrides
    cases.yaml           # N structured cases
    tricky-customer.md   # 1 prose-heavy case (frontmatter = asserts, body = input)
graders/
  check-ledger.ts        # custom code grader
  • YAML cases for structured, matrix-style inputs.
  • Markdown cases for long, prose-heavy task prompts — frontmatter carries the asserts, the body is the input.
  • Single-file shorthand (evals/smoke.eval.yaml) for simple suites.
  • CLI authoring for everything: vet new eval, vet add case, vet add grader. No editor required.

Graders

Configured per case in v1 (eval-level shared graders arrive in v1.1). Three tiers:

  1. Deterministic — equals, contains, regex, json-schema, custom TypeScript (type: code).
  2. Trajectory — called_tool, never_called, max_steps, min_steps, files_untouched (computed by workspace diff). This tier is the agentic differentiator.
  3. LLM-as-judge — first-class, and the judge is itself an invokable agent.

An expect: sugar block on cases maps to deterministic and trajectory graders for the common path.

LLM-as-judge — judges are agents

Named judges are defined in provet.yaml using the same adapter schema as targets — a judge can be Claude Code, Codex, or an HTTP service:

judges:
  strict:
    type: claude-code
    model: claude-opus-5
  cheap:
    type: http
    url: http://localhost:8080/judge

Graders reference judges by name (use: strict). The judge receives the case input, the full trajectory (not just the final answer), and the rubric, and must reply with a structured verdict — {pass, score, reasoning}. Parse failure triggers one retry with error feedback, then the case is marked grader-error (distinct from fail). Judge cost and latency are tracked separately from agent cost in every run.

Workspace fixtures

A case can declare workspace: ./fixtures/shop — a directory copied to a temp cwd for the agent to work in. Essential for coding-agent evals, and it powers files_untouched via post-run diff. The post-run workspace copy is also handed to code graders.

Runs

  • vet run [--filter x] [--repeat N] [--concurrency C]
  • Repeated trials aggregate via pass_if: all | any | ratio:0.66 (project, eval, or case level).
  • Per-case cost, latency, and token counts always recorded.
  • Storage: .provet/runs/<id>/ — run.json summary + per-case JSONL event logs + latest symlink. Run snapshots include git commit and dirty flag.

Reporting

  • CLI: summary tables, per-case drill-down (transcript, tool calls, grader reasoning), --json on every command.
  • HTML: vet report --html renders a self-contained static file through a templating system (built-in default theme; project templates/ dir overrides partials). A document, not an app — no server.
  • vet diff <a> <b>: per-case regressions/improvements plus cost delta.
  • Templates receive the same JSON view-model as --json output — humans, agents, and templates all see one data shape.

Agent-ready CLI (design rules, not a feature)

  • No interactive prompts, ever, in v1. Destructive ops require --force.
  • --json on every command, including errors (structured error codes, not prose).
  • vet run --reporter jsonl streams per-case events for an agent to watch.
  • vet schema [config|eval-case|grader|run] dumps JSON Schemas; vet validate lints config and all eval files. Together they form the agent authoring loop: generate → validate → fix from structured errors.
  • Meaningful, documented exit codes (0 pass, 1 failures, 2 config error, …).
  • vet init can write an AGENTS.md/skill snippet so agents on the repo self-serve.

A side effect: these constraints (no prompts, structured IO, exit codes) make v1 CI-ready for free when CI integration lands in a later version.

Full CLI surface (v1)

vet init                                  # scaffold project + example
vet new eval <name> [--format dir|file]   # scaffold eval
vet add case <eval> --input "…" …         # or --from-json / stdin; --format md|yaml
vet add grader <eval> --type judge --use strict --rubric "…"
vet validate                              # lint config + all eval files
vet schema [config|eval-case|grader|run]  # dump JSON schemas
vet run [--filter] [--repeat] [--concurrency] [--reporter jsonl] [--json]
vet report [run] [--case id] [--html] [--open] [--json]
vet diff <a> <b> [--json]

Key schemas (abridged)

provet.yaml

version: 1
target:
  type: claude-code          # claude-code | codex | http | command
  model: claude-sonnet-5
  args: ["--allowedTools", "Bash,Edit"]
  timeout: 300
judges:
  default: {type: claude-code, model: claude-opus-5}
defaults:
  concurrency: 4
  repeat: 1
  pass_if: all
report:
  templates: ./templates

${VAR} interpolates environment variables in config; API keys never live in files.

Case (YAML)

- id: full-refund-window
  input: "Customer bought item 10 days ago, wants refund…"
  workspace: ./fixtures/shop
  repeat: 5
  expect:
    contains: "refund approved"
    trajectory:
      called_tool: stripe_refund
      never_called: delete_order
      max_steps: 12
      files_untouched: ["src/**"]
  graders:
    - {type: code, file: ../../graders/check-ledger.ts}
    - {type: judge, use: default, rubric: "Policy followed?"}

Case (Markdown)

---
id: tricky-customer
repeat: 5
workspace: ./fixtures/shop
graders:
  - type: judge
    rubric: Stayed polite under abuse?
---
Customer writes:

> I bought this 45 days ago and it broke. Refund me now or I chargeback.

Vet event protocol (normalized trajectory)

{"type": "step", "n": 1}
{"type": "message", "role": "assistant", "text": "…"}
{"type": "tool_call", "name": "stripe_refund", "input": {}, "result": "…", "durationMs": 812}
{"type": "result", "output": "final answer", "cost": 0.042, "tokens": {"in": 1200, "out": 900}}

Judge verdict protocol

{"pass": true, "score": 0.9, "reasoning": "Policy followed; no over-promise."}

run.json (summary)

{
  "id": "20260809-123000-a1b2",
  "git": {"commit": "abc123", "dirty": true},
  "summary": {
    "cases": 12, "passed": 10, "failed": 1, "graderErrors": 1,
    "passRate": 0.833,
    "cost": {"agent": 1.23, "judge": 0.31},
    "durationMs": 84000
  },
  "cases": [
    {"id": "refunds/tricky-customer", "status": "fail",
     "trials": 5, "passedTrials": 2, "passIf": "ratio:0.66",
     "graders": [{"type": "judge", "pass": false, "score": 0.3, "reasoning": "…"}]}
  ]
}

Case status values: pass | fail | grader-error | skipped. Grader errors are never silently counted as failures.

Tech stack

  • Runtime: TypeScript on Bun. Fast startup, native TS, easy npm distribution (bunx vet / global install). bun build --compile single-binary distribution is an option later.
  • Custom graders: TypeScript modules imported natively (a default-export grade(ctx) function).
  • HTML templating: a tiny TS-native engine (Eta or similar) with overridable partials.
  • Storage: plain JSON/JSONL files under .provet/ in v1; SQLite in v1.1 (run JSON is designed as the import source).
  • Adapters as the core module: claude-code, codex, http, command — each exposing invoke(case|prompt) → {output, trajectory, cost, latency}, consumed by both target execution and judging.

Explicitly cut from v1

Web UI · cloud execution · CI integration · dataset management / synthetic case generation · prompt registry & versioning · tracing/observability platform ambitions · human annotation queues · multi-project dashboards.

Roadmap

v1 (now)

The full feature set above: four adapters (Claude Code, Codex, HTTP, generic command), mixed-format eval authoring + CLI authoring, three grader tiers with per-case configuration, agent-as-judge, workspace fixtures, repeated trials with pass_if aggregation, file-based run storage, CLI + templated static HTML reporting, vet diff, agent-ready CLI surface.

v1.1

  • SQLite storage (one-command import from v1 run files)
  • Interactive dashboard (consumes the existing report view-model) and/or terminal TUI
  • Eval-level shared graders — graders declared once in the manifest, run for all cases, with per-case override (v1 keeps graders per-case)
  • Multi-turn / conversational evals — scripted or simulated multi-turn interactions with the agent under test
  • Majority-vote judging — repeat judge invocations with vote aggregation (no design change needed; judges already ride the adapter layer)

Later (unscheduled)

Cloud execution · CI integration (largely free given agent-ready CLI constraints) · web UI · dataset tooling.
