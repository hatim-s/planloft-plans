The picture is uneven: two runs burn almost all of their life waiting on a serial poll loop, while the real build turn is dense, parallel, and LLM-heavy. Fixing the right bottleneck means treating those two failure modes as different problems.

The build turn never idles. #1acf8499 (“Approved — go ahead and build it”) is 9m28s, 0% idle, 128 LLM calls, 208 tools, up to 12 spans in parallel.

The tension

There are three distinct latency signatures, and only one of them is “the agent is slow.”

Polling loops dominate wall clock. #1359ceb6 and #1ad360d7 spend 87–95% of their life with zero active LLM/tool span. The active work is tiny: 62 tools totaling under two minutes, three LLM calls. The gap pattern is mechanical — Trigger → wait ~80s → Inspect → Compile → repeat ×18 — so the user stares at a stalled timeline while the orchestrator sleeps between poll intervals. Same disease on the On-Demand rebuild: max idle slice 1m35s, steady multi-ten-second beats.

The real build is compute-bound and well-parallelized. #1acf8499 has zero idle and twelve concurrent lanes. Lane 0 is the planner/orchestrator (Invoke Solution Planner Agent, Generate App, object writes). Lanes 1–3 are the Workflow Agent build streams — each carrying ~7–11× Compile, 8–10× Trigger, 9–10× Inspect. Lanes 4–11 are short schema/search helpers fanning out. The longest single tool is Generate App at 10m03s, which alone exceeds the displayed 6m2s UI latency. This is where wall clock equals work, not wait.

Clarification turns burn tokens and wall time on huge prompts. #13595555 is 8% idle but 79 LLM calls — one call hit 1m48s, others 48s / 27s / 25s — for ~11.7M input tokens and $1.44 on that turn alone. RequestClarification alone totaled 1m46s. Same Compile/Trigger/Inspect swarm as the build (30/30/36), so config-after-clarify re-enters the poll path even when LLM is the visible cost.

Approach

Split the fix along the failure mode, not the trace name.

  1. Kill the poll gap first. It is the largest absolute latency (43 minutes and 11 minutes of pure wait) and the cheapest to reason about. Target the Trigger → Inspect cadence: cut the fixed sleep, back off on success, fail fast when the run is terminal, and surface run status as an event instead of a timer. Success metric: idle share on the store-master turn drops from 95% toward the 0–8% range the dense builds already show.

  2. Cap LLM time on clarification/config turns. Cap thinking budget, batch schema/search tools instead of round-tripping one at a time, and treat RequestClarification as a single front-door wait rather than a multi-minute tool busy block. Watch $/turn on #13595555-shaped turns as the guardrail.

  3. Instrument Generate App as its own critical path. 10m single tool span is invisible in the 6m UI number. Either expose it as a progress-bearing step or chunk it so the timeline reflects real work instead of one opaque bar.

  4. Do not mis-attribute connection waits. Keep Request Connection out of agent SLAs; it is human wait and already explains the 20s / 8.7s short traces.

Concrete steps

  • Re-run the offline analysis against fresh GetTraceTimeline pulls after any poll-timer change; compare idle % and max idle slice per trace (trace_analysis.json, trace-gantt.html).
  • In the Trigger/Inspect path: replace the ~80s fixed beat with adaptive backoff + terminal-state short-circuit; log one structured event per poll cycle with wait duration.
  • On clarification turns: measure p95 single-LLM latency (currently up to 1m48s) and input tokens per turn; set a budget before the next UAT pass.
  • For Generate App: add start/heartbeat/end spans under the parent query so Gantt and UI both show progress.
  • Keep the Gantt as the shared readout: trace-gantt.html already ranks runs, splits LLM/tool/idle by lane, and marks slow tools >30s.

Dependencies and risks

  • Poll behavior lives in automation run orchestration, not the chat UI — changing timers affects every solver that shares the runner.
  • Lane → Workflow Agent #1–4 mapping is inferred from concurrency + tool mix; exact attribution still needs workflowId from TraceTimelineDetails on Compile/Trigger inputs if we need names, not just streams.
  • UI latency and span-window wall clock already disagree on two traces (21s vs 5m35s connection wait); any SLA definition must say which clock it uses.

Expected outcome

Wall-clock pain concentrates in serial waits and one opaque generator, not in the parallel build. Cut the poll beat and the two idle giants collapse; instrument Generate App and the dense turn becomes honest. Next UAT pass should show the store-master turn drop from 43 minutes to minutes, with the Gantt as the pass/fail artifact.
