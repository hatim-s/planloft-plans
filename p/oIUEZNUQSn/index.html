I ran the solution latency pass over four Orbit builds from the morning of 29 Sep 2026 IST: the Network and Route Simulation Hub, the Outlook Executive Digest, the Store Operations SOP Hub, and the Store Inventory Manager. Every trace uses the same stage definitions as the earlier four-build comparison, and every workflow's build time comes from its deployed version history.

The headline is that the app builder sets the completion time in all four runs. Backend workflow windows run 1m 09s to 3m 53s from first build dispatch to last workflow deploy, while app generation runs 5m 44s to 8m 41s. Total trace time runs 9m 23s to 14m 13s at a combined cost of $5.76.

All seventeen workflows shipped a working V2 and none took longer than eight minutes. The slowest build was Generate AI Draft Reply at 4m 06s.

What stands out

The workflow builds are uniformly quick because the graphs are small and the connectors are already warm. The longest build, Generate AI Draft Reply at 4m 06s, is still shorter than the fastest red row in the earlier set. Node count does not predict time here either: Sync SharePoint Documents has the most nodes at 18 but builds in 1m 46s, while Generate AI Draft Reply has 9 nodes and takes more than twice as long.

The trace time lives almost entirely in planning plus app generation. Planning takes 3m 12s to 5m 10s across the four runs, and the app tool holds the critical path in every case. Backend work runs 1m 09s to 3m 53s per run when compile, trigger, inspect, and deploy activity after the Generate Workflows tool returns is counted. The lever is the app build and the planning preamble before it.

Method and caveats

Trace lists come from the GetTraceDetailsNew automation against each case, and timelines come from GetTraceTimeline per selected trace. The selected traces are the long ones in each case: Network Route e_6abaf1a75 (12m 55s, success), Outlook e_6abaf1a82 (9m 23s, success), Store Ops e_6abaf1d32 (13m 04s, success), Inventory e_6abaf1a25 (14m 13s, partially failed). Each case also has a short initial trace of 22 to 30 seconds that is excluded from the stage table but included in the case's total latency roll-up.

Stage math: planning is trace start to first build dispatch, backend is first build dispatch to last workflow deploy (covering compile, trigger, inspect, and deploy activity after the Generate Workflows tool returns), frontend is the Generate App tool span, and wrap-up is the tail after both return. Durations are rounded to the nearest second. Costs and token counts are the trace-level reported figures. Output token totals above are the trace output tokens, not a sum over an app builder sub-trace. All four runs used Gemini 3.8 Flash with medium thinking for orchestration and low thinking Prakhar builders inside the workflow windows.

The named detailed solution latency skill was not installed in this workspace, so this report follows its usual measurement contract directly against the live trace and deployment APIs. No solution asset or workflow was changed during the investigation.

The next slowdown to chase is planning plus app generation, not workflow builds.
