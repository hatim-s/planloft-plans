Await Plan is 7m 39s of pure waiting, 10% of app builder time. The builder runs a planning agent in parallel and blocks on it, and the block ranges from 0 s to 2m 14s across the 10 traces. In 7 of them it interrupts editing, so the builder has already started writing files when it stops to wait; in the other 3 it blocks up front, right after investigation. Real editing is 40m 9s (54%) and is generation-bound, not waiting.
Build, commit, finish is the second biggest phase at 13m 10s (18%), and it is three to four Build tool calls per run, which are compiles and deploys, not model calls. It is the one place where wall clock is platform work rather than generation.

Every trace is generation-bound, not orchestration-bound. A model is generating for 17m 18s inside a 13m 14s trace, more than the wall clock because the main agent and its sub-agents generate in parallel. Only 33s is the main agent sitting on tool results, and runtime overhead, the gap between an LLM call ending and the next one starting, never exceeds 17 s in any of the 62 runs. No run in this set hits the 30 s stall threshold. There is no orchestration tax to remove here.
Throughput is the ceiling. Workflow runs generate at 83 tok/s and the app builder at 173 tok/s, so a 5k-token edit costs about 30 s of generation no matter how little else the run has to do. All 10 traces hit the output-bound detector. The app builder is the largest LLM consumer in 7 of the 10, the workflow runs in the other 3, and the main agent is never the largest. Uncached calls take a further 44% to 64% of total spend in every trace, median 56%. That one is a pricing lever rather than a latency lever.
Planning is the one stage nobody looks at. 5m 2s per trace, 38% of wall clock, before a single file is written, for $2.84 across the ten. It is main agent and planner LLM work: connection setup, schema discovery, clarifications, the plan. Only 39s per trace is wrap-up after the last build, so the run is front-loaded and the tail is short.
