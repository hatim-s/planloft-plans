Workflow agent knowledge & validation roadmap

A source-grounded plan for deciding what workflow agents should reason about, what they should load on demand, and what the platform should enforce before a workflow reaches runtime.

UACode 1c24bac · WWW e6012dd on refactor/automation-cleanup-modular · UA Builder 43509e0

Decision Do not begin by adding a large body of prompt knowledge. First repair the source catalog and the two destructive cleanup defects found in WWW. Then generate a versioned contract catalog, add deterministic validators, and retain only semantic choice, surprising runtime behavior, safety boundaries, and cross-node lifecycle rules in skills.

Scope and evidence standard

The research combined three read-only code scouts and a direct audit of the active cleanup pipeline. It inventoried all Storage resources, 229 resources across ten internal platform domains, and 178 resources across utilities, files, code, variables, caches, streams, signals, and latches. The platform scout traced 196 Java implementations; the utility scout traced the corresponding Java builders, runtime handlers, selected tests, and checked-in platform-feature workflows.

Authority 1

Java runtime

Builders, action handlers, trigger handlers, dynamic schema providers, and runtime validation define what executes.

Authority 2

Node contracts

configs/workflow-nodes defines the authoring surface. Any disagreement with Java is a defect to resolve, not something to silently teach around.

Evidence only

Workflows and notes

Checked-in workflows show real conventions. Notes accelerate discovery but are not normative: UACode’s own wiki stress audit found guessed fields and false entity names.

Usage counts in this report are checked-in configs/platform-features occurrences, not production telemetry. The runtime skill list is a UAT snapshot fetched on 03 August 2026, not a live read.

What WWW already does

The active pipeline is modular and substantial. It prepares structure, loads one static asset wave, normalizes known representations, resolves output schemas, validates pills and generic inputs, applies UI-equivalent defaults, runs callable/API and SQL checks, and invokes backend validation once for remote cleanup. New work should extend these seams, not create a parallel validator.

The capability index

Add prompts/skills/workflow-capability-index.md, approximately 60–100 lines, and make it available to planner, builder, and editor. It should contain only:

  • User intent → owning skill.
  • appName/resourceName family → owning skill or knowledge-only route.
  • “Wrong skill? stop and switch” boundaries.
  • Authority order and the source revision/date.
  • Planner owns business intent; builder/editor own emission contracts; cleanup owns deterministic invariants.
  • Never infer one action’s input/output shape from a similarly named action.

It should not contain action tables, copied schemas, tutorials, examples, or descriptions of runtime orchestration.

Generated knowledge

Generate prompts/knowledge/workflow-nodes/<family>/ from UACode. Each action entry should include resource name, inputs, required and conditional fields, enums, outputs/pill paths, Java builder/runtime pointers, known conflicts, checked-in usage count, source SHA, and generation date. Generated files should fail CI on unexplained drift. A reviewed delta overlay should record facts only Java can reveal.

Validation and cleanup backlog

P0 · prevent corruption and catalog drift

  • WWW: preserve create_variables.inputs; normalize only output schema. Replace the current destructive test with preservation and schema-key tests.
  • WWW: canonicalize every Java-supported Storage system alias and nested path form. Add idempotence cases for aliases, verbose names, dot paths, and underscore paths.
  • UACode CI: globally enforce required ⊆ properties, with explicit dynamic-schema exceptions.
  • UACode contract parity: compare resource registrations with JSON inventory and Java-consumed input/output keys. Fail unexplained additions, removals, and type conflicts.
  • Denylist until fixed: files_by_unifyapps_copy_file; cleanup cannot safely infer append vs overwrite.
  • Runtime fixes: return booleans for Storage delete/archive, align append-line type, correct signal/notification/auth/unified-entity schemas, and prevent encryption secret logging.

P2 · specialist validations and advisories

  • Files/iterators: file object vs URL/base64 compatibility; upload discriminators; batch size ≥ 1; JSON iterator encoding/start fields; text iterator’s distinct defaults; action-specific outputs.
  • Utilities: list SQL has data sources and referenced names; nonempty filters; 1-based index bounds where literal; explicit epoch unit; warn when blank date would silently become now.
  • Streams: object event, consumer group for commit flows, delay pairing, DLQ dependency, replay/force-republish semantics.
  • Unified entity: Java-required relationship fields, bounded query limit, destructive filter, explicit permission for skipRBAC, corrected outputs.
  • Auth: workflow vs interface surface, supported pills, explicit brief requirement, secret/session logging sinks.
  • Workflow operations: bounded cancel/cleanup target, required run/workflow IDs, self-retry maximum/guard.
  • Analytics/audit: projection/filter/sort/time semantics; advise when omitted assetId broadens an audit query.

Runtime surprises worth teaching—until fixed

  • Variable creation values are real node inputs; find/update resolves a plain name, while normal update uses a producer pill.
  • Plural signal wait waits for all IDs; long waits preserve only selected outputs; loop completion uses completed: true.
  • In-app notifications need content.templateId; USER and USER_GROUP receiver cardinalities differ.
  • Storage patch accepts bare or dotted field names, not underscore filter spelling; UNSET needs no value.
  • List indexing is 1-based; blank date can become “now”; an empty/invalid utility filter can evaluate true.
  • JSON iterator defaults differ from text iterator; zero batch size can loop indefinitely.
  • AES-SHA mismatch returns isValid:false instead of throwing; the flow must branch on it.
  • Async callable output is only {result:boolean}; synchronous callee fields are invalid pills.

Incremental roadmap

Freeze evidence and protect current work

Record UACode/WWW/UA Builder SHAs, preserve the dirty checkout, publish a machine-readable issue ledger, and assign every claim an owner, source path, and intended layer.

Exit: no untracked contract decision; zero source edits mixed into research.

Fix P0 source and cleanup defects

Stop variable-value deletion; repair Storage alias/nested canonicalization; add global schema lint; fix or denylist broken resource contracts; update stale skill claims only after source decisions land.

Exit: regression tests fail on the old behavior and pass on preservation/canonicalization.

Build the contract generator

Generate action catalogs from JSON plus Java registration/consumption overlays. Stamp revision and date. Emit an unresolved-conflict report; never silently merge conflicting authorities.

Exit: deterministic regeneration is clean and CI catches a seeded drift.

Add high-value WWW blockers

Implement variable, callable, Storage, Playwright, signal/latch, notification, retry/error, branch, and pill rules in the existing phase pipeline. Preserve fixed ordering and one asset wave.

Exit: focused rule tests, idempotence, immutability, package typecheck, and backend parity fixtures pass.

Add the routing index

Ship the 60–100 line capability index to planner/builder/editor. Test that it routes exact intents without leaking implementation fields into planner briefs.

Exit: routing evals cover every current and proposed skill, including wrong-skill cases.

Refactor existing skills

Slim Storage, callables, code, files, variables, and platform. Move exhaustive tables to generated references. Remove rules now owned by deterministic validation and split platform administration from identity resolution.

Exit: fewer tokens, no lost semantic decisions, and builder/editor goldens stay equivalent or improve.

First new-skill wave

Add signals-and-waits, workflow-latches, notifications, and workflow-operations. Fold audit into analytics and cache actions into workflow-performance.

Exit: planner business-language tests plus builder/editor valid/invalid goldens for each family.

Conditional specialist wave

Add streams, unified-entity graph, and authentication only after their contracts and security boundaries are corrected. Add data-pipelines only if evals or production telemetry show demand.

Exit: no skill teaches around an unresolved blocker; security-sensitive flows require explicit intent.

Continuous drift and quality gates

Run catalog lint, Java-registration parity, generated-doc drift, WWW validators, agent routing evals, golden workflow tests, and prompt-size budgets in CI. Track validator false positives and skill load rates.

Exit: a node contract change cannot land without updated generated knowledge or an explicit reviewed conflict.

Definition of done

  • Every skill fact is either semantic judgment or links to a revisioned generated source.
  • No skill preserves a workaround for a corrected deterministic defect.
  • Planner output stays in business language; builder/editor load exact contracts only when relevant.
  • Every blocking validator has a minimal failing fixture and a valid near-neighbor fixture.
  • Every canonicalizer is immutable, idempotent, and meaning-preserving.
  • Unknown or runtime-defined contracts fail open only where the existing pipeline explicitly permits it; confirmed invalid contracts fail closed.
  • Checked-in notes cannot introduce a field/entity claim without a source pointer.
