AI App Builder — Early GTM Readiness and Polish Plan

Prepared: 2026-08-08
Planning horizon: 4–6 focused weeks to paid early access
Product thesis: an AI-native builder for safe, editable internal tools whose app is a JSON spec, whose agent changes can be inspected and reverted, and whose published apps can read and mutate real APIs without exposing credentials.

Executive decision

The builder is no longer in a broad “prove the architecture” phase. The core architecture, visual builder, agent editing, data queries, releases, event/lifecycle system, encrypted app secrets, BYOK foundations, and pessimistic mutations are substantially present. CRUD is the current product spine and should remain the integration priority.

Feature parity is not yet complete for a credible CRUD/internal-tool launch, but the missing feature set is narrow. Do not add another large platform layer before GTM. Complete the small internal-tool parity pack, then spend most capacity on activation, reliability, usage control, security, and polish.

The fastest credible release sequence is:

  1. Private design-partner alpha: CRUD golden paths, truthful onboarding, production deployment, recovery/security gates, and funnel instrumentation.
  2. Paid early access: authoritative usage limits, billing, legal/support basics, and repeatable launch operations.
  3. Team beta: invitations, roles, shared ownership, and durable audit/history.

Current progress snapshot

Confirmed shipped on main

  • JSON-spec builder, preview, publish/release rendering, and public app routes.
  • Human and agent co-editing with operation history, undo/revert, forked conversations, and guarded revision semantics.
  • Query runtime with page/app scope, derived state, lifecycle handlers, event actions, retries, and proxy boundaries.
  • Pessimistic mutation contract and execution path for POST, PUT, PATCH, and DELETE, including invalidation and secret-aware proxying.
  • Encrypted app-secret vault, origin restrictions, release redaction, and server-only secret resolution.
  • Clerk ownership boundaries, user BYOK storage foundations, agent run telemetry, and provider/model selection.
  • Builder catalog for Stack, Text, Button, TextInput, Checkbox, RadioGroup, Form, Table, Chart, and List.
  • CI-gated Studio deployment topology and a development stack across Vercel, Railway, Convex, and Clerk.
  • Event/lifecycle platform, interaction editor, loop protection, event log, and agent grammar from the recent D2 merge series.

Current work observed but not counted as shipped

The working tree shows active implementation around optimistic mutation projection/rollback, query cache projection, op-signal watermarks, stricter BYOK service-key boundaries, and deployment documentation. These are strong CRUD/trust fast-follows, but remain work in progress until committed, reviewed, green in CI, and deployed from one verified SHA.

Two local commits also add a landing bundle budget and fail-closed measurement. They are ahead of the remote main branch and therefore are not yet part of the deployed product.

  • No remote CRUD branch was visible; the CRUD/optimistic work currently appears in the local working tree.

Roadmap reconciliation

The older roadmap and GTM notes correctly identified writes, secret handling, deployment, billing, and trust as launch blockers. The first three have moved materially:

  • Writes: pessimistic CRUD exists; optimistic behavior is actively being completed.
  • Secrets: encrypted app secrets and stronger BYOK boundaries exist or are in progress.
  • Deployment: a development topology and CI-gated Studio deployment exist.

What remains unchanged:

  • Usage telemetry is non-authoritative and cannot safely drive billing or quotas.
  • There is no complete paid-plan, entitlement, checkout, webhook, or budget-exhaustion experience.
  • Onboarding promises persistent CRUD outcomes before explaining where data lives or how an API is connected.
  • The current product is single-owner; collaboration and governance remain later differentiators.
  • Production recovery, stress, security, accessibility, and launch operations have not yet passed an evidence-based GTM gate.

Scope boundary: the last pre-GTM product features

Must add for credible internal-tool CRUD parity

Keep this as one deliberately small catalog expansion:

  • Select input with static and query-backed options.
  • Date input; retain TextInput number mode for the first release, adding currency formatting only if a golden template proves it necessary.
  • Status/Badge display primitive for operational tables and lists.
  • Confirmation dialog for destructive actions; a general modal/drawer system is not required yet.
  • Search/filter pattern for Table/List, either as first-class props or a documented TextInput + state + query pattern.
  • Form validation and field-level error states, including server mutation errors.

Each addition must cover the frozen definition, renderer, inspector, DSL round trip, agent grammar, event/binding behavior, accessibility, and golden examples. Avoid adding tabs, navigation builders, arbitrary JavaScript, database hosting, code export, mobile-native output, CRDT collaboration, or a broad component marketplace before the first paid cohort.

Defer until evidence demands it

  • File upload as an app block (chat image attachments already solve a different problem).
  • Custom domains, unless a design partner makes it a purchase condition.
  • Teams, roles, and approval workflows for the solo/prosumer early-access cohort.
  • General modal/drawer/navigation primitives beyond destructive confirmation.
  • Hosted database/schema builder; the first GTM can be API-first if onboarding says so clearly.

Parallel delivery lanes

CRUD remains the spine. The following lanes can run in parallel using isolated branches/worktrees and the existing ownership boundaries. Shared schema/catalog/contracts must land through an integrator wave.

Lane A — CRUD completion and golden paths (critical path)

Goal: five operations feel like one coherent feature: list, create, inspect, edit, delete.

  • Finish pessimistic and optimistic behavior, deterministic rollback, invalidation, duplicate-submit protection, and visible pending/success/error states.
  • Finish structured mutation authoring and agent grammar.
  • Build three golden apps: customer requests tracker, expense tracker, and inventory manager.
  • Test draft and released runtime parity against the same API fixtures.

Exit: each golden app completes create/read/update/delete, survives refresh, handles 4xx/5xx/timeout, and publishes without credential leakage.

Lane B — Internal-tool block parity

Goal: close only the UI primitives that block believable CRUD apps.

  • Select, Date, Badge/Status, destructive confirmation, search/filter, and validation states.
  • Keyboard and screen-reader semantics from the first commit.
  • Agent examples and evaluator fixtures for each primitive.

Exit: the three golden apps need no fake text fields or custom workarounds.

Lane C — Activation, onboarding, and templates

Goal: a new user reaches a successful live data operation without guessing the product model.

  • Replace generic CRUD promises with two explicit paths: “connect an API” and “explore with sample data.”
  • Add connection test, secret setup, method/endpoint explanation, and recovery copy.
  • Turn golden apps into maintained starter templates with preview and duplicate.
  • Add an activation checklist: first app, first agent change, first data read, first successful write, first publish.
  • Reconcile the landing message: lead with safe editable internal tools, then use selective revert as proof.

Exit: median test user reaches first successful published CRUD action in under 15 minutes without operator help.

Lane D — Usage control, entitlements, and billing

Goal: prevent uncontrolled spend and make the pricing page true.

  • Record usage at a trusted server boundary; never bill from caller-supplied Convex telemetry.
  • Enforce per-run step/token/time limits plus monthly account allowances.
  • Add free/pro entitlements, Stripe Checkout, Customer Portal, idempotent webhooks, and a small immutable usage ledger.
  • Define BYOK behavior separately from platform-funded usage.
  • Build warning, exhaustion, failed-payment, cancellation, and restore-access states.

Exit: duplicate webhooks cannot double-grant access, every paid capability checks entitlement server-side, and a hard budget cannot be exceeded through retries or concurrent sessions.

Lane E — Production release and reliability

Goal: deploy, observe, recover, and roll back one coherent product version.

  • Resolve the GitHub billing/CI blocker; push the local bundle-budget commits through review.
  • Establish separate production Clerk, Convex, Railway, and Vercel configuration.
  • Deploy all services from one recorded commit SHA; add health/version endpoints and a compatibility smoke test.
  • Document database backup/restore, secret rotation, rollback, incident response, and ownership.
  • Add error aggregation, structured logs, uptime checks, and a public status surface.

Exit: a clean checkout reaches production through CI; rollback and restore are rehearsed; operators can identify app, user, run, release, and service version without exposing secrets.

Lane F — Trust, security, and recovery

Goal: make “safe co-editing” true under failure and hostile input.

  • Persist the minimum operation/checkpoint history required to recover after reload or another device; clearly label session-only history until then.
  • Close op-signal pruning/gap recovery and stale-writer cases.
  • Threat-model proxy SSRF/DNS rebinding, secret exfiltration, cross-tenant access, stored/published XSS, prompt injection through API data, and release redaction.
  • Enforce tenant checks on every read/write/action boundary; automate adversarial tests.
  • Add account export/deletion and secret revocation workflows.

Exit: critical/high findings are zero; red-team fixtures cannot cross tenant boundaries or leak secrets; a failed agent run and failed mutation both recover deterministically.

Lane G — Product analytics and learning loop

Goal: know whether the product activates and retains users before buying traffic.

  • Instrument: landing CTA, sign-up, onboarding start/completion, template chosen, first app, first agent success, first data read, first write, first publish, return visit, and error category.
  • Keep product analytics separate from operational traces; establish consent and retention rules.
  • Add in-product feedback and “report this run” with redacted diagnostics.
  • Build a small cohort dashboard for activation, time-to-value, publish success, agent success, CRUD success, and week-one return.

Exit: every critical funnel stage has a denominator, failure reason, and owner; a design-partner session can be replayed through events without reading private app data.

Lane H — Comprehensive polish and stress pass

Goal: remove the friction that makes a technically complete product feel unfinished.

  • Run the iteration matrix below after UI contracts settle; fix severity 0/1 issues immediately and schedule severity 2 issues against activation impact.
  • Perform a copy pass across navigation, empty/loading/error/success states, destructive actions, publish, quotas, and authentication.
  • Ensure reduced motion and no delayed invisible primary CTA; motion must not obstruct automation, scrolling, or comprehension.
  • Validate responsive density for landing, onboarding, dashboard, builder panels, data editor, settings, and released apps.

Exit: the launch matrix is signed off with screenshots, recordings, measurements, owners, and accepted residual risks.

Lane I — GTM operations, support, and proof

Goal: be able to acquire and support the first 10 paying users.

  • Recruit 5–10 design partners with one narrow job: build a governed internal CRUD tool over an existing API.
  • Publish a 90-second product demo, three template walkthroughs, concise API/data docs, privacy policy, terms, support SLA, and security overview.
  • Create onboarding email, stalled-user rescue, feedback interview, incident, refund, and cancellation playbooks.
  • Collect proof around time saved, successful published tools, and recovery from agent mistakes.

Exit: every signup has an owner and support route; the landing page has real proof; launch messaging describes what the product reliably does today.

Polish and stress-test matrix

End-to-end product journeys

Test on Chrome, Safari, and Firefox at desktop and mobile/tablet breakpoints:

  1. Landing → sign-up → onboarding → template → first agent run.
  2. Connect API → save secret → test query → bind Table/List.
  3. Create → optimistic state → server success → invalidated query refresh.
  4. Update/delete → confirmation → server rejection → rollback and recovery.
  5. Undo one agent run while retaining later human edits.
  6. Publish → visit live slug → refresh → pinned release → republish.
  7. Quota warning → exhaustion → upgrade → entitlement restore.
  8. Sign out/in, expired auth, deleted account, and revoked provider key.

Data and failure matrix

  • Empty, one-row, 1,000-row, deeply nested, malformed, and partially missing data.
  • API 400/401/403/404/409/422/429/500, network loss, slow response, invalid JSON, oversized response, and retry storms.
  • Double click, back navigation, reload mid-write, concurrent writes, out-of-order responses, and stale revisions.
  • Agent unavailable, provider unavailable, rate limited, tool loop, partial stream, browser close, and service-version skew.
  • Publish while editing, release read during deploy, proxy timeout, secret rotation, and invalidated credentials.

Performance budgets

  • Landing LCP ≤ 2.5 s p75, CLS ≤ 0.1, INP ≤ 200 ms on representative mobile hardware/network.
  • Dashboard usable ≤ 3 s p75 after auth; builder interaction remains responsive with 250 blocks and 20 queries/mutations.
  • Agent feedback appears immediately, long runs can abort, and streamed updates do not freeze the canvas.
  • Published app query/mutation overhead is measured separately from upstream API latency.
  • Bundle budgets fail closed in CI and are measured on the artifact actually deployed.

Accessibility and usability

  • Complete keyboard path, visible focus, sensible focus return, skip navigation, labels/descriptions, and error associations.
  • Screen-reader pass for onboarding, builder controls, Data panel, dialogs, notifications, Table, Form, and released apps.
  • Contrast, reduced motion, 200% zoom, reflow, touch targets, and status announcements.
  • Destructive actions and irreversible consequences use explicit copy and confirmation.

Security and privacy

  • Cross-tenant ID substitution on every query, mutation, action, release, message, attachment, secret, and telemetry endpoint.
  • SSRF, redirect chains, DNS rebinding, credential forwarding, request/response size, and egress-rate limits.
  • Prompt injection via fetched data and attachments; HTML/style/URL sanitization; release credential redaction.
  • Secret values absent from browser state, public releases, logs, analytics, support bundles, and error messages.
  • Dependency and supply-chain scan, headers/CSP, cookie policy, session expiry, webhook signature/replay, and deletion retention.

Operational resilience

  • Backup and restore rehearsal with measured RPO/RTO.
  • Rollback Studio, agent, and backend independently while enforcing compatibility.
  • Load test concurrent agent runs, published-app traffic, proxy writes, telemetry, and live subscriptions.
  • Alert tests for error rate, latency, budget burn, failed billing webhooks, and deployment mismatch.
  • Incident drill with customer communication and post-incident follow-up.

Launch gates

Gate 1 — Design-partner alpha

  • Three golden CRUD apps pass the full journey.
  • Production environment is isolated, observable, restorable, and same-SHA verified.
  • Truthful data onboarding and at least one maintained template are live.
  • Critical auth/secret/proxy/release tests are green.
  • Funnel analytics and in-product feedback are live.
  • No severity 0/1 known issues.

Gate 2 — Paid early access

  • Authoritative usage ledger, hard budgets, entitlements, checkout, portal, and webhook replay protection are live.
  • Terms, privacy, support, account deletion/export, and incident process are live.
  • At least five design partners have completed the golden journey; at least three returned and published again.
  • Activation and retention targets are set from observed data rather than invented benchmarks.

Gate 3 — Broader/team GTM

  • Invitations, roles, shared ownership, and durable audit/history exist.
  • Proven acquisition message and at least two credible customer stories exist.
  • Support load, gross margin, reliability, and security evidence support wider distribution.

Recommended six-week sequence

Week 0: integration and release hygiene

  • Freeze shared contracts for the CRUD milestone.
  • Convert current working-tree changes into narrow conventional commits/PRs.
  • Resolve CI billing and deploy the same SHA across the development stack.
  • Establish owners and dashboards for each launch gate.

Weeks 1–2: alpha critical path

  • Lane A completes CRUD and golden fixtures.
  • Lane E establishes production/recovery basics.
  • Lane C ships truthful onboarding and one sample-data template.
  • Lane G instruments the funnel.
  • Lane F closes the highest-risk auth/secret/proxy cases.

Weeks 3–4: paid-product path

  • Lane B lands only launch-blocking primitives.
  • Lane D ships usage limits and billing-lite.
  • Lane H runs cross-browser, accessibility, responsive, performance, and failure iterations.
  • Invite the first five design partners; fix activation blockers daily.

Weeks 5–6: evidence and launch

  • Complete the full stress matrix and recovery drill.
  • Close legal/support/incident materials and publish real proof.
  • Invite the next five design partners, verify repeat usage, and open paid early access only when Gate 2 is met.

Immediate next slice

Run four parallel tracks now:

  1. CRUD integration remains the spine and owns shared-contract timing.
  2. Production + recovery starts immediately because it is independent of CRUD UI details and is the longest operational lead time.
  3. Authoritative usage + entitlements starts at the server boundary before Stripe UI work.
  4. Onboarding + golden templates + funnel analytics starts with sample-data mode and becomes live-data aware as CRUD contracts stabilize.

Start the small block-parity pack after the CRUD contract freeze. Run the broad polish matrix only after those surfaces stabilize; otherwise the team will repeatedly polish moving UI.

Definition of “GTM-ready”

GTM-ready does not mean every requested feature exists. It means a narrowly defined buyer can reach a valuable, published CRUD outcome quickly; the outcome survives failure; spend and access are bounded; secrets and tenants stay isolated; operators can recover the service; and the team can measure, support, and improve the journey.
