We analysed the eight Orbit UAT traces behind the Advance Auto Parts Store Performance Hub build to find which workflow-agent runs are actually slow. The answer is not LLM cost. Two runs burn 30+ minutes while doing almost no LLM or tool work at all.

The situation is a single solution chat with eight query traces, one of which fans out to five sub-agents. Total wall time is dominated by two workflow-agent sessions that loop on Compile, Trigger, and Inspect while spending over 85% of their lives idle. The token-heavy traces are a separate problem: they finish, but they cost dollars because every turn re-sends the full brief.

The longest runs are gap-dominated, not compute-dominated. Fix the waiting, not the model.

Generate App is the critical path of the fan-out. Everything else waits on it.

Turns and patterns that take the time

Store-Master runs a tight Compile (3s), Trigger (2s), Inspect (0.2s) loop more than fifteen times. Each iteration costs about five seconds of tool time, then sits idle for thirty to ninety seconds before the next iteration. Only three LLM calls appear in the whole run.

On-Demand repeats the same loop for ten cycles, then stalls 95 seconds between two LoadSkill calls with nothing in between. Skill fetch or cold start plus serial skill loads explain that hole.

DailyMetrics plus Alerts is a genuine build-test loop: 79 LLM turns averaging nine seconds, max 48 seconds with one 108-second outlier, interleaved with Compile and Trigger. The 1m45s RequestClarification span is user think time on the four questions, not compute. Input tokens hit 11.6M, which points at the full brief being re-sent every turn.

The Approved fan-out is the parent of the five agents. Generate App runs 10m02s and outlives the 9m28s parent query, so it continues in the background. Generate Workflows runs 1m52s in parallel. Inside it are dozens of sub-300ms Open Automation, Describe Storage, and Get Operation Schema calls, plus a 3m28s RequestClarification wait and the usual Compile, Trigger, Inspect cycles for the four workflow stubs.

The Slack-connection trace is one 2m56s Gemini thinking call with about 100k tokens. That is plan population with the full object and automation briefs in context. Expected shape, oversized prompt.

What changes

  • Cap Inspect Automation Run polling for Store-Master and On-Demand. Replace sleep-poll with run-status push, and record automation runId queue time as its own span so gaps stop hiding inside the agent.
  • Cache skills and load them in parallel. The 95-second LoadSkill hole should not exist twice per run.
  • Batch compiles in DailyMetrics plus Alerts. Do not Compile, Trigger, Inspect on every small edit when the failure signature has not changed.
  • Shrink planner context. Summarise object and automation briefs before the 2m56s thinking call instead of sending 100k tokens raw.
  • Profile Generate App on its own. It is the fan-out critical path at ten minutes, likely generating five screens serially.

Risks and open questions

  • Timeline wall time and span sums disagree on parallel traces because nested and overlapping spans are double-counted. Treat LLM and tool totals on #13595555 and #1acf8499 as effort, not wall time.
  • Store-Master shows success at the trace level but the solution summary reports it as not deployed. The Deploy Automation span exists, so the loss happened after deploy or on a later overwrite. That needs a deployment-log check.
  • Short Request Connection tools report durations longer than their parent traces, which means they continue asynchronously. Do not read those tool totals as blocking time.

The slow agents are slow because of waiting between fast steps. Close the gaps first, then cut the tokens.
