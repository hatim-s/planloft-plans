Planloft Single-Skill, Contract Repair, API, and Distribution Roadmap

Goal

Make Planloft an agent-native document compiler with one deep semantic skill, a self-teaching CLI, trustworthy contracts, a reusable Node interface, and a verified installation experience across npm, pnpm, Bun, Codex, and Claude Code.

The target product model is intentionally small:

  • write-plan is the only semantic skill.
  • The CLI owns rendering, storage, preview, copy, publication, removal, configuration, and discovery.
  • planloft help teaches agents and humans how every command works.
  • Non-plan documents remain supported through planloft hoist; they do not need an automatically triggered save-doc skill.
  • Installing the CLI, installing the skill, and installing the full plugin are treated as distinct products with explicit capability boundaries.

Context

Planloft currently ships five skills: write-plan, save-doc, planloft-preview, planloft-copy, and planloft-deploy. Four are unnecessary as independent semantic skills. Preview, copy, and deploy restate single CLI invocations. Save-doc adds capture policy, but its actual persistence capability already exists at the hoist seam.

Planloft also exposes eleven public CLI commands, a canonical document pipeline, three built-in themes, a project-keyed global store, a small Node library, and GitHub Pages publication. The main architectural problem is not a shortage of commands. It is that command knowledge, validation, output formatting, and side effects are spread across skills, command prompts, CLI handlers, README prose, configuration code, renderer code, and the GitHub adapter.

The external skills CLI already provides the desired installation mechanism. It can discover skills/<name>/SKILL.md from a GitHub repository and install a selected skill for Codex, Claude Code, and other agents. The canonical package-runner forms are:

npx skills add hatim-s/planloft --skill write-plan
pnpm dlx skills add hatim-s/planloft --skill write-plan
bunx skills add hatim-s/planloft --skill write-plan

There is no generic npm skills, pnpm skills, or bun skills command. The runner is npx, pnpm dlx, or bunx; the executable being run is the separate skills npm package.

Decisions to ratify

  1. Planloft has exactly one semantic skill: write-plan.
  2. Automatic agent capture applies only to substantial plans.
  3. preview, copy, and deploy remain CLI commands, not skills.
  4. save-doc is removed; non-plan documents use planloft hoist.
  5. planloft help becomes the authoritative command-discovery interface.
  6. The remaining skill contains only compact references to other commands.
  7. Deploy and publish remain explicit, user-authorized external writes.
  8. The canonical document pipeline remains the source of truth: document source -> canonical document -> render, hoist, or publish.
  9. Direct Markdown, JSON, and explicitly trusted HTML remain supported.
  10. Agent-authored plans should be Markdown sources rendered into HTML; direct trusted HTML remains available to explicit callers.
  11. Installing the skill does not imply that the CLI, hooks, themes, or plugin assets were installed.
  12. GitHub Pages deployment is public. An unguessable URL and noindex do not provide access control because the hosting repository and manifest are enumerable.

After Phase 0, the skill/help, contract-repair, installer, and public-interface discovery lanes can proceed in parallel. Skill and help must converge before installer testing. Contract semantics must be stable before the public Node interface is frozen.

Phase 0 - Freeze the product model

0.1 Capture the existing surface

Before changing behavior:

  1. Record planloft --help.
  2. Record planloft help <command> for every public command.
  3. Record all currently discovered skill names.
  4. Record the Codex and Claude plugin manifests.
  5. Record hook matchers and hook messages.
  6. Record the npm pack manifest and exact tarball contents.
  7. Run existing ingestion, hoisting, and rendering tests.
  8. Run typecheck and build.
  9. Add baseline tests for help, configuration, themes, hooks, deploy option parsing, copy destination, skill discovery, and package contents.

0.2 Add a superseding ADR

Add a new ADR that:

  • Supersedes ADR-0002 E4, which introduced save-doc.
  • Supersedes ADR-0004's five-skill decision.
  • Amends ADR-0001 D1 and D23 to distinguish CLI, skill, and plugin installation.
  • Amends ADR-0001 D16 if Claude slash-command aliases are removed.
  • Amends ADR-0001 D9 if agent plan authoring becomes Markdown-only.
  • Preserves write-direct plan capture, project identity, plan-mode hooks, theme-guided authoring, the existing CLI verbs, and ADR-0007's canonical document pipeline.

0.3 Define release boundaries

Use two releases:

  • Release 1: one skill, deep help, all contract repairs, installer experience, and migration documentation.
  • Release 2: deep public Node interface after the repaired behavior is stable.

This prevents the installation and contract work from being blocked by premature interface design.

Phase 1 - Consolidate to one skill and deepen help

1.1 Remove shallow skills

Delete:

skills/planloft-preview/
skills/planloft-copy/
skills/planloft-deploy/
skills/save-doc/

If the intended model is literally CLI-only for preview/copy/deploy, also retire:

commands/planloft-preview.md
commands/planloft-copy.md
commands/planloft-deploy.md

Do not remove the corresponding CLI commands, the resolve helper, hooks, themes, document kinds, or canonical document operations.

1.2 Rewrite write-plan

The remaining skill should have one deep responsibility: author and persist a substantial, renderable Planloft plan.

Trigger contract

Use for:

  • Substantial implementation plans.
  • Migration, refactor, architecture, and design plans worth retaining.
  • Plan-mode completion with durable content.
  • Explicit requests to save a plan with Planloft.

Skip for:

  • Trivial one-step work.
  • Conversational or throwaway output.
  • Requests that only preview, copy, render, hoist, or deploy an existing source.

Resolution contract

Run:

planloft resolve --kind plan --slug "<slug>" --title "<title>"

Never guess the storage path.

Authoring contract

  • Author Markdown.
  • Include title, slug, kind, and status frontmatter.
  • Follow the returned theme guidance.
  • Write a standalone plan that can be reviewed without conversation history.
  • Let Planloft render the HTML artifact; do not manually author generated HTML.

Discovery references

The skill should say:

Run `planloft help` to discover all operations.

Common next actions:
- `planloft render <input>` produces HTML without storing or publishing.
- `planloft preview [slug]` opens a stored plan locally.
- `planloft copy [slug]` copies raw source into the repository.
- `planloft deploy [slug]` explicitly publishes a stored plan.
- `planloft hoist <input>` stores another Markdown, JSON, or trusted HTML document.

The skill must not reproduce every flag or workflow. It must never deploy unless the user explicitly requests publication.

1.3 Create a command-knowledge module

Concentrate these facts for every command:

  • Name and category.
  • One-line purpose.
  • Whether it consumes a source or stored document.
  • Whether it writes locally.
  • Whether it performs an external write.
  • Whether it is destructive.
  • Defaults.
  • Examples.
  • Trust and privacy notes.

The command-knowledge module should serve:

  • Commander root help.
  • Per-command help.
  • README verification or generation.
  • Tests.
  • The compact discovery section in write-plan.
  • Plugin default prompts.

This creates one authoritative interface instead of allowing skills, docs, and CLI descriptions to drift independently.

1.4 Deepen planloft help

Group commands by workflow:

Write and transform sources
  render, hoist, publish

Work with stored documents
  list, preview, copy, deploy, rm

Agent integration
  resolve

Configuration
  config, init

Teach state transitions:

render:  source -> artifact
hoist:   source -> canonical document -> store
publish: source -> store -> artifact -> GitHub Pages
preview: stored document -> temporary local artifact
copy:    stored document -> repository source
deploy:  stored document -> public GitHub Pages artifact

Include safety markers:

  • --trusted-html is an explicit trust decision.
  • publish and deploy write to GitHub.
  • The backing GitHub repository and manifest are public.
  • rm deletes stored source.
  • Comments require valid giscus configuration.
  • TTL must be a positive integer.

Every command should include at least one tested example.

1.5 Align integration files

Update:

  • Codex plugin metadata.
  • Claude plugin metadata.
  • README.
  • Hook wording.
  • resolve comments.
  • Package description and keywords.
  • Default prompts.
  • ADR index and statuses.

Phase 1 gate

  • Exactly one skill is discoverable: write-plan.
  • No shipped file advertises the four removed skills.
  • Root help lists all public commands.
  • The remaining skill refers to help instead of duplicating commands.
  • Hooks still nudge only toward write-plan.
  • The npm tarball contains one skill directory.
  • CLI-only and full-plugin installation both remain coherent.

Phase 2 - Repair all ten contract gaps

Run the publication, configuration/theme, and document/persistence lanes in parallel.

Publication lane

2.1 Implement comments fully

Current --comments behavior inserts a placeholder.

  1. Define required giscus repository and category configuration.
  2. Decide global versus project override precedence.
  3. Validate configuration before rendering or Git operations.
  4. Render the real giscus integration only when requested.
  5. Escape every inserted attribute.
  6. Fail early with an actionable message when configuration is incomplete.
  7. Keep default artifacts comment-free.
  8. Document GitHub Discussions prerequisites.
  9. Test comments off, correctly configured, and misconfigured.
  10. Remove every promise of comments until it works end to end.

2.2 Implement the promised GitHub authentication flow

  1. Specify credential discovery precedence.
  2. Preserve authenticated gh as the preferred path.
  3. Distinguish interactive TTY and noninteractive execution.
  4. Prompt only in an interactive terminal.
  5. Provide stable, machine-readable errors in CI.
  6. Validate credentials before repository mutation.
  7. Never echo tokens.
  8. Never persist token-bearing remote URLs.
  9. Align init, help, README, and runtime behavior.
  10. Test authenticated gh, configured fallback, missing credentials, invalid credentials, and noninteractive execution.

2.3 Validate TTL

  1. Use one parser for deploy and publish.
  2. Accept only finite positive integers.
  3. Reject zero, negative, fractional, mixed, and non-finite values.
  4. Use the configured default only when TTL is omitted.
  5. Do not let zero accidentally mean permanent.
  6. Validate defaultTtlDays in configuration.
  7. Use an injected clock for expiry tests.
  8. Print the effective expiry.
  9. Verify that redeploy keeps the stable URL and moves expiry forward.
  10. Document the exact rule in help.

2.4 Correct privacy language

  1. Remove "public-by-link" wording.
  2. State that the path is hard to guess and marked noindex.
  3. State that the backing repository is public.
  4. State that repository visitors can enumerate document folders and manifest metadata.
  5. Show the warning in deploy help and output.
  6. Document that sensitive plans should remain local.
  7. Snapshot-test the disclosure text.

Configuration and theme lane

2.5 Validate configuration instead of swallowing errors

  1. Distinguish absent, malformed, inaccessible, and semantically invalid config.
  2. Use defaults only when the file is absent.
  3. Produce stable diagnostics for all other failures.
  4. Define a versioned configuration contract.
  5. Ship a JSON Schema if manual editing remains supported.
  6. Validate before saving.
  7. Write atomically.
  8. Preserve unrelated valid settings during targeted updates.
  9. Validate after the editor closes.
  10. Test every failure class.

2.6 Make unknown themes explicit

  1. Require the theme directory to exist.
  2. Distinguish a missing theme from an optional missing asset.
  3. List available themes in errors.
  4. Preserve documented defaults only inside a real theme.
  5. Validate constrained layouts.
  6. Test built-in themes, user overrides, invalid names, missing optional layouts, and invalid slots.
  7. Fail resolution before a plan is written with an unusable theme.

Document and persistence lane

2.7 Make agent-authored plans Markdown-only

  1. Keep direct trusted HTML ingestion for explicit callers.
  2. Make write-plan author Markdown.
  3. Remove or deprecate HTML from the agent-capture setting.
  4. Keep existing stored HTML documents readable and deployable.
  5. Provide migration diagnostics for old planFormat: html configuration.
  6. Make resolve return a Markdown path for plans.
  7. Update theme authoring templates.
  8. Test legacy HTML documents and new Markdown plans.

2.8 Copy to the repository root

  1. Resolve the Git root.
  2. Copy to <git-root>/.planloft/plans/.
  3. Fall back to the current directory only outside a Git repository.
  4. Print when fallback occurs.
  5. Define overwrite behavior explicitly.
  6. Preserve exact raw source.
  7. Test root, nested directory, worktree, no-origin repository, and non-Git directory.

2.9 Fix schema identity

  1. Correct the planlof typo in the schema $id.
  2. Choose a stable versioned schema URL.
  3. Assert the exact identity in tests.
  4. Align README, package, and source references.
  5. Confirm the schema is in the tarball.

2.10 Align runtime and schema validation

  1. Reject present-but-empty metadata strings.
  2. Apply the same rule to title, slug, kind, theme, and status.
  3. Continue allowing omission.
  4. Normalize whitespace before validation.
  5. Define heading-based title inference explicitly.
  6. Run shared fixtures through runtime and JSON Schema validation.
  7. Test CLI flags and JSON sources through the same fixtures.
  8. Keep unknown-field rejection.
  9. Version the schema when the accepted document language changes.

Phase 2 gate

  • Every gap has a regression test.
  • Publication inputs are validated before Git or GitHub effects.
  • Configuration corruption cannot masquerade as defaults.
  • Plan capture cannot lose metadata.
  • Runtime and JSON Schema fixtures agree.
  • Privacy and security wording matches reality.

Phase 3 - Add the skills installation experience

3.1 Define three installation products

CLI-only

Provides the executable, themes, schemas, renderer, store, and publication behavior.

npm install -g planloft
pnpm add -g planloft
bun add -g planloft

Skill-only

Provides only write-plan instructions. It does not install the executable, hooks, themes, runtime assets, or plugin metadata.

npx skills add hatim-s/planloft --skill write-plan
pnpm dlx skills add hatim-s/planloft --skill write-plan
bunx skills add hatim-s/planloft --skill write-plan

The CLI is a prerequisite for a functioning skill.

Full plugin

Provides the one skill, plan-mode hook backstop, plugin metadata, and the appropriate runtime/package integration.

3.2 Publish paired recipes

# npm + Codex
npm install -g planloft
npx skills add hatim-s/planloft --skill write-plan -g -a codex

# pnpm + Codex
pnpm add -g planloft
pnpm dlx skills add hatim-s/planloft --skill write-plan -g -a codex

# Bun + Codex
bun add -g planloft
bunx skills add hatim-s/planloft --skill write-plan -g -a codex

Document -a claude-code for Claude Code and omission of -g for project scope. Reserve -y for CI/noninteractive examples.

3.3 Version skill sources

  • Support the repository shorthand for latest development.
  • Verify a release-tagged GitHub URL for reproducible installation.
  • Test that each release tag contains exactly the intended skill.
  • Never imply that npm package versioning automatically pins a GitHub-sourced skill.

3.4 Run the installer matrix

Test:

  • npx, pnpm dlx, and bunx.
  • Codex and Claude Code.
  • Project and global scope.
  • Symlink and --copy installation.
  • CLI absent and CLI installed.
  • Release-tagged and latest source.
  • List, add, update, remove, and reinstall.

Assertions:

  1. Exactly one skill is discovered.
  2. The installed name is write-plan.
  3. Installed content matches the release tag.
  4. The target agent discovers it after reload.
  5. planloft resolve works with the CLI installed.
  6. Missing CLI produces an actionable prerequisite message.
  7. Skill installation never claims hooks were installed.

3.5 Migrate existing skill installations

Document removal of stale copies:

npx skills remove save-doc
npx skills remove planloft-preview
npx skills remove planloft-copy
npx skills remove planloft-deploy
npx skills add hatim-s/planloft --skill write-plan

Cover global/project scope, Codex/Claude targets, copy/symlink installations, full plugin upgrades, and manual cleanup when the installer cannot locate old files.

Do not retain discoverable deprecated skill stubs.

3.6 Consider a first-party setup command later

Only after the external installer route is stable, evaluate:

planloft setup --agent codex
planloft setup --agent claude-code

Do not build this in the first release if it would duplicate unstable external installer internals.

Phase 4 - Deepen the public Node interface

Do not freeze exact method signatures before interviewing the intended callers and settling error semantics.

4.1 Command-knowledge module

Concentrate command purpose, categories, defaults, examples, effects, and safety notes. Let CLI help, documentation, the skill, and tests consume the same interface.

4.2 Application module behind the CLI seam

Move operation behavior out of Commander handlers. The CLI adapter should only parse arguments, call the application module, format returned results, and select an exit code.

Requirements:

  • No console.* below the CLI adapter.
  • No process.exitCode below the CLI adapter.
  • No process-argument parsing below the CLI adapter.
  • Operations return structured values.
  • Failures use stable categories.
  • Validation occurs before effects.

4.3 Validated configuration module

Concentrate parsing, defaults, validation, project overrides, diagnostics, theme resolution, and persistence. Give CLI, library, renderer, publisher, and tests one consistent configuration interface.

4.4 Document persistence module

Unify direct hoisting, agent write-direct capture, canonical source serialization, metadata preservation, index mutation, replacement, copy lookup, and removal.

4.5 Publication module

Concentrate TTL policy, authentication acquisition, privacy disclosure, comment configuration, rendering, manifest behavior, and host invocation. Keep GitHub Pages as an adapter satisfying the publication interface rather than the owner of every policy.

4.6 Interface-design checkpoint

Resolve:

  1. First-class callers: CLI, Node scripts, agents, CI.
  2. Pure versus local-effect versus external-effect operations.
  3. Required structured results.
  4. Stable error categories.
  5. Async behavior.
  6. cwd and Planloft home injection.
  7. Deterministic clocks and filesystem testing.
  8. Real adapter seams versus speculative abstraction.
  9. Compatibility for existing free-function exports.
  10. Versioned public types versus implementation details.

Phase 4 gate

  • CLI and Node callers use the same implementation.
  • Application modules never format terminal output.
  • Phase 2 semantics are represented in the public interface.
  • Compatibility exports are tested.
  • Structured results contain no secrets.
  • Publication can be tested without a live GitHub mutation.
  • Packed declarations expose only intentional public types.

Parallel work lanes

After Phase 0, these lanes can execute simultaneously:

  • Skill deletion, write-plan, and manifests.
  • Command knowledge and CLI help.
  • Publication contracts.
  • Configuration and themes.
  • Document persistence and schemas.
  • External skills installer experiments.
  • Public-interface caller discovery.

Convergence rules:

  • Skill and help converge before installer testing.
  • Contract lanes converge before the public interface freezes.
  • Skill, contract, installer, and migration work converge before Release 1.
  • Release 1 semantics stabilize before Release 2 publishes the deeper interface.

Risks and mitigations

Existing installations retain removed skills

Mitigation: provide explicit removal commands and verify update behavior for project, global, copy, symlink, Codex, Claude, and plugin installations.

Skill installation is mistaken for full installation

Mitigation: publish a capability matrix and require the CLI in every skill-install recipe.

Help becomes another drifting documentation surface

Mitigation: back help, README checks, skill references, and tests with one command-knowledge module.

Contract repairs accidentally become breaking surprises

Mitigation: document TTL, config, Markdown capture, privacy, and schema changes in one migration guide and release them before freezing the deeper Node interface.

Public interface exposes implementation accidents

Mitigation: finalize repaired behavior first, interview callers, and make the application interface the shared test surface.

GitHub publication leaks sensitive content

Mitigation: describe the public repository accurately, retain explicit deploy authorization, never log credentials, and advise keeping sensitive plans local.

Explicit non-goals

  • Do not create replacement micro-skills.
  • Do not duplicate full CLI documentation inside write-plan.
  • Do not imply that skill installation installs the CLI or hooks.
  • Do not invent npm skills, pnpm skills, or bun skills commands.
  • Do not ship placeholder comments behavior.
  • Do not let TTL zero accidentally mean permanent.
  • Do not silently recover from malformed configuration.
  • Do not describe a public GitHub repository as access-controlled.
  • Do not expose current CLI handler side effects as the permanent Node interface.
  • Do not release based only on source metadata; inspect the packed artifact and fresh consumer installs.

Completion criteria

The roadmap is complete when:

  1. Planloft ships exactly one semantic skill.
  2. planloft help fully teaches the CLI.
  3. All ten contract gaps are repaired and tested.
  4. npm, pnpm, and Bun CLI installation works from the public registry.
  5. npx, pnpm dlx, and bunx install exactly write-plan for Codex and Claude.
  6. Existing users can remove stale skills safely.
  7. The CLI and Node library share deep application modules.
  8. Configuration, persistence, and publication semantics are centralized.
  9. GitHub Pages publication accurately communicates visibility and expiry.
  10. Both release artifacts pass isolated consumer, package, plugin, and live publication verification.
