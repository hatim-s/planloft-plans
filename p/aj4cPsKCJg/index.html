The new package is a useful experiment in giving a coding agent typed workflow primitives instead of asking it to edit flat workflow JSON. The idea is sound for a trusted expert building a small workflow, but the current implementation is not safe to run unattended against production automations. It can build code that passes the local checks, accept invalid workflow semantics, replace an existing graph, and deploy a version other than the one it inspected.

I recommend keeping the approach, but stopping short of autonomous save and deploy. The first release should support linear workflows and IF_ELSE branches, require an explicit production gate, validate against the platform before every write, and pass a semantic test suite before deployment.

The current package proves that generated TypeScript can produce workflow-shaped JSON. It does not prove that the workflow is correct, safe to run, or safe to deploy.

What the approach actually does

“Executable workflow” refers to executing TypeScript during workflow authoring. The package does not execute the generated automation. It does not contain the scheduler, queue, worker runtime, connector execution engine, or workflow state store.

The end-to-end path is:

  1. workflow init creates a local project, packs the current package, installs it, writes Pi settings, and copies platform credentials. See packages/workflow-code/src/cli/init.ts:10-93.
  2. An external Pi coding agent edits src/workflow.ts. The package has no model client, retry policy, turn limit, cost budget, or structured model-output contract. The agent policy is in packages/workflow-code/agent/SYSTEM.md:1-6.
  3. workflow build finds the nearest tsconfig.json, runs tsc --noEmit, then imports and runs the source module. See packages/workflow-code/src/cli/files.ts:13-40.
  4. workflow.node(...) returns a deferred step. Typed proxy objects represent future platform outputs. See packages/workflow-code/src/node.ts:48-112 and packages/workflow-code/src/reference.ts:34-76.
  5. workflow.define(...) executes the step closures, builds flat native nodes and edges, and returns JSON. See packages/workflow-code/src/define.ts:3-15.
  6. workflow save either creates a new automation or updates one when the definition contains an ID. See packages/workflow-code/src/cli/workflow-command.ts:17-35.
  7. workflow deploy reads the saved workflow, posts an unversioned deploy request, reads the deployed definition, and compares graph fields. See packages/workflow-code/src/platform/workflows.ts:102-112.

The public API exposes node, condition, schema overrides, and lookup narrowing. It does not expose faithful loops, scopes, error paths, parallel fan-out, retries, or other native control-flow structures. See packages/workflow-code/src/workflow.ts:9-58.

What works

The package has several good decisions that should survive the redesign.

  • Generated declarations cover 14,578 connector resources and give the agent useful app, action, input, and output names. Runtime catalog loading is lazy by app. See packages/workflow-code/src/generated/manifest.json:1081-1083 and packages/workflow-code/src/catalog.ts:15-31.
  • The graph rejects duplicate steps and IDs, invalid first-node placement, unreachable steps, and references to producers that are unavailable on the current branch. See packages/workflow-code/src/graph.ts:29-68.
  • Branch output availability is intersected across both IF_ELSE arms, so a later node cannot consume an output that only exists on one path. See packages/workflow-code/src/condition.ts:39-47.
  • Mutations are not blindly retried. The package reads create, update, and deploy results back after writing. See packages/workflow-code/src/platform/client.ts:26-49 and packages/workflow-code/src/platform/workflows.ts:71-112.
  • Requests stay on one configured /api/ origin, redirects are rejected, each request has a 30-second timeout, and HTTP error bodies are not printed. See packages/workflow-code/src/platform/client.ts:32-49.
  • The README is honest that generated TypeScript is trusted code. Credential files are created with mode 0600 and excluded from npm packaging. See packages/workflow-code/README.md:13-17 and packages/workflow-code/src/platform/config.ts:31-38.
  • The focused test suite passes: 33 tests, 170 assertions, zero failures. The strict TypeScript check and production build also pass in the current working tree.

These are real strengths. They reduce accidental mistakes, but they do not cover the production risks below.

Correctness findings

C2. The graph model is not faithful to the platform

The public builder creates ordinary linear nodes and two-arm IF_ELSE nodes. Every non-terminal node receives one next exit, and every node is assigned fallbackMode: 'STOP'. See packages/workflow-code/src/graph.ts:52-68.

That does not match the platform's native control-flow model. The platform defines LOOP, BRANCH, SCOPE, and related edge semantics in packages/defs/src/workflow/types.ts:9 and apps/platform/src/modules/flow/transformers/flowTreeToEntityDefNodesAndEdges.ts:287-303.

The generated catalog makes the mismatch visible:

  • loop_for_each, loop_for, and loop_while are typed as ordinary ACTION nodes in packages/workflow-code/src/generated/apps/loop.d.ts:82-88.
  • node.ts copies that catalog type directly into the native node at packages/workflow-code/src/node.ts:87-96.
  • BREAK and CONTINUE resources therefore have no loop scope to target.
  • Existing error paths, retries, fallbacks, and parallel behavior cannot be expressed through NodeOptions, which only contains ID, title, connection, and trigger fields. See packages/workflow-code/src/node.ts:11-18.

This is more than a missing convenience API. The native types are narrower than the platform model in packages/workflow-code/src/native.ts:2-35, so TypeScript can report success while the graph means something different from the developer's intent.

The first fix is to derive the authoring model from the platform's canonical workflow types. Do not hand-maintain a second partial model.

C3. Local success does not mean the workflow is valid

workflowDefinition checks that name is a nonblank string and that nodes and edges are arrays. It does not inspect node or edge contents. See packages/workflow-code/src/platform/workflows.ts:11-29.

The platform tests explicitly save { nodes: [], edges: [] } and treat that as valid input. See packages/workflow-code/src/_tests_/platform.test.ts:13-20 and packages/workflow-code/src/_tests_/platform.test.ts:98-120.

A direct probe confirmed that the boundary accepts an empty graph. Another probe built a scheduled workflow with delay_for input { duration: 0 }, even though the generated connector schema requires a positive duration. The probe emitted the invalid value unchanged.

The repository already exposes a strict workflow validation endpoint at packages/network/src/generated/workflow-definition-rest-api/workflow-definition-rest-api.ts:2028-2044. The new package does not call it before save or deploy.

Required validation should cover:

  • Exactly one valid trigger and the required terminal or return behavior.
  • Unique node and edge IDs.
  • Existing edge endpoints.
  • Allowed native node and edge types.
  • Required inputs, JSON Schema constraints, patterns, enums, and numeric limits.
  • Required return nodes and callable output contracts.
  • Connection ownership and availability.
  • Trigger compatibility with the graph.
  • Cycle and scope rules.
  • Platform size and execution-budget limits.

Local validation should remain for fast feedback, but the platform validator must be authoritative.

C4. Deployment races with concurrent edits

deployWorkflow reads the current definition, posts {} to the deploy route, then compares the deployed graph with the definition it read. See packages/workflow-code/src/platform/workflows.ts:102-111.

The normal platform client pins deployment to _workflow.version in apps/platform/src/modules/workflows/hooks/useDeployWorkflow.tsx:57-62. The package does not.

A failure sequence is straightforward:

  1. Agent A reads version 10.
  2. Agent B saves version 11.
  3. Agent A deploys without a version.
  4. Version 11 becomes active.
  5. Agent A's readback may match version 11 and report success, even though it never validated or intended to deploy that graph. If the readback differs, the wrong version is already active.

Deployment must send the expected version and fail closed on a conflict. It should then verify the exact deployed version and deployment state, not only the graph shape.

H1. Existing workflows are replaced, not preserved

updateWorkflow retains current top-level metadata, then replaces nodes and edges with the generated definition. See packages/workflow-code/src/platform/workflows.ts:86-100.

There is no command to import an existing workflow as TypeScript, no graph diff, and no partial-update model. The README says the retained ID is needed for later edits, but the initial source template has no ID and no separate state file. See packages/workflow-code/README.md:106-123 and packages/workflow-code/src/cli/init.ts:67-76.

The package also cannot represent several existing native node fields. A valid update can therefore remove or change:

  • Trigger configuration.
  • Return envelopes and alternate returns.
  • Runtime connection settings.
  • Custom schemas.
  • Fallback modes and error paths.
  • Existing control-flow scopes.
  • Platform metadata not included in the local NativeWorkflow type.

The current readback check proves that the newly generated graph was stored. It does not prove that the old workflow's intended contract was preserved.

An update flow needs an importer, a three-way diff, explicit replacement approval, and a durable project-to-workflow ID mapping.

H2. Mutations are ambiguous and not idempotent

Create posts a definition without an idempotency key. Update and deploy also have no operation ID. See packages/workflow-code/src/platform/workflows.ts:71-112.

If the server commits a write and the response is delayed beyond the 30-second timeout, the client cannot tell whether the mutation succeeded. Retrying create can produce a second automation. Retrying update or deploy can repeat an operation against a changed state.

The CLI also writes local output only after the remote mutation returns. See packages/workflow-code/src/cli/workflow-command.ts:22-35. A disk or permission failure after a successful POST leaves the remote workflow changed while the command reports failure.

Use idempotency keys for create, update, and deploy. Persist the operation receipt before retrying. Treat a timeout as “unknown outcome” until the operation can be reconciled by ID.

H3. Copied output references can silently become empty objects

Output values are empty-object proxies. Only a string get trap returns another proxy or the hidden reference address. See packages/workflow-code/src/reference.ts:45-55.

A direct probe confirmed this behavior:

const original = producer.output;
const copied = { ...original };

copied serializes as {} rather than a {{ producer.outputs }} expression. Direct access such as producer.output.permalink works, but spread, object assignment, destructuring, and similar operations erase the reference identity.

This failure is dangerous because every existing success signal can remain green:

  • Typecheck passes.
  • Graph construction passes.
  • Save and readback pass.
  • Deploy can pass.
  • Runtime receives {} or an empty value instead of the referenced output.

The reference type should either be a branded non-spreadable object with tests, or the API should reject copying at the type and runtime boundary. The simplest repair is to make spread impossible and add regression tests for object spread, Object.assign, destructuring, JSON.stringify, and nested references.

H4. The checked source is not the executed source

readWorkflow runs tsc and then imports the original path in a separate operation. See packages/workflow-code/src/cli/files.ts:28-40.

There is a time-of-check to time-of-use gap. An editor or second agent can change the source or an imported dependency between typechecking and execution. The changed code runs without a new check.

Generated source also has no execution timeout, memory limit, process boundary, network policy, or filesystem policy. It runs with the user's OS permissions and can read the copied .cookie, environment variables, local files, and network. The README calls this trusted code, which is accurate but leaves the safety burden with the user. See packages/workflow-code/README.md:13-17.

The second problem is determinism. A TypeScript module can use time, randomness, network data, environment variables, filesystem state, or imported side effects. Identical source does not guarantee identical JSON.

Typecheck and execute one immutable snapshot. For agent-generated code, use a sandbox with no platform credentials, restricted networking, a wall-clock timeout, memory and process limits, and an explicit output channel.

H5 and H6. Type safety is useful but overstated

Generic output types such as workflow.node<CustomerObject>(...) are erased before serialization. The README says this directly at packages/workflow-code/README.md:55. The model can choose a structurally plausible T that the connector never returns.

Generated JSON Schema types also omit constraints that TypeScript cannot express. The delay type is a plain number at packages/workflow-code/src/generated/apps/delay.d.ts:1-13, so the positive minimum in the connector schema is not enforced at authoring time.

Catalog generation catches conversion errors and emits never for failed inputs or unknown for failed outputs. It records the failure but exits successfully. See packages/workflow-code/scripts/catalog.ts:90-102 and packages/workflow-code/scripts/catalog.ts:148-180.

The current manifest contains 14 known conversion failures across Aweber, Cal, Capsule CRM, Eventbrite, Freshdesk, GiftUp, and HubSpot. See packages/workflow-code/src/generated/manifest.json:1121-1205.

Typechecking is still useful, but the system should not call a schema type “validated.” Catalog failures need an explicit allowlist and owner, or generation should fail.

Security and trust findings

C1 and C5. The agent has code execution and production authority

The agent prompt says, “After a successful build, save and deploy the automation unless the user asks otherwise.” See packages/workflow-code/agent/SYSTEM.md:3.

That collapses four different actions into one default:

  1. Execute model-written local code.
  2. Persist a tenant resource.
  3. Activate a trigger.
  4. Potentially run external side effects.

The catalog includes privileged actions, including on-premises command execution and impersonation. A compromised prompt, malicious source file, or mistaken model decision can reach those actions with the user's credentials.

workflow schema request can issue an authenticated GET or POST to any caller-selected /api/ path on the configured origin. It is intended for schema discovery but has no route allowlist or read-only policy. See packages/workflow-code/src/platform/schemas.ts:64-98.

The platform client accepts HTTP origins as well as HTTPS, so credentials can be sent without transport encryption if a caller supplies an HTTP host. See packages/workflow-code/src/platform/client.ts:13-23.

The immediate policy should be:

  • Never auto-deploy from the default agent prompt.
  • Require a separate validate, save, and deploy approval boundary.
  • Pin production deployment to a reviewed version.
  • Keep generated source in a credential-free sandbox.
  • Do not copy .cookie into generated projects by default.
  • Allowlist schema request routes and methods.
  • Require explicit approval for privileged connector categories and production credentials.

Scalability and operations

Graph construction grows quadratically

Graph.add scans all existing nodes to detect duplicate IDs and copies the full available-output set for every node. See packages/workflow-code/src/graph.ts:29-37 and packages/workflow-code/src/graph.ts:64-68.

A local benchmark against the built package produced:

Linear nodes Construction time
1,000 15.05 ms
2,000 51.14 ms
4,000 225.99 ms
8,000 1,131.18 ms

Doubling the node count multiplied construction time by about five. The cause matches the implementation: duplicate detection is O(n²), and the available-token set copies add another O(n²) term.

define then clones the completed graph through JSON.parse(JSON.stringify(...)), temporarily doubling memory. See packages/workflow-code/src/define.ts:9-14. Nested conditions add more set copies and intersections in packages/workflow-code/src/condition.ts:29-47.

The current package has no limits for:

  • Node or edge count.
  • Branch depth.
  • Input or output bytes.
  • Available-reference count.
  • Schema nesting depth.
  • Source execution time.
  • Final workflow JSON size.

Use an ID map for O(1) duplicate checks, a more efficient availability representation, and explicit size and depth limits. Reject oversized graphs before work becomes superlinear.

The type catalog and package are large

The current checks measured:

  • Generated source: 62 MB.
  • Built distribution: 65 MB.
  • Packed tarball: 5,613,721 bytes.
  • Unpacked package: 60,521,191 bytes across 2,234 files.
  • Package typecheck: 4.60 seconds on the review machine.

This is workable for one local process, but it affects every scaffold, install, editor session, CI task, and agent iteration. A generated project receives the complete type tree, even when it uses a few connectors.

Consider project-scoped connector declarations or a compiler plugin that loads only referenced apps. At minimum, add artifact-size and typecheck-duration budgets to CI so growth is visible.

Lookup generation is bounded by pages, not time or bytes

Lookup fetching makes up to 1,000 serial requests with 100 records per page. See packages/workflow-code/src/platform/lookups.ts:19-20 and packages/workflow-code/src/platform/lookups.ts:57-84.

At the 30-second request timeout, 1,000 failed page requests could take about eight hours and 20 minutes. The client buffers whole request and response bodies, and lookup code stores every page signature and every discovered key. See packages/workflow-code/src/platform/client.ts:35-47.

Add an aggregate deadline, maximum response bytes, maximum result count, maximum page count based on business needs, and a visible partial-failure receipt. Do not hold every page signature in memory when the page offset already provides a stronger pagination identity.

Generated workflows can express unbounded runtime work

The generated types allow unrestricted loop limits and loop_while conditions. Delay duration has no maximum, and delay-until accepts an arbitrary date. See packages/workflow-code/src/generated/apps/loop.d.ts:32-88 and packages/workflow-code/src/generated/apps/delay.d.ts:1-33.

The authoring API does not expose the platform's retry, timeout, rate-limit, circuit-breaker, bulkhead, or resource-budget fields. The agent can therefore build a workflow that typechecks but has no defensible runtime ceiling.

The platform runtime is outside this repository, so this audit cannot certify queue or worker scalability. It can certify that the new package does not require or preserve explicit runtime budgets. Add default limits for steps, loop iterations, delay duration, async fan-out, workflow wall time, retries, and variable size. Require explicit approval to raise them.

Model usage is expensive and poorly bounded

The latest recovery report selected 369 previously blocked or incomplete cases. It records 6,054 complete assistant turns, 181 unique Pi attempts, 526,942,259 total tokens, and $18.03 in cost. Twenty-five provider transport failures were retried and rebuilt. See packages/workflow-code/.evals/recovery-20260923-005120/REPORT.md:43-50.

That is not necessarily a bad cost for a recovery run, but it shows why the package needs explicit budgets. Add:

  • Maximum turns and tool calls per workflow.
  • Input, output, cache, and reasoning token limits.
  • Spend limit per case and per tenant.
  • Retry count with exponential backoff and jitter.
  • A circuit breaker for provider transport failures.
  • Concurrency limits by tenant and provider.
  • A resumable operation state that does not repeat completed work after a transport failure.

Evaluation evidence

The tests prove local mechanics, not business correctness.

The focused suite passed 33 tests across graph construction, conditions, schema conversion, lookups, credentials, injected types, and mocked platform routes. The direct probes and source review show why semantic coverage is still missing.

The latest recovery run reports:

  • 369 of 369 cases built.
  • 289 saved and read back.
  • 160 deployed.
  • 157 platform TEST runs completed.
  • 86 platform TEST runs succeeded.
  • Zero cases had a machine-readable semantic oracle.

See packages/workflow-code/.evals/recovery-20260923-005120/REPORT.md:9-31.

An earlier 39-brief run built 34, saved 26, completed 17 supplied native fixtures, and had only two briefs pass all supplied semantic assertions. Only 14 briefs had complete assertion coverage. External writes and notifications were mocked, and runtime completion did not prove delivery or persistence. See packages/workflow-code/.evals/solution-briefs-run/report.md:5-20.

This is the most important test gap. “Built,” “saved,” “deployed,” and “TEST completed” are transport and lifecycle signals. A release corpus needs expected records, messages, external calls, side-effect counts, timing, and negative cases.

Release readiness

The source build is not enough to call the package releasable.

  • pnpm --filter @unifyapps/workflow-code run build passes, but dist is generated locally and there is no prepack build gate. See packages/workflow-code/scripts/build.mjs:1-11 and packages/workflow-code/package.json:26-33.
  • npm pack --dry-run succeeds, but the package is 5.6 MB compressed and 60.5 MB unpacked.
  • npm ci --dry-run fails because package-lock.json omits json-schema-to-ts and transitive dependencies. The repository uses pnpm, but the package is designed around npm commands during init.
  • Package-focused Biome lint reports 11 errors. Root pnpm lint also fails and includes unrelated monorepo failures, but the package itself does not have a passing lint gate.
  • PR CI runs workspace TypeScript and tests, but not this package's build, pack, install, CLI smoke test, or semantic evaluation. See .github/workflows/pr.yml:15-43.
  • The npm publish workflow does not include @unifyapps/workflow-code. See .github/workflows/publish-npm-packages.yml:4-13 and .github/workflows/publish-npm-packages.yml:58-77.
  • The package has no load benchmark or benchmark script.

A release candidate should be built from a clean checkout, packed, installed into a clean project, and exercised through the public CLI before publication.

Remediation plan

Phase 0. Contain production risk

  1. Remove “save and deploy” from the default agent prompt. Require separate commands and explicit approval.
  2. Pin deploy to the reviewed version and verify that exact version and deployment state after activation.
  3. Call the platform validator before save and again before deploy.
  4. Reject direct JSON inputs in the autonomous path until they pass the same deep validation as TypeScript output.
  5. Do not copy .cookie into new projects. Read credentials from the environment or a secret manager.
  6. Run generated source in a credential-free sandbox with no arbitrary network access, a wall-clock timeout, and memory limits.
  7. Allowlist schema request paths and reject mutating routes.

Phase 1. Make generation correct

  1. Replace NativeWorkflow with a generated or shared contract derived from the platform API.
  2. Build faithful primitives for linear steps, IF_ELSE, loops, scopes, returns, error paths, and parallel branches.
  3. Preserve unsupported existing fields by default. Require an explicit replace operation before removing them.
  4. Add workflow import and a three-way diff for updates.
  5. Store workflow ID, last saved version, and operation receipts in project state rather than expecting the agent to edit an ID into source.
  6. Add idempotency keys and structured conflict handling.
  7. Make output references non-copyable, or reject copy operations with a clear error.
  8. Validate the compiled workflow against connector JSON Schema and platform graph rules.
  9. Write local output atomically after a durable remote receipt.

Phase 2. Add semantic and load gates

  1. Build a release corpus with machine-readable expected outcomes.
  2. Include destructive actions, missing fields, wrong connections, wrong branches, duplicate sends, missing returns, and reference-copy mistakes.
  3. Require zero critical failures and an agreed pass threshold on fully asserted cases.
  4. Add benchmarks for 100, 1,000, 5,000, and 10,000 nodes across linear and branching graphs.
  5. Record build time, peak memory, package size, model turns, tokens, spend, retries, save latency, deploy latency, and semantic pass rate.
  6. Add graph, payload, lookup, source-execution, and model budgets.

Phase 3. Make release repeatable

  1. Choose one supported package-manager path and keep its lockfile current.
  2. Make lint pass and add a package-specific lint script.
  3. Add prepack build and a clean pack/install smoke test.
  4. Add the package to CI and the publish workflow.
  5. Fail catalog generation on unapproved conversion failures.
  6. Add artifact-size and typecheck-duration budgets.
  7. Publish only from a clean, tagged commit with passing semantic evaluation.

Acceptance criteria for an autonomous pilot

Do not enable unattended deployment until all of these are true:

  • Every deploy request names the exact reviewed version.
  • Every save and deploy passes platform semantic validation.
  • Every create, update, and deploy operation is idempotent and reconcilable.
  • Existing workflow changes show an explicit diff before replacement.
  • Generated code runs without access to platform credentials.
  • Model turns, retries, spend, and concurrency are bounded.
  • Runtime loops, delays, retries, fan-out, and variable size have enforced limits.
  • The release corpus has complete semantic assertions and passes the agreed threshold.
  • Graph and package load budgets pass in CI.
  • A clean pack installs and runs through the public CLI.
  • Lint, typecheck, tests, build, pack, and install checks all pass.
  • The npm publish path is explicit and reproducible.

Final recommendation

Keep executable TypeScript as the authoring model. It is more legible for an AI agent than hand-edited workflow JSON, and the current graph checks are a good start.

Do not ship the current package as an autonomous production generator. First remove automatic deployment, define a real trust boundary, use the platform as the semantic authority, pin concurrent writes, preserve existing workflows, and replace lifecycle metrics with business-outcome tests. Once those changes are in place, the approach is worth piloting on small, linear, IF_ELSE workflows with human approval.
