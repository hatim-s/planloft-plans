PR #28885 audit — reposition the typed workflow authoring DSL

Reposition PR #28885 (feat(llm-tools): add typed workflow authoring DSL, +11,245/−131) so the well-designed DSL core can merge without shipping its eval harness, AI-SDK runtime dependency, and convention violations inside @unifyapps/llm-tools.

Verdict

The approach architecture is right; the positioning is not merge-ready.

Right direction — keep as-is:

  • One-directional coupling: the experiment imports production (FlowBuilder, NodeStore, serializer); production imports nothing back. Nothing registers on any MCP surface, so product blast radius is zero.
  • Host-owned identity: opaque handles for resources, connections, and options; the model never sees native workflow JSON; IDs, pills, and mappings come from the production serializer path.
  • Two-pass compile with schema-revision suspension (compiler.ts) is a clean compiled | suspended | failed contract with no serialization against stale schemas.
  • Changelog entry, WORKFLOW_TOOLS.md cross-link, and colocated __tests__/ follow convention.

Findings, severity-ordered:

  1. Eval/agent harness inside src/ of a shipped package: pi-runtime/ (20 files: CLIs, Pi session runner, live UAT/alert evaluators) and the attest/ project (with nested attest/attest/ and RESULTS.md) sit in src/tools/workflow/code-authoring/. Repo convention puts runnable non-tool code in package-root scripts/; no package checks an eval harness into src/; attest has no precedent on origin/main.
  2. Dependency placement: @earendil-works/pi-coding-agent and typebox are runtime deps of @unifyapps/llm-tools but are used only by the harness — the first AI-SDK dependency in any package manifest in the repo. tsx was added although every existing CLI runs via bun. Lockfile grew 880 lines.
  3. Production module patched for the experiment: workflowUpdate/flowBuilder.ts gained a .default ?? Module ESM/CJS interop shim solely because the harness runs under node+tsx; its two production importers never needed it.
  4. Ambiguous placement: on origin/main the PR creates src/tools/workflow/ holding only the experiment, while branch fix/workflow-edit-flow-hardening restructures llm-tools to make workflow/ the real module home (and moves flowBuilder.ts into workflow/update/), guaranteeing conflicts. The three sibling experiment PRs use three different layouts, undermining comparison.
  5. CLAUDE.md violations: 19 files exceed the 200-line cap (validator.ts 750, alertEvaluator.ts 684, platformProof.ts 676, context.ts 612, parser.ts 509); both folders exceed the 7–8-item rule; two barrel index.ts files were added where the convention is a sibling entry file (workflowUpdate.ts pattern).
  6. Hygiene: root .gitignore gained package-specific artifact paths (belongs in packages/llm-tools/.gitignore); the README hardcodes machine paths (/Users/hatim.shakir/.nvm/...) and live run IDs; the changelog entry sits above the deeper src/tools/changelog/; no docs/specs/ design record exists for a novel language (the approaches A–F note was never pushed to any ref).

Actions

  1. Split the PR: keep the DSL core (lexer, parser, validator, typeGenerator, context, schemaLifecycle, canonicalBuilder, compiler, provider, diagnostics, types, __tests__/) in llm-tools; move pi-runtime/ and attest/ to a repo-root workspace package tools/workflow-code-authoring-evals/ with src/ + evals/attest/, mirroring the sibling pi PR's tools/pi-workflow-runtime/ layout.
  2. Move @earendil-works/pi-coding-agent, typebox, tsx, and the three workflow:code:* scripts into that harness package, restoring @unifyapps/llm-tools to a zero dependency diff.
  3. Revert workflowUpdate/flowBuilder.ts to the origin/main version; if node+tsx interop is still needed, wrap it inside the harness package.
  4. Resolve the workflow/ placement against fix/workflow-edit-flow-hardening: rebase onto it and land as workflow/code-authoring/ if it merges first, otherwise rename to the flat convention (src/tools/workflowCodeAuthoring/ with a sibling entry file instead of index.ts); align the semantic and pi experiment PRs on the same core/harness split.
  5. Decompose oversized core files toward the 200-line cap: validator.ts into structure / input-option / ref-and-control-flow / condition modules; context.ts into build / refresh / catalog; parser.ts into statements / expressions; canonicalBuilder.ts into topology / mappings / conditions; harness files after the move.
  6. Sweep hygiene: move the root .gitignore entries into package-local .gitignore; replace machine paths with a stated Node version requirement; move run IDs and results into attest/RESULTS.md; relocate the changelog entry to src/tools/changelog/; add a docs/specs/ design note recording why this approach beat mutation tools, a typed SDK, and code-mode scripts.
