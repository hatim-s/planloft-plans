Automation Coder should not inherit the Workflow Planner and Workflow Builder skill lists wholesale. Those agents manipulate or describe workflow internals. Automation Coder writes TypeScript and delegates node ids, indexes, groups, edge wiring, and JSON serialization to the compiler. The right comparison is therefore about retained behavior, not copied files.

The current cut is directionally right but incomplete. It removed most structure-specific knowledge and replaced several overlapping skills with smaller TypeScript-facing ones. Five practical domains are still missing: analytics choice and reporting, callable contracts, platform users and assets, runtime error policy, and performance controls.

Move business and runtime knowledge. Leave JSON shape and graph construction with the compiler.

What moved

files-and-attachments and storage-records moved directly. Both describe runtime contracts that remain true regardless of whether the author writes JSON or TypeScript.

code-by-unifyapps, code-node-selection, and utilities were consolidated into data-transforms-and-code. This is a good decision. The Coder needs one route from native operation to code node, plus sandbox, bindings, and result rules. It does not benefit from three overlapping entry points.

sql-query-builder became sql-nodes. The rewrite keeps connection, table, column, bind, and result-envelope discovery while dropping planner annotations and Builder payload examples.

dates-and-time was split out of the utility material because date absence, milliseconds, unit selection, and silent "now" behavior are costly runtime traps. node-inputs-and-pills collects dynamic schemas, nullable values, mapped arrays, and output envelopes around the DSL and compiler.

The five additions

1. Analytics and reporting

Combine the old analytics-and-reports implementation knowledge with the storage-vs-analytics choice. The skill should answer one question first: does this flow need records or a computed result? Then it should require live report, projection, filter, paging, export, and output-envelope reads through existing tools.

2. Callable contracts

The core prompt has the syntax. A skill should carry the deeper contract: who calls the automation, which trigger owns each input, which node owns the response, what every branch returns, whether the call waits, and which deployed version callers can reach.

3. Platform users and assets

This needs a narrow Coder rewrite. It should distinguish platform users, teams, roles, connections, projects, and automation metadata from app-object records. The mistake to prevent is choosing Storage for platform metadata or guessing fields on standard-entity outputs.

4. Error handling

Keep this behavioral. The skill should help Coder decide whether to retry, continue, compensate, or fail, then express the decision through supported TypeScript constructs and operation options. It should never teach raw fallback edges.

5. Performance

This can stay short. Teach batching over per-record callable loops, cache only when staleness is acceptable, bound database and Storage reads, and test with representative volume. Do not include topology diagrams or JSON option blocks.

Proposed final assignment

The target is 11 Automation Coder skills:

  • Existing: data-transforms-and-code, dates-and-time, files-and-attachments, node-inputs-and-pills, sql-nodes, storage-records
  • Add: analytics-and-reports, callable-contracts, platform-users-and-assets, workflow-error-handling, workflow-performance

Names may differ, but ownership should not overlap. Each new skill should use the current MCP services, point to live tenant schemas over memorized examples, and avoid workflow JSON, raw edge construction, group ids, node indexes, or legacy pill strings.

Implementation order

  1. Add analytics-and-reports, including the Storage-versus-Analytics decision.
  2. Add callable-contracts and platform-users-and-assets; both prevent workflows that compile but integrate with the wrong runtime contract.
  3. Add workflow-error-handling and workflow-performance as concise TypeScript-facing guides.
  4. Run the existing skill sync and deployment path.
  5. Reload Automation Coder (Hatim), read back the deployed skill ids and normalized contents, and compare them with source.
  6. Evaluate one focused case per new skill. A saved workflow is not proof; inspect the real test output and deployed state where deployment is requested.

The result keeps Automation Coder small without making it naive: the compiler owns structure, while the agent owns operation choice, runtime contracts, and business behavior.
