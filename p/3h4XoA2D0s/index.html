PR 28885 typed workflow authoring audit

Turn PR #28885 into a reviewable experiment that keeps workflow identities and native serialization host-owned without building a second workflow platform inside llm-tools.

Do not merge commit 2387c5ac62a3b3bef6b48c3946ae384acbe60964 in its current form. The trust boundary and production-builder lowering are in the right direction. The compiler validation, source layout, runtime placement, dependency boundary, and review state are not merge-ready.

  1. Preserve the parts of the approach that are already sound.

    • Keep opaque resource, connection, and lookup-option handles. The model should never receive native IDs or author WorkflowDefinition JSON.
    • Keep the optimistic schema-revision handshake in compiler.ts and context.ts. A changed selector or workflow context should suspend compilation and require a new pass.
    • Keep lowering through FlowBuilder, NodeStore, workflowTreeToXyNodeEdges, and transformToWorkflowDefinition in canonicalBuilder.ts. This is the strongest part of the design because the product still owns node IDs, edges, groups, indexes, defaults, mappings, and serialization.
    • Keep the four-tool Pi allowlist, in-memory sessions, one-time artifact handles, _at-only cookie extraction, and persisted UAT execution checks.

  2. Reposition the PR as an experiment before changing more code.

    • The head is one commit, 58 changed files, 11,245 additions, and 131 deletions. It is open as a non-draft feat PR, but no shipped product or MCP registration imports the new module. The only external entrypoints are three manual package scripts.
    • Move Pi, Attest, demo, alert, local-runtime, and live-UAT code out of packages/llm-tools/src/tools/workflow/code-authoring. Use an evaluation-only location such as packages/llm-tools/evals/workflow-code-authoring or a separate workspace package.
    • Keep only a reusable authoring core and the production-builder adapter in shipped source. If this is meant to become a product feature now, add the actual caller, authentication boundary, session lifecycle, and artifact consumer in the same architectural plan before calling it production code.
    • Mark the PR as draft or replace it with a small stack until the intended runtime is explicit.

  3. Replace the custom JSON Schema validator before trusting status: "compiled".

    • validator.ts:703-705 treats every non-literal expression as a match for const and enum. I reproduced a dynamic field constrained to const: "email" compiling with { invalid: true }, zero diagnostics, and that object in the serialized workflow.
    • The same validator implements oneOf as anyOf, approximates if/then/else, ignores several standard constraints, and has its own incomplete $ref handling. This is a correctness boundary, not a formatting concern.
    • Reuse the package's existing Ajv and RJSF schema machinery under tools/plugins/automation-inputSchemaValidation, including its schema expansion and pointer handling. Keep only workflow-reference availability and output-to-input assignability as authoring-specific checks.
    • Add focused tests for non-literal const and enum values, exact oneOf behavior, if/then/else selection, nested and escaped $ref paths, defaults, and additionalProperties. The reproduced invalid program must fail before an artifact handle is issued.

  4. Reuse shared workflow schema primitives instead of forking them.

    • schemaLifecycle.ts and context.ts reimplement dynamic-field discovery, payload interpolation, schema injection, and builder-local operation dispatch that already exist in resolveNodeDynamicSchemas.ts and tools/plugins/automation-inputSchemaValidation.
    • Extend the shared dynamic-schema loader for workflow-specific operations such as getCallableResponse and getNodesByResourceName. Do not keep two parsers for DynamicSchemaField metadata or two interpretations of schema paths.
    • Move the hard-coded Groovy checks from validator.ts:192-294 and typeGenerator.ts:85-99 into a resource-contract registry owned by the provider or catalog adapter. A generic compiler should not know code_by_unifyapps_groovy, and evaluation-specific prompt repairs should not define the core architecture.
    • Keep the authoring path independent from cleanup and JSON repair. Sharing schema primitives does not require routing compiled output through cleanup_automation_config.

  5. Split the implementation along real ownership boundaries.

    • Twenty new TypeScript files exceed the repository's 200-line limit. validator.ts is 750 lines, context.ts is 612, parser.ts is 509, canonicalBuilder.ts is 480, and provider.ts is 471.
    • The root folder has 14 files and pi-runtime has 20, both beyond the repository's folder-size rule. The two new index.ts files are generated barrel exports despite the repository rule against them.
    • Separate the language AST and parser, catalog/context state, schema resolution, platform lowering, Pi adapter, and evaluation harness. Import concrete modules directly.
    • Run Oxlint as a gate after the split. The current command completes with 20 warnings, including max-depth, max-params, and curly violations that the repository rules explicitly call out.

  6. Remove evaluation dependencies and dead code from the production package boundary.

    • @earendil-works/pi-coding-agent and typebox are production dependencies even though only the manual evaluation runtime imports them. Put them in the isolated evaluation package or its development dependencies.
    • pnpm-lock.yaml changes by 880 additions and 128 deletions and also changes unrelated peer resolutions such as jiti, yaml, and Babel. Regenerate a minimal lockfile after the package split.
    • pi-runtime/localRuntime.ts has no caller outside its barrel export. Remove it if it is obsolete. If local execution remains required, do not execute model-authored JavaScript in an in-process node:vm guarded by a regular expression. Use a disposable process or container with explicit resource limits.
    • If the local runtime remains, align its numeric operators with the compiler. canonicalBuilder.ts:429-438 emits GT, GTE, LT, and LTE, while localRuntime.ts:187-200 checks GREATER_THAN, GREATER_THAN_OR_EQUAL, LESS_THAN, and LESS_THAN_OR_EQUAL.

  7. Make provider failures return compiler diagnostics instead of escaping the tool call.

    • compileWorkflowSource catches builder lowering and serialization errors, but loadRequiredControls and resolveContextualSchemas can reject outside those catches. The Pi compile tool also awaits the compiler without its own error boundary.
    • Convert catalog, system-node, schema-lookup, and option-lookup failures into typed diagnostics with the current context handle when retry is safe. Pass abort signals into provider requests instead of checking only before and after network calls.
    • Add one test for a rejected workflow-schema request and one for a rejected system-node lookup. Neither should crash the Pi session or lose actionable context.

  8. Separate implementation proof from historical evaluation prose.

    • The focused suite passes locally with 22 tests and 80 assertions. Package typecheck, Biome, and formatting also pass.
    • The changelog still claims two tools, 17 focused tests, three scenarios, and GPT-5.5, while the current runtime has four tools, 22 focused tests, larger UAT suites, and Luna/Terra results. Update or replace the stale entry.
    • Remove personal absolute Node paths from README.md. Use package scripts and an explicit supported Node range.
    • Move Attest configuration and results out of src. Commit sanitized, immutable result summaries or machine-readable artifacts for claims that reviewers are expected to trust. The current 30-case and alert raw reports live only in ignored local directories, so the PR cannot independently reproduce those historical claims.

  9. Split the work into a reviewable stack.

    • First PR: extract or extend shared schema and production-builder adapter primitives with no behavior change.
    • Second PR: add the restricted language, authoring context, compiler, and focused correctness tests.
    • Third PR: add the remote provider and Pi adapter in the evaluation-only package.
    • Fourth PR: add Attest and live-UAT cases plus sanitized evidence. Keep live workflow creation and deployment out of ordinary unit-test and CI paths.

  10. Clear every merge gate on the final core PR.

    • The current GitHub test and typecheck jobs pass, but vulnerabilities-sca-scan fails. Its log names postcss 8.5.26 and CVE-2026-45623 with CVSS 9.1. That version already exists in the base lockfile, so the failure blocks the PR but does not prove the Pi dependencies introduced the vulnerability.
    • The Wiz summary reports four medium and five low SAST findings, and the SAST check is neutral. Triage the actual findings before merge rather than treating the neutral conclusion as a pass.
    • No human review has been submitted. The automated Codex review did not run because repository review credits were exhausted.
    • Re-run the focused tests, package typecheck, Biome, Oxlint with zero warnings, formatting, full affected package tests, SCA, and SAST on each split PR. Require one workflow-platform owner and one llm-tools owner to approve the core compiler PR.

  11. Merge only when the architecture has one source of truth and the compiler fails closed.

    • Accept the direction when invalid schema values cannot return compiled, dynamic-schema semantics come from shared code, resource-specific guidance is registered outside the core, the production dependency graph excludes the evaluation agent, and a real caller or explicit experiment boundary owns the lifecycle.
    • Close or keep the current PR as an evaluation record if those conditions are intentionally out of scope. Do not merge the present 11,000-line branch as the production implementation.

Risks

  • Splitting the PR can accidentally change serialized workflow shape. Freeze a small set of canonical workflow fixtures around linear flow, IF join, named branches, connections, lookup options, and dynamic-schema suspension before moving files.
  • Reusing shared schema code may expose differences between RJSF form semantics and backend strict validation. Record those differences explicitly and make backend strict validation the final acceptance gate.
  • Moving Pi and live UAT out of src can make experiments less convenient. Preserve the three package commands as thin wrappers into the evaluation package so the developer workflow stays one command.
