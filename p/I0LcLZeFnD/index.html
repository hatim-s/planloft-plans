Attest agent and eval setup UX

Source-grounded product and interaction proposal for getting from an existing agent to a useful first evaluation in under five minutes.

Audit date: 7 August 2026
Audited commit: c0f946329af72c0edc6c85f9822778f8ff2a52db
Recommendation: keep Attest file-first, add a guided CLI setup layer now, and add a visual editor only after the safe config-mutation foundation exists.

Executive answer

Attest already has a complete runnable loop, but not yet a complete setup experience.

  • attest init [directory] creates a fixed sample project. It is not interactive and exposes only --force.
  • Users configure their real agent by editing attest.config.yaml or JSON. One config has exactly one agent target: a CLI command or an HTTP URL.
  • Users create an “eval” by manually defining a suite, its cases or JSONL dataset, and one or more metrics. The product currently calls this a suite, while many users will naturally ask to “add an eval.”
  • The generated quickstart and contract specifications document the primitives. There is no root README, dedicated setup guide, agent add, eval add, config validator command, connection tester, or step-by-step wizard.
  • A pasted cURL command is not supported today. The current HTTP runner always sends POST, Content-Type: application/json, and the Attest request envelope to one URL. It cannot import arbitrary headers, auth, request bodies, or response extraction rules.

The best UX is a progressive system with four equivalent entry points:

  1. Guided setup — attest init for the first project and attest agent add / attest eval add afterward.
  2. cURL import — paste an existing request; Attest parses it without executing it, redacts secrets, asks for input/output mappings, then performs an explicit connection test.
  3. Composable flags — complete non-interactive commands for automation and AI coding agents.
  4. Direct config editing — preserve YAML/JSON plus schema completion as the power-user path.

Product language and information architecture

Use this user-facing hierarchy:

Project
├── Agents        How Attest calls the system under test
├── Evals         A goal-oriented group of test cases and scoring criteria
│   ├── Cases     Inputs plus optional expected values
│   └── Scorers   Assertions, judges, or custom code
└── Runs          Immutable executions, evidence, comparisons, and reports

Keep suite as the v1 config/runtime term if necessary, but label it Eval in onboarding and explain it once: “An eval is stored as a suite in attest.config.” Do not make a new user learn “suite,” “case,” “metric,” “judge,” and “run” before they see value.

Step 1 — project

Ask only for a project name, defaulting to the directory name. If a config exists, switch to additive mode and say exactly which file will change.

Step 2 — connect an agent

Recommended choice labels:

  • Paste a cURL command — “Import an API request you already know works.”
  • HTTP endpoint — “My endpoint already accepts Attest’s request envelope.”
  • Local command — “Run a script or binary for each case.”
  • Start with an example — “Explore a passing demo before connecting my agent.”

Ask advanced settings only after the basic target is understood. Timeout, retries, concurrency, environment forwarding, and trace options belong under “Customize reliability and evidence.”

Step 3 — prove the connection

Do not save an untested setup by default. Show:

  1. The sample input Attest will use.
  2. The redacted request or exact CLI argv.
  3. A clear Test connection action.
  4. The response and extracted output.
  5. Contract/transport diagnostics separated from agent-reported errors.

Offer Save without testing for offline endpoints and CI-only environments, with a visible “Untested” status.

Steps 4–6 — create the first eval

Ask for the outcome in plain language before exposing metric types:

What should a good answer do?

Suggested presets:

  • Match an expected value → generates equals, contains, or JSON Schema assertions.
  • Follow a rubric → generates a judge metric, then asks for provider/model and the secret environment variable.
  • Use tools correctly → offers tool-called, order, argument, and failed-tool assertions; explains traces are required.
  • Run my own scorer → generates an executable or HTTP metric target.
  • Record outputs only → valid zero-scorer eval for exploration; prompt the user to add scoring after the first run.

Step 7 — review before write

Show a unified diff of every generated or changed file. Default actions:

  • Save and run eval
  • Save only
  • Go back
  • Cancel without changes

Never silently replace an existing config, and never hide generated adapters.

Additive commands

# Guided
attest agent add
attest eval add
attest case add smoke
attest scorer add smoke

# Inspect and repair
attest config validate
attest agent test support-api --case smoke/refund-policy
attest doctor

# Automation / AI-agent friendly
attest agent add support-api --from-curl request.sh --no-test --json
attest eval add smoke --agent support-api --cases cases.jsonl --scorer correctness --json
attest config validate --format json

Every interactive operation needs a complete flag/JSON equivalent. --json should return the files changed, warnings, next required environment variables, and the next suggested command.

Command behavior principles

  • Interactive only when stdin is a TTY; otherwise fail with the exact missing flags.
  • --yes accepts safe defaults, but never approves network calls or secret persistence implicitly.
  • --dry-run prints the proposed file diff and performs no write or request.
  • Config writes must be atomic and preserve comments/formatting.
  • Existing files changed since load must be rejected with a recovery command.
  • Errors should identify the stage: parse, config, connection, contract, scoring, or persistence.

cURL import: recommended design

Yes, but import it — never execute it

Treat cURL as a familiar interchange format, not as a shell script. Parse a strict subset:

  • URL and --url
  • -X / --request
  • -H / --header
  • -d, --data, --data-raw, and --json
  • basic auth declarations, converted to secret references

Reject or require explicit manual handling for shell expansions, command substitutions, file uploads, @file bodies, client certificates, proxies, cookies, redirects, and arbitrary cURL config files. Never invoke a shell and never execute copied text.

Import sequence

  1. Parse locally.
  2. Detect and redact credentials before any output or persistence.
  3. Explain unsupported flags with line/column locations.
  4. Infer content type and parse JSON bodies when possible.
  5. Ask which body fields come from case.input, case.params, or constants.
  6. Ask how to extract output and errors from a sample response.
  7. Show the redacted normalized request and response mapping.
  8. Ask before making the first request.
  9. Save only environment variable names, not secret values.
  10. Add parser and secret-redaction evidence to the config diff, not the secret itself.

Durable connector model

Do not overload the current native HTTP target. Preserve it as the clean Attest-envelope transport and add an explicit mapped-request connector.

config_version: 2
project: support-agent

agents:
  support-api:
    type: http_request
    request:
      method: POST
      url: https://api.example.com/chat
      headers:
        content-type: application/json
        authorization:
          env: AGENT_API_TOKEN
          prefix: 'Bearer '
      json:
        message: '{{ case.input.question }}'
        locale: '{{ case.params.locale }}'
    response:
      output_path: $.choices[0].message.content
      error_path: $.error.message

evals:
  smoke:
    agent: support-api
    cases:
      - id: refund-policy
        input: { question: How do refunds work? }
    scorers: [answer-quality]

This is a north-star shape, not a request to rewrite v1 immediately. For the first implementation, a cURL importer can generate a visible local adapter that speaks the existing Attest envelope. That delivers user value while the mapped-request contract and migration story are designed deliberately.

Four UX options

Option Strength Cost/risk Recommendation
Improve docs only Fast, no runtime change Still makes users translate their system into contracts manually Necessary baseline, not sufficient
Interactive CLI wizard Meets developers where they start; easy to version and test Needs safe config mutation and careful non-TTY behavior Build first
cURL importer Fastest path from a working API to value Secret safety, mapping semantics, and unsupported shell syntax require rigor Build with the wizard after parser design
Dashboard setup wizard Best discoverability and response-mapping preview Requires authenticated writes, CST round-trip, stale-write protection, and more UI states Build after CLI/config foundations

The CLI wizard and future dashboard should call the same pure setup engine: inputs → diagnostics → proposed patches → optional connection test → atomic commit. This prevents two onboarding products from drifting.

Compatibility and migration strategy

Phase A — no schema break

  • Make attest init interactive in TTY mode while retaining today’s sample via attest init --example.
  • Add attest config validate, attest agent test, and attest eval add that write the existing single-agent v1 schema.
  • Add JSON Schema hints and a focused “Connect your agent” guide.
  • Correct contract docs that imply the deferred editor already exists.

Phase B — cURL import on v1

  • Parse cURL without execution.
  • Generate an inspectable connector/adapter file plus the existing CLI agent target.
  • Store only secret environment variable names.
  • Provide request/response mapping fixtures and redacted dry-run output.

Phase C — named agents and evals

  • Introduce config v2 only when users need multiple named agents or direct mapped HTTP targets.
  • Load v1 as an implicit default agent and keep it fully supported.
  • Provide attest config migrate --to 2 --dry-run; never auto-rewrite.
  • Let attest run <eval> --agent <agent> make comparisons explicit.

Phase D — visual setup

  • Reuse the setup engine behind loopback-authenticated write APIs.
  • Add agent and eval empty states to attest view.
  • Require diff preview, atomic CST patching, and stale-file refusal before enabling writes.

Required states and error recovery

State Message and recovery
cURL parsed, secret found “A bearer token was found. Choose an environment variable name; the token will not be saved.”
Unsupported cURL option Name the flag and offer “Edit request manually” or “Show supported options”
Endpoint unreachable Preserve all entered data; offer retry, edit URL, or save untested
Response is non-JSON Show bounded redacted preview; allow text output or an adapter
Output path matches nothing Show response tree and let the user select a value
Trace scoring without traces Explain which scorer needs trace data and offer output-only scoring
Existing config conflict Show exact paths and a diff; never suggest --force as the first recovery
Missing secret at run time Name the environment variable and platform-appropriate export command without printing a value

Accessibility and trust requirements

  • Full keyboard operation; visible focus; no arrow-key-only choice controls.
  • Progress announced as text, for example “Step 3 of 7 — Test connection.”
  • Visible labels and examples; placeholders are never the only labels.
  • Status is expressed by icon/text as well as color.
  • Redacted request/response previews work at 200% zoom and can be copied without hidden secrets.
  • Every external request and process execution has a plain-language confirmation and target preview.
  • Telemetry records at most command/category counts; never cURL text, URLs, headers, bodies, filenames, prompts, outputs, or secrets.

Documentation plan

Ship docs in the same order users encounter the product:

  1. Root README: install → connect agent → create eval → first result in under five minutes.
  2. “Connect your agent” guide with tabs for cURL, native HTTP, CLI, and framework adapters.
  3. “Create your first eval” guide using goal-oriented scoring presets.
  4. Config reference generated from the runtime schema.
  5. Agent and metric protocol specifications for advanced integrations.
  6. Troubleshooting organized by setup stage and error code.

The current generated quickstart, handoff, and contract specs should remain, but the contract reference should not be the primary onboarding journey.

Success metrics

  • Median time from install to first real-agent result: under 5 minutes.
  • At least 80% unassisted completion in five-developer cold testing.
  • At least 90% of supported JSON cURL fixtures import without manual config editing.
  • Zero secret values written to config, logs, telemetry, generated diffs, or error reports.
  • Users can identify whether a failure is configuration, connectivity, contract, agent, or scorer-related without source inspection.
  • The entire setup flow is keyboard-complete and usable at 200% zoom.

Immediate product decisions

  1. Adopt Agent → Eval → Cases + Scorers → Run as the user-facing model.
  2. Build the guided CLI before the visual editor.
  3. Treat cURL as a safe import format and never execute pasted shell text.
  4. Preserve native Attest HTTP as a simple, explicit contract; model arbitrary APIs separately.
  5. Delay config v2 until named agents or direct request mapping are implemented, and provide an explicit migration command.
  6. Cold-test the flow with users who have an existing agent and a working cURL command—not only users willing to write an adapter.
