UAC DSL guide

Read this guide to author an automation in TypeScript and inspect the workflow JSON it produces. The standalone project contains the compiler, DSL declarations, operation metadata, examples and this reference. Platform validation has been removed from the extraction.

Start with one compilation

Unzip uac-dsl-20261008.zip, open the project directory, and run:

npm ci
npm run build
npm run compile -- examples/callable-return.ts output.json

Open examples/callable-return.ts next to output.json. The source declares a trigger, an operation and a return. The JSON contains a START node, an ACTION node and a STOP node. Output references become {{ nodeId.outputs.path }} strings, and the compiler connects the nodes with edges.

Read in this order

  1. Learn the flow entry point and triggers, then operations and output references.
  2. Read conditions and control flow to understand how blocks become graph edges.
  3. Compare the four complete source/JSON examples. They cover a callable return, a branch inside a loop, protected steps with an error path, and compilation without platform policy checks.
  4. Use the helper tables and implementation map as a reference when extending the DSL.

The archive includes 140 further examples in examples/library/, with matching JSON in compiled/library/. Use npm run examples -- --all to regenerate all 144 pairs. The compiler was checked for exact JSON parity against the original UAC compile path for all 140 library examples.

Language reference

This project compiles the UAC TypeScript DSL into workflow JSON. A flow describes operations and their nesting. The compiler writes the flat nodes and edges arrays, node IDs, ordering indices, and group IDs.

The compiler reads the TypeScript AST. It does not execute the flow, resolve its imports, call connectors, or run scripts embedded in operation inputs. Only the syntax described here has a compilation rule. A file can be valid TypeScript and still use syntax this compiler cannot translate.

This extraction includes compact connector metadata for compilation, with platform validation, server, and deployment integration removed. It accepts operation names and input payloads without checking their existence or platform schemas. Emitted JSON describes a workflow; compilation does not prove that a platform can run it.

Compile a flow

import { compile, compileFile, Catalogue } from "uac-dsl-compiler";

const { program, workflow } = compile(source, { fileName: "flow.ts" });
const fromDisk = compileFile("examples/callable-return.ts");
const customMetadata = Catalogue.fromOperations([
  { appName: "custom", resourceName: "send", displayName: "Send" },
]);
const custom = compile(source, { catalogue: customMetadata });
const withoutMetadata = compile(source, { catalogue: false });

compile accepts source text. compileFile reads a file; build is its alias. Both return { program, workflow }. program is the nested IR, and workflow is the emitted JSON. The fileName option affects source-text diagnostics. File compilation uses the path it reads.

The CLI accepts an input path and optional output path:

npm ci
npm run build
node dist/cli.js examples/callable-return.ts compiled/callable-return.json

CompileOptions.emit forwards emitter options. indexBase changes the starting index; constantIndex assigns the same index to every node; ignoreEdgeHints ignores IR edge-label overrides. rootGroupId is an emitter fallback, so a parsed program's generated root group ID takes precedence.

The default bundled metadata includes operation display names, selected node types, input schemas and layouts, and connector display names. Catalogue.load() loads it, Catalogue.load(file) accepts a JSON or gzip metadata file, and Catalogue.loadDirectory(directory) reads a platform catalogue arranged as <app>/<resource>.json. Catalogue.fromOperations accepts an array of metadata records and optional connector display names. A missing operation remains compilable.

Compilation applies these transformations after parsing:

  • Fill known operation titles and connector subtitles; retain authored labels.
  • Apply known CALL_INTERFACE_WORKFLOW node types.
  • Generate variable-node input and output schemas from declared or inferred fields.
  • Normalize object schema roots in callable/API triggers and embedded code-node schemas.
  • Wrap bare references in array inputs as identity mapped arrays, and expand mapped whole-object inputs into declared item properties when metadata gives a closed object shape.
  • Normalize bare leaves in named condition inputs triggerInputCondition, filters, where, and conditions to an AND group.

catalogue: false skips metadata-driven titles, types, and variable schemas. Schema-root normalization, named condition normalization, and array handling that derives from authored schemas still run. For a strict parse-to-emit path, use emit(parseFlow(source).program) directly.

The declarations under runtime/ describe the authoring helpers. The examples use @ua/automations. Map that module to runtime/index.d.ts in an authoring project for editor completion. The package also exports the declarations as uac-dsl-compiler/dsl. Either import path works for the AST compiler because it does not resolve imports. Configure your editor's path mapping or use the package export for type completion.

Start a flow

import { automation, callable, op } from "@ua/automations";

export default automation(
  {
    name: "Echo",
    description: "Return the requested message",
    trigger: callable({
      setup: {
        type: "object",
        properties: { message: { type: "string" } },
      },
      result: {
        type: "object",
        properties: { message: { type: "string" } },
      },
    }),
  },
  (t) => {
    return { message: t.message };
  },
);

The default export must be a direct call to automation. The first argument must be an object literal with a name and trigger. The second must be an arrow function or function expression with a block body. Its first named parameter refers to trigger outputs.

Metadata Compilation
name Workflow name; also seeds generated IDs
description Workflow description
settings Workflow settings, carried as a JSON value
trigger A START node

Extra metadata keys have no DSL mapping. A leading line comment on a statement becomes the node's subTitle. An operation's explicit label option takes precedence over the comment.

Module-level constants above the default export can contain JSON literals, arrays, objects, references to earlier module constants, negative numbers, and as assertions such as as const. They are substituted when consumed and do not create nodes. They cannot contain functions, runtime references, helper calls, or computed expressions. Declare one variable per statement inside the automation body.

Triggers

Helper START context Trigger type
callable(config) callables / callables_from_automation CALLABLE
callableApi(config) callables / callables_from_api CALLABLE
schedule(config) schedule / schedule_default SCHEDULED
webhook(config) webhooks / webhooks_default WEBHOOK
appEvent(appName, resourceName, inputs?, opts?) Supplied connector and resource Follows connector

Each config becomes the trigger node's inputs. callable usually carries setup and result. callableApi usually carries endpointType, request, and a response array. These are open payloads, not schemas enforced by this compiler.

appEvent requires literal string names. Its fourth argument can contain connectionId, which becomes context.connectionId. For appEvent, connectors callables, schedule, and webhooks retain their corresponding trigger types. Other connectors use EVENT.

Inside a trigger config, TRIGGER.field refers to that trigger's own output. It resolves to the same node as the automation body's t.field parameter. This is useful for triggerInputCondition.

trigger: callable({
  setup: { type: "object", properties: { mode: { type: "string" } } },
  triggerInputCondition: eq(TRIGGER.mode, "active"),
})

Operations

const result = op("connector", "resource", { input: t.value }, {
  label: "Fetch the value",
  connectionId: "connection-id",
  onError: "CONTINUE",
});

op accepts literal string connector and resource names. Missing inputs become {}. Bind the result to a single identifier when later steps read its outputs. A bare op(...) statement emits the same operation without a binding.

Option JSON mapping
label node.subTitle
connectionId node.context.connectionId
onError node.fallbackMode and node.options.stepError; default STOP
retryConfig node.options.retryConfig
rateLimitConfig node.options.rateLimitConfig
skip: true node.skip: true
nodeType Explicit node.type override

Pass operation options as an object literal. Unknown option keys have no mapping. The declarations describe STOP, CONTINUE, and MANUAL error policies; this compiler does not validate platform semantics for those policies.

The compiler infers these node types before an explicit nodeType override:

Connector/resource Inferred type
callables / callables_call_interface CALL_INTERFACE_WORKFLOW
callables / resource beginning callables_call_automation CALL_WORKFLOW
delay DELAY
break BREAK
continue CONTINUE
stop STOP
Everything else ACTION

retryConfig supports enabled, count, initialDelay, maxDelay, backOffFactor, captureRetries, and filter. Delay fields are milliseconds. rateLimitConfig supports enabled, threshold, duration, unit, waitForNextWindow, key, incrementParameter, and filter. Unit declarations include NANOSECONDS, MICROSECONDS, MILLISECONDS, SECONDS, MINUTES, HOURS, and DAYS. Both configurations pass through without range or schema checks.

For an entire object-valued payload, pass a reference directly:

op("connector", "resource", prepared.result.payload);

The compiler emits an identity wrapper rather than inserting the pill string directly:

{ "ua:type": "identity", "source": "{{ <prepared-id>.outputs.result.payload }}" }

It does not merge connector defaults into this payload. SELF substitution runs for leaf operations; do not depend on it in scope or connector-backed loop inputs. Object spreads have no compilation rule.

Values and output references

Inputs can contain strings, finite numeric literals, booleans, null, arrays, and objects. Object keys must be identifiers or quoted strings. Ordinary input objects also support shorthand properties such as { result }, which read the binding as an output reference. Parentheses and as assertions do not change the value.

DSL Compiled value
step.result "{{ <step-id>.outputs.result }}"
step.items[0].id "{{ <step-id>.outputs.items[0].id }}"
step["@odata_nextLink"] "{{ <step-id>.outputs.@odata_nextLink }}"
step "{{ <step-id>.outputs }}"
`Hello ${t.name}` "Hello {{ <trigger-id>.outputs.name }}"
nodeId(step) Bare generated node ID, without a pill wrapper
SELF in a leaf operation's inputs That operation's own node ID

Computed property indices such as step.items[i] are unsupported. Numeric indexing is a literal path, not JavaScript evaluation. String bracket access produces a dotted platform path, so a string key containing a dot does not receive special path escaping.

Template placeholders can read node outputs or runtime roots, or interpolate an earlier module constant. They cannot perform arithmetic, call helpers, or contain a nested template literal. A plain string beginning with = is a platform formula. To refer to outputs inside a formula, interpolate references in a template:

{ value: `=SUM(${t.count},1)` }

The compiler writes the formula text and pills. It does not evaluate the formula or check which functions the platform supports.

Runtime roots

Root Compiled pill root Available declarations
RUN __RUN__ executionId, rootExecutionId, parentExecutionId, workflowId, workflowVersion, userId, customerId, applicationId, workflowStartTime, currentTime, uaTraceId, locale, timezone
USER __USER__ id, name, username, locale, contactDetails.email, contactDetails.phoneNumber, customProperties
ENV __ENV__ Tenant environment variables by property name
TRIGGER Generated START node ID Trigger payload fields

These roots remain open references. For example, RUN.userId emits {{ __RUN__.outputs.userId }}. USER denotes the execution user; this compiler does not determine who that user is.

Mapped arrays

A concise .map on an output reference creates a platform mapped-array value:

{ records: t.rows.map(row => ({ id: row.id, title: row.title })) }

{
  "records": {
    "ua:type": "mappedArray",
    "source": "{{ <trigger-id>.outputs.rows }}",
    "items": {
      "id": "{{ <trigger-id>.outputs.rows[0].id }}",
      "title": "{{ <trigger-id>.outputs.rows[0].title }}"
    }
  }
}

The [0] path is the platform's placeholder for an element, not a request to map only the first element. Use one named callback parameter and a concise body. Block callback bodies and a literal-array source are unsupported. The compiler does not infer whether the source actually returns an array.

Joined strings and embedded scripts

["line one", "line two"].join("\n") compiles to one string. Its source must resolve to a compile-time array. The default separator is a comma. Non-string array values are JSON-stringified. A runtime output's .join is unsupported.

In an object value under a key named code or script, an unresolved template placeholder remains ${...} as written. Resolved node/runtime references still become pills. This preserves embedded language interpolation such as Groovy GString expressions. This behavior follows the key name and applies to nested values under that key; it is not restricted to one connector. Tagged templates such as String.raw are unsupported.

Conditions

Condition helpers produce filter values, not JavaScript booleans.

Helper Platform operator Arguments
eq, ne EQUAL, NOT_EQUAL property, value
gt, gte, lt, lte GT, GTE, LT, LTE property, value
contains, notContains CONTAINS, NOT_CONTAINS property, value
startsWith, endsWith STARTS_WITH, ENDS_WITH property, value
isIn, notIn IN, NOT_IN property, list value
regex, notRegex REGEX, NOT_REGEX property, pattern
exists, missing EXISTS, MISSING property 
and(eq(t.status, "OPEN"), or(gt(t.score, 80), exists(t.owner)))

A leaf eq(t.status, "OPEN") becomes:

{
  "property": "{{ <trigger-id>.outputs.status }}",
  "filter": { "operator": "EQUAL", "value": "OPEN" }
}

and and or create { "operator": "AND" | "OR", "filters": [...] }. An if, while, or branch arm automatically wraps a lone leaf in an AND group. Named condition inputs can also receive that normalization during compilation.

! only negates a leaf with an exact operator opposite. Supported pairs are eq/ne, contains/notContains, isIn/notIn, regex/notRegex, and exists/missing. There is no general not helper. !gt(...), !and(...), JavaScript comparisons, and &&/|| have no mapping. Platform behavior for missing values can differ from JavaScript comparisons.

Use a runtime list output with isIn or notIn when targeting the platform. Literal list input can be emitted by this validation-free extraction, but compilation does not establish its runtime membership behavior.

Control flow

If and else

if (gt(t.score, 80)) {
  op("connector", "priority_action", { id: t.id });
} else {
  op("connector", "normal_action", { id: t.id });
}

This emits an IF_ELSE node using if_else / if_else_condition. Its inputs is the condition group itself. Its yes edge is if / yes; its no edge is next / no. The compiler wires both arms to the next statement. else if compiles as a nested IF_ELSE in the else arm.

For each

for (const row of t.rows) {
  op("connector", "consume", { id: row.id });
}

A standard list loop emits LOOP, context loop / loop_for_each, and inputs.listSource. The loop variable reads the loop node's outputs.item.

each(source, options) adds inputs to the loop:

for (const batch of each(t.rows, { repeatMode: "BATCH", batchSize: 50 })) {
  op("connector", "consume_batch", { records: batch });
}

Options such as repeatMode, batchSize, and captureIterations are carried as inputs. They are not checked against a connector schema. Batch syntax alone does not specify parallel execution.

A named loop lets its body and later steps read the loop node's own outputs:

const page = each(t.rows);
for (const row of page) {
  breakIf(eq(page.isLast, "true"));
}
return { lastIndex: page.index };

Declared loops become nodes when consumed by for...of or while. A named loop can expose index, isFirst, isLast, size, or connector-specific outputs; actual fields come from the execution platform.

For connector-backed iteration, the operation is the loop node:

for (const row of each(op("connector", "stream_rows", { source: t.file }))) {
  op("connector", "consume", { item: row });
}

The node has type LOOP and the supplied operation's context and inputs. The operation's connection, retry, rate-limit, error-policy, and skip settings are retained. The outer each options merge into its inputs.

Counted loops

for (let i = 0; i < 10; i++) {
  op("connector", "consume_index", { index: i });
}

This emits loop / loop_for with { start: 0, limit: 10, step: 1, captureIterations: false }. The index variable reads outputs.index.

The ordinary for parser reads numeric start and right-hand limit values. It always emits step 1 and does not interpret the actual comparison or increment operator. Use the shown canonical form. Use range for explicit step or capture settings:

for (const i of range({ start: 0, limit: 10, step: 2, captureIterations: true })) {
  op("connector", "consume_index", { index: i });
}

range works directly in the for...of head. A local declaration initialized with range(...) is unsupported.

While loops

while (gt(t.remaining, 0)) {
  op("connector", "advance", {});
}

This emits loop / loop_while with an inputs.condition group. while (each(condition, options)) adds input options. const more = each(condition, options); while (more) { ... } also names the loop. The compiler does not change runtime values to make the loop terminate.

Break and continue

break and continue emit BREAK and CONTINUE nodes with the target loop ID in inputs.loop. breakIf(condition) and continueIf(condition) add inputs.conditions. They require an enclosing loop.

A labelled loop can be targeted from an inner loop:

outer: for (const row of t.rows) {
  for (const cell of row.cells) {
    continueIf(missing(cell.value), "outer");
  }
}

Keywords break outer and continue outer use the same label mapping. In a branch or scope callback, use breakLoop("outer") and continueLoop("outer") when no condition is needed. These helpers avoid TypeScript's restriction on keyword jumps across function boundaries. Without a label argument, the helpers target the innermost loop.

Multi-way branches

branch([
  { id: "priority", name: "Priority", when: gt(t.score, 80), then: () => {
    op("connector", "priority_action", { id: t.id });
  } },
  { name: "Owned", when: exists(t.owner), then: () => {
    op("connector", "owner_action", { id: t.id });
  } },
], () => {
  op("connector", "default_action", { id: t.id });
});

branch emits BRANCH with arm definitions in inputs.branches. Arms support only id, name, when, and then; then must have a block body. The intended platform behavior is to run the first matching arm. An arm can omit when. IDs default to positional strings "1", "2", and so on.

For each nonempty non-default arm, the compiler inserts a BRANCH_CONDITION node with ID <branch-id>@<arm-id>, unless the body already starts with that node type. Empty arms connect directly to the continuation. A default arm is always present in the emitted arm list; the optional second callback supplies its body. Branch edges have type branch and the arm ID as their name.

Scopes and error handling

try {
  scope(op("connector", "scope_operation", {}), () => {
    op("connector", "first_action", {});
    op("connector", "second_action", {});
  });
  op("connector", "success_action", {});
} catch {
  op("connector", "error_action", {});
}

scope emits a SCOPE node owned by the inline op call. Its body is a child block with a scope edge, and the last body node returns to the scope through next / scope-loopback. The inline operation's connection, retry, rate-limit, and error policy are retained. A scope's label comes from its leading comment; the inline operation's label, skip, and nodeType options have no scope mapping.

A try block protects its first emitted node. That node receives the MANUAL error policy; remaining try statements become its success block and catch statements become its error block. Both paths converge on the statement after the try. To protect several steps as one unit, put a scope first, as above. An empty try has no node to protect and cannot compile.

A catch parameter does not create a runtime error binding. Read an available node output to inspect an error. finally has no mapping and is ignored by the parser, so keep it out of DSL source.

Returning and stopping

Syntax STOP context Inputs
return value callables / callables_return_to_automation { result: value }
return Same {}
respond("name", { body, status, ... }) callables / callables_return_response_to_api responseName plus object fields
stop() stop / stop {}
stop(op(...)) Supplied operation context Supplied operation inputs

Use return for callable results, respond for API response definitions, and stop for event, schedule, or webhook termination. This extraction does not check that a termination form matches the trigger. respond requires a literal response name and an object-literal second argument to carry response fields.

Top-level STOP nodes have no outgoing edge. The parser preserves structural fall-through for nested STOP nodes. A BREAK or CONTINUE node still receives its structural continuation edge; the runtime handles its loop target separately.

Shared bindings and statement labels

let output; output = op(...) reserves a node binding for a later operation. This allows references across nested blocks. If the same declared name receives multiple operation assignments, the compiler creates a workflow variable using variable_by_unifyapps_create_variables; each assignment emits an operation and a variable_by_unifyapps_update_variables node. Later reads use the shared variable rather than one branch's node.

This is a compilation rule for operation results, not general mutable JavaScript. Assignments from literals, arbitrary expressions, or property writes are unsupported. For explicit mutation of scalar/list state, call the platform's variable operations through op.

Labels can name an if, branch, or scope so later steps can reference that statement's outputs. For valid TypeScript, reserve the binding first:

let decision;
decision: if (exists(t.owner)) {
  op("connector", "consume", { owner: t.owner });
}
return { decision: decision.result };

A reserved named loop can also be initialized later with page = each(...). Mixed assignments that attempt to rebind one node ID to incompatible node/loop forms have no compilation rule.

Raw values and lower-level nodes

raw(value) reads a plain JSON value without recognizing condition helpers or mapped-array structures. References and template placeholders inside the value still resolve. Literal pill strings remain strings. Raw objects require explicit key: value properties; shorthand properties and spreads are unsupported there.

op("connector", "resource", {
  unusual: raw({ "ua:type": "custom", source: t.payload }),
});

if (raw(conditionJson)) and while (raw(loopInputJson)) accept existing condition or loop input shapes without rewriting their group structure. each(raw(loopInputJson)) supplies the entire for-each loop input object. Use these only when the desired platform shape is already known. Raw values bypass condition-group normalization. The schema-root, variable-schema, and array-input enrichment passes do not consult raw markers, so raw is not a universal opt-out from later compilation transforms.

There is no nodes(...) DSL helper. Workflow JSON exposes nodes and edges arrays, and the TypeScript library exposes the lower-level Program and Stmt types plus the emitter. To represent custom node fields outside DSL syntax, construct an IR program and call emit; statement extra carries additional JSON node fields. nodeType on op can change a leaf node's type but does not create nested graph structure. raw is a value escape, not an escape that inserts arbitrary graph nodes or edges.

Graph generation

Generated node IDs are deterministic hashes of the workflow name and structural statement paths, including binding names where relevant. Renaming a workflow changes its generated IDs. Moving or inserting statements can change path-derived IDs; do not assume IDs survive arbitrary source edits.

The emitter traverses statements in depth-first order, assigns one-based indices by default, and derives group IDs from parent statement IDs and child-block roles. Edges use priority: 0 and skip: false unless a lower-level representation changes the relevant data.

Structural role Edge type Edge name
Sequence next Absent
Loop body entry loop Absent
End of loop body next loopback
Loop completion next Absent, except an enclosing loopback role
If true if yes
If false next no
Branch arm branch Arm ID
Protected scope entry scope Absent
Scope body return next scope-loopback
Manual success next success
Manual failure error error

An empty child block connects to its continuation where that construct defines one. Fresh leaf nodes emit debug: false, dirty: false, and skip: false. They retain authored context, inputs, error policy, and options. No separate JavaScript runtime graph is produced.

Unsupported syntax and compilation boundaries

Do not use arbitrary helper functions, local computed aliases, destructuring, object/array spreads, dynamic indices, promises, await, JavaScript arithmetic or boolean expressions, switch, do...while, class/function declarations inside the body, or runtime .filter, .reduce, and other array methods. Use DSL nodes, workflow conditions, loop constructs, formulas, and embedded script inputs instead.

The compiler recognizes helper names in source, not imported implementations. Renaming op on import does not rename the parser's helper. Imports supply editor declarations but are not evaluated. Module-level code after the default export is not part of the compiled automation.

Unsupported-syntax errors remain necessary because the compiler needs a defined mapping to JSON. Connector availability, platform schema validity, reference availability at runtime, response compatibility, and graph acceptance are outside this compiler's checks.

Branching and loop control

A for-each loop, an if condition, output references, a connector connection, and callable return.

Source: examples/branch-and-loop.ts. Output: compiled/branch-and-loop.json.

import { automation, callable, each, eq, op } from "@ua/automations";

export default automation(
  {
    name: "Notify active accounts",
    trigger: callable({
      setup: { type: "object", properties: { accounts: { type: "array", items: { type: "object" } } } },
      result: { type: "object", properties: { done: { type: "boolean" } } },
    }),
  },
  (t) => {
    for (const account of each(t.accounts, { captureIterations: false })) {

Where the implementation lives

src/tsparse.ts owns helper recognition, value/reference conversion, and the TypeScript-to-IR rules. src/ir.ts defines statements and child blocks. src/emit.ts derives graph layout and edges. runtime/index.d.ts provides the authoring declarations; runtime/index.js prevents accidental execution of those helpers. The project README describes the compiler API and CLI.

Read source when changing a DSL rule. Update its declarations and this reference together, regenerate paired examples, and inspect the resulting JSON.
