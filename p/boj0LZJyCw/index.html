Attest Local and CLI North Star Roadmap

A source-grounded product, validation, and delivery plan for making Attest the best local experience for humans and agents to create, validate, run, and continuously improve agent evaluations.

Planning date: 7 August 2026
Scope: local files, local execution, CLI and terminal workflows, packaged artifacts, CI, coding-agent interfaces, live-provider validation, and local human review
Explicitly deferred: hosted control plane, accounts, organizations, cloud execution, cloud persistence, browser-based authoring, and cloud collaboration
Authority: this roadmap builds on the ratified CLI v2 North Star contract. Where an older foundation document describes YAML-first v1 behavior, the ratified v2 contract wins.

1. Executive decision

Attest should be built as one local evaluation system with several equally capable operators:

  1. A non-technical domain expert who knows what a good answer looks like.
  2. A developer who can connect a process or endpoint and customize anything.
  3. A coding agent that needs deterministic discovery, schemas, structured errors, and atomic writes.
  4. An unattended agent or CI job that cannot answer prompts and must operate through stable machine contracts.

Those operators must not receive four different products. They should use different interfaces over the same project model, command-request schemas, transaction engine, evaluation runtime, evidence model, and validation rules.

The CLI v2 initiative establishes that common authoring and execution substrate. The next product problem is trust:

  • Does the CLI actually work against real providers, not only scripted test seams?
  • Does an LLM judge agree with qualified humans on this rubric and domain?
  • Can a human review, correct, and adjudicate results without corrupting immutable run evidence?
  • Can Attest measure whether its own onboarding works for humans and coding agents?
  • Can a team use the local artifacts reliably in Git and CI before any cloud product exists?

The North Star is therefore not merely “under five minutes to a passing demo.” It is:

In under five minutes, a human or coding agent can connect a real agent, create a meaningful test, select an appropriate metric, run it, understand every result, and know whether the evidence is deterministic, model-estimated, human-reviewed, or still unvalidated.

2. Product thesis

2.1 The authored model

The ratified v2 hierarchy is normative:

project
├── agents
├── tests
│   ├── direct test cases
│   └── attached datasets
│       └── test cases
├── datasets
├── metrics
└── eval runs
    ├── immutable case attempts
    ├── immutable metric results
    └── linked review and calibration evidence

Important language decisions:

  • Project is the local Attest unit rooted by attest.project.json.
  • Agent is a reusable invocation adapter.
  • Test replaces the v1 suite and binds an agent, cases or datasets, metrics, and run defaults.
  • Metric is the stored technical term for assertions, judges, and executable scorers.
  • Eval is the execution namespace. attest eval run creates an immutable eval run; there is no authored “eval” resource.
  • Review is human evidence linked to a run, case, metric, or comparison.
  • Calibration measures whether a judge metric is trustworthy for a specific rubric, model identity, prompt version, and labeled corpus.

2.2 The trust hierarchy

Attest must never flatten all forms of judgment into an unexplained boolean. Every result should preserve its source and authority:

Deterministic evidence
    exact checks, schemas, executable outcomes, trace invariants
          │
          ├── strongest for facts the system can prove mechanically
          │
Human reference evidence
    blinded labels, pairwise preferences, corrections, adjudication
          │
          ├── ground truth for the defined rubric, with disagreement retained
          │
Calibrated model estimates
    LLM judge results measured against human reference evidence
          │
          ├── scalable estimates with known limitations and provenance
          │
Uncalibrated model estimates
    useful during exploration, never silently presented as established truth

These evidence sources may disagree. Attest should expose the disagreement rather than overwrite one result with another.

2.3 The operator model

Operator Primary entry point What they contribute What Attest must hide until requested
Domain expert interactive CLI and import/export review packets examples, expected outcomes, rubrics, labels, corrections JSON structure, transport envelopes, process semantics
Developer guided commands, flags, request JSON, direct inspection transports, traces, custom metrics, CI policy repetitive boilerplate and unsafe mutation details
Coding agent JSON help, schemas, --from-json, dry run, project hash project inspection, generated resources, repair loops prose scraping, TTY prompts, implicit defaults
CI/unattended agent non-interactive commands and JSON/JSONL output repeatable execution and gating prompts, ambiguous exit codes, mutable hidden state

2.4 Non-goals for this roadmap

  • No cloud dependency is required for authoring, execution, review, or calibration.
  • No browser editor is required.
  • No account, organization, role, or hosted reviewer assignment model is introduced.
  • No live LLM call enters required pull-request CI.
  • No secret value is stored in authored resources, diffs, run bundles, logs, command results, or telemetry.
  • No human label mutates an immutable eval run or destroys an earlier machine verdict.
  • No universal claim is made that one judge model, threshold, or agreement score is valid across domains.
  • No v1 compatibility runtime is carried forward. The v2 break is intentional.

3. Current-state audit

3.1 What already works

Attest already has meaningful runtime foundations:

  • CLI and HTTP agent invocation.
  • Process timeouts, cancellation, retries, evidence caps, and process-tree cleanup.
  • Assertion, executable, HTTP, and LLM-judge metric contracts.
  • OpenAI and Anthropic judge adapter selection through the TanStack AI seam.
  • Structured judge responses, retry handling, recorded attempts, token usage, rationale, raw-response evidence, and content-addressed caching.
  • SQLite run persistence, immutable completed runs, run diffing, JSON and JUnit output.
  • Trace ingestion, trajectory assertions, local dashboard inspection, and self-contained reports.
  • Deterministic conformance, hostile-agent, property, storage, and rendering coverage.

3.2 What the current tests prove

The existing judge tests prove the deterministic machinery around a provider call:

  • Provider-qualified model parsing.
  • Adapter selection.
  • Prompt rendering.
  • Structured-output parsing.
  • Retry after malformed structured output.
  • Timeout and cancellation classification.
  • Provider-error mapping.
  • Cache behavior.
  • Persistence of judge request, attempts, raw response, rationale, and usage evidence.
  • CLI wiring from a judge metric through persistence.

This is valuable. It means the seam is testable and failures are isolated.

3.3 What the current tests do not prove

The current required suite does not prove:

  • That current OpenAI or Anthropic credentials authenticate successfully.
  • That installed SDK adapters still match current provider response behavior.
  • That configured model aliases exist or support the required structured-output operation.
  • That token-usage and provider metadata arrive in the expected form.
  • That a real model follows the rubric reliably.
  • That repeated judgments are stable.
  • That a judge score agrees with qualified human judgment.
  • That the default threshold is meaningful for a domain.
  • That model aliases have not drifted while the cache key remained unchanged.
  • That users can configure a live judge without assistance.

All current judge tests stop before the network:

  • Adapter tests inject a scripted structured-chat executor.
  • Metric tests create an explicitly no-network JudgeClient.
  • CLI integration injects a hand-authored synthetic judge result.
  • The generated quickstart uses deterministic exact assertions, not a live judge.

This is consistent with the repository rule that required CI must not call a live LLM. The gap is that the separately promised scheduled, budget-capped provider smoke lane does not yet exist.

3.4 Human validation status

No implemented contract currently represents:

  • A human review rubric.
  • A review batch or queue.
  • A human label or correction.
  • Reviewer identity or pseudonym.
  • Blinding or randomized candidate order.
  • Multiple reviewers.
  • Inter-rater agreement.
  • Adjudication.
  • Judge-versus-human calibration.
  • A human-approved baseline or release decision.

Human review and judge calibration are explicitly deferred in the existing product decisions and remain backlog work.

3.5 Usability evidence status

Current evidence is functional acceptance, not user research:

  • A technical operator successfully ran the generated quickstart.
  • Browser-controlled checks verified dashboard behavior.
  • The source-grounded setup report identified workflow gaps.

There has not yet been an observed participant study covering representative developers, domain experts, or coding agents. The planned friendly-developer cold test remains necessary but is not broad enough to validate the full North Star.

3.6 Audit conclusion

The correct conclusion is:

Attest has a real provider-capable judge implementation and strong deterministic seam tests. It does not yet have live-provider compatibility evidence, semantic judge-quality evidence, human review, judge calibration, or representative onboarding usability evidence.

5. System contracts required after CLI v2

5.1 Evidence provenance

Every metric result must answer:

  • What produced this result?
  • Which exact metric resource version and content hash were used?
  • Was it deterministic, executable, model-generated, or human-generated?
  • Which inputs and bounded evidence were visible to the evaluator?
  • Which provider, model identity, prompt version, parameters, and attempts were used?
  • Was the result served from cache?
  • Was the evaluator calibrated? If so, against which corpus and human-label snapshot?
  • Has that calibration become stale?
  • Did a human later agree, disagree, or adjudicate the result?

Required provenance additions for judge results:

provider
requested_model
resolved_model_or_revision when supplied
provider_system_fingerprint when supplied
judge_prompt_version
metric_resource_hash
rubric_hash
request_parameters
attempt_count
cache_status
calibration_id or null
calibration_status: draft | valid | stale | rejected

Absence of provider revision metadata must be represented as unknown, not inferred.

5.2 Human review rubric resource

A review rubric is authored and versioned. It is separate from a machine metric because review instructions, label taxonomies, blinding, and reviewer requirements have different semantics.

Minimum fields:

rubric_id
schema_version
name
instructions
target: run | case | metric | pairwise_case
criteria[]
  id
  description
  value_type: binary | categorical | ordinal | continuous | free_text
  allowed_values or range
  required
reviewer_count
blinding_policy
adjudication_policy

5.3 Annotation record

Human annotations are append-only evidence records:

annotation_id
schema_version
batch_id
rubric_id
rubric_hash
target reference
reviewer_id or local pseudonym
presented_candidate_order
labels and scores
rationale
confidence
optional corrected expected value
created_at
supersedes_annotation_id or null

Corrections never edit the original annotation. A new annotation may supersede one with an explicit link.

5.4 Review batch

A review batch freezes:

  • Source run ids and case ids.
  • Selection rule and selection seed.
  • Rubric id and hash.
  • Redaction policy.
  • Blinding policy.
  • Candidate randomization map.
  • Required reviewer count.
  • Review state per item.

Batch states:

draft → open → fully_labeled → needs_adjudication → complete
                 └──────────────────────────────→ complete_with_disagreement

5.5 Calibration snapshot

A calibration snapshot is immutable and content-addressed. It binds:

  • Judge metric resource hash.
  • Rubric hash.
  • Judge prompt version.
  • Provider and requested model.
  • Provider-resolved model metadata when available.
  • Human-label corpus hash.
  • Inclusion and exclusion rules.
  • Number of independent reviewers and adjudication state.
  • Number of judge trials per item.
  • Sampling seed.
  • Metrics and confidence intervals.
  • Creation timestamp.

Changing any bound input makes the snapshot stale. Attest does not silently transfer calibration to a different rubric, prompt, model alias, or dataset.

5.6 Derived decision policy

Machine and human evidence remain immutable. A separate policy produces a current decision:

pass
fail
error
needs_review
insufficient_evidence

Examples:

  • Deterministic assertion failure → fail.
  • Provider timeout → error.
  • Uncalibrated judge used under strict policy → insufficient_evidence.
  • Near-threshold calibrated judge result under human-escalation policy → needs_review.
  • Completed adjudicated human review → policy may derive pass or fail while retaining the machine result.

6. LLM-judge validation strategy

6.1 Four separate test layers

Layer A — deterministic implementation tests

Required on every pull request and fully offline:

  • Prompt construction.
  • Model identifier parsing.
  • Request limits and redaction.
  • Structured response parsing.
  • Retry classification.
  • Timeouts and cancellation.
  • Usage accounting.
  • Cache keys and invalidation inputs.
  • Persistence round trips.
  • Error serialization.

These tests prove implementation correctness, not judge quality.

Layer B — recorded provider-shape replay

Required on every pull request and fully offline after fixtures are reviewed:

  • Sanitized successful OpenAI response shape.
  • Sanitized successful Anthropic response shape.
  • Usage-bearing response.
  • Missing-usage response.
  • Malformed structured output.
  • Rate limit and retry metadata.
  • Authentication error classification.
  • Provider-side model-not-found error.
  • Streaming or SDK-specific edge events when applicable.

These tests detect SDK and parser regressions without spending money. They do not prove current provider availability or semantic quality.

Layer C — live-provider compatibility smoke

Scheduled and manually dispatched; never required PR CI:

  • One minimal OpenAI judge case.
  • One minimal Anthropic judge case.
  • Strict maximum calls, tokens, time, and daily cost.
  • Pinned model identifier where the provider offers one.
  • No sensitive application data.
  • Structured-output success assertion.
  • Evidence persistence assertion.
  • Cache-hit assertion on identical second evaluation.
  • Redaction assertion on stored artifacts.
  • Alert on authentication, model availability, SDK compatibility, or schema failure.

This layer proves that the integration still works today. It should not assert one exact semantic score from a stochastic model.

Layer D — semantic calibration

Opt-in local or scheduled evaluation against human-labeled data:

  • Judge-human agreement.
  • False-pass and false-fail rates.
  • Confusion matrix for categorical labels.
  • Rank correlation for ordinal or continuous outcomes.
  • Mean absolute error where numeric scores are meaningful.
  • Repeated-call variance.
  • Pairwise order consistency.
  • Sensitivity to verbosity, style, and candidate position.
  • Performance by dataset slice and failure category.
  • Bootstrap confidence intervals with a recorded seed.

This layer determines whether a judge is trustworthy for a specific use.

6.2 Adversarial judge-quality cases

Every judge calibration project should include, where applicable:

  • Correct concise answer versus correct verbose answer.
  • Fluent wrong answer versus awkward correct answer.
  • Candidate A/B order swapped.
  • Exact same answer in both positions.
  • Agent output that instructs the judge to award a high score.
  • Agent output that imitates rubric or system-prompt syntax.
  • Long irrelevant preamble before the answer.
  • Missing expected data.
  • Contradictory expected data.
  • Partial trace and malformed optional trace evidence.
  • Same semantic answer with different formatting.
  • Safety refusal when refusal is appropriate.
  • Safety refusal when refusal is inappropriate.
  • Tool result correct but final synthesis wrong.
  • Final answer correct but required tool trajectory wrong.
  • Candidate produced by the same model family as the judge.
  • Inputs with protected or domain-sensitive attributes when the domain requires bias checks.

Research has repeatedly shown that LLM judges can exhibit position and presentation biases. Attest should therefore measure these properties rather than assume the structured response is objective.

6.3 Calibration measures by rubric type

Rubric type Minimum report Optional advanced report
Binary accuracy, precision, recall, false-pass rate, false-fail rate, confusion matrix Matthews correlation, subgroup slices
Categorical macro/micro accuracy, per-class confusion, agreement macro F1, Krippendorff alpha
Ordinal exact agreement, within-one agreement, weighted disagreement weighted kappa, rank correlation
Continuous MAE, distribution, threshold sensitivity Pearson/Spearman, calibration curve
Pairwise agreement, tie rate, swapped-order consistency Bradley-Terry or Elo analysis only when justified

Attest should report measurements and uncertainty. It should not ship universal “good” thresholds without domain evidence.

6.4 Judge lifecycle states

draft
  judge exists but has no accepted calibration

valid
  exact judge inputs match an accepted calibration snapshot

stale
  rubric, prompt version, model identity, or corpus changed

rejected
  owner explicitly rejected the calibration for gating use

Default behavior:

  • Exploration may run a draft judge with a visible warning.
  • Strict CI policy must explicitly allow or reject draft judges.
  • A stale judge never inherits the old “valid” label.
  • Cached scores retain the calibration status that existed when they were created and may be reinterpreted by a newer decision policy without being rewritten.

6.5 Cost and safety controls

Live judge validation requires:

  • Maximum cases.
  • Maximum trials per case.
  • Maximum provider calls.
  • Maximum input and output tokens where enforceable.
  • Whole-run wall-clock deadline.
  • Provider and model allowlist.
  • Explicit environment-secret references.
  • --dry-run cost estimate based on configured limits.
  • Immediate cancellation.
  • No retries for invalid credentials or non-retryable quota errors.
  • Artifact redaction scan before publication.

7. Local human-in-the-loop design

7.1 Why human review is not another metric type

A human label has identity, workflow state, possible disagreement, blinding, and adjudication. Treating it as a synchronous metric call would lose those semantics and tempt the runtime to block indefinitely.

Human review should therefore be an asynchronous evidence workflow linked to immutable runs.

7.2 CLI command model

Proposed grammar:

attest review rubric add <rubric-id>
attest review rubric show <rubric-id>
attest review create --run <run-id> --rubric <rubric-id> [selection flags]
attest review list
attest review show <batch-id>
attest review next <batch-id> [--reviewer <id>] [--blind]
attest review submit <batch-id> <item-id> --from-json <path|->
attest review status <batch-id>
attest review adjudicate <batch-id> <item-id>
attest review export <batch-id> --format jsonl|csv
attest review import <batch-id> <path> --format jsonl|csv
attest review promote <annotation-or-item-id> --to-dataset <dataset-id>
attest review agreement <batch-id>

Every command follows the CLI v2 output, error, dry-run, transaction, and optimistic-concurrency contracts.

7.3 Review selection strategies

all
random
stratified
failed
regressed
near-threshold
judge-disagreement
judge-variance
metric-error
tag-filtered
manual case list

Selection must record its seed and exact source population so the batch is reproducible.

Recommended defaults:

  • Calibration batch: stratify by expected class and known difficulty.
  • Release audit: include all regressions, all metric errors, near-threshold results, plus a random passing sample.
  • Judge comparison: prioritize disagreements and high-variance cases without excluding a random control sample.

7.4 Blinding

For single-output review, optional blind mode hides:

  • Machine metric score.
  • Judge rationale.
  • Earlier reviewer labels.
  • Whether the case is baseline or candidate.

For pairwise review:

  • Candidate order is randomized with a recorded seed.
  • The stored mapping preserves which run was shown as A or B.
  • Reviewers cannot see other reviewer choices until they submit.
  • Swapped-order sentinel pairs may be inserted to measure consistency.

7.5 Terminal interaction

The human terminal flow must be usable without direct JSON editing:

  • One item per screen or line-mode block.
  • Visible rubric instructions.
  • Bounded input, output, expected data, and trace summary.
  • Explicit keys for categorical labels.
  • Numeric entry with visible ranges for continuous scores.
  • Optional rationale and confidence.
  • Save-and-next, skip, return, and quit-with-progress-preserved.
  • Full keyboard access with alternatives to arrow keys.
  • Screen-reader-compatible line mode.
  • No color-only status.
  • Resume from the next unreviewed item.

7.6 Multi-reviewer and local concurrency

Without accounts or cloud identity, Attest provides local coordination rather than identity assurance:

  • Reviewer id is a user-supplied stable string or local configuration value.
  • A batch may require multiple distinct reviewer ids.
  • Local claims use bounded leases to avoid duplicate work by concurrent processes.
  • Imported annotations from another machine preserve reviewer id and original timestamp.
  • Duplicate annotation ids are idempotent.
  • Conflicting annotations are retained, not overwritten.
  • Attest does not claim that a reviewer id proves a legal identity.

7.7 Adjudication

Disagreement is data. The system should distinguish:

  • Reviewer disagreement.
  • Invalid or incomplete annotation.
  • Rubric ambiguity.
  • Evidence insufficiency.
  • Accepted plural outcomes where multiple labels are defensible.

An adjudication record contains:

  • References to all reviewed annotations.
  • Adjudicator id.
  • Final label or accepted-disagreement state.
  • Rationale.
  • Optional rubric-improvement note.
  • Timestamp and rubric hash.

7.8 Promoting human corrections

Promotion is a separate transactional operation:

  1. Select an adjudicated correction.
  2. Show the target dataset row or proposed new case.
  3. Show semantic diff.
  4. Preserve provenance linking the new expected value to review evidence.
  5. Validate the whole project.
  6. Apply atomically.

The original run, output, machine score, and annotation remain unchanged.

7.9 Export and offline participation

To include non-technical reviewers without a browser product:

  • Export a redacted CSV review packet with stable item ids and clear column descriptions.
  • Export JSONL for agents and structured tools.
  • Include a generated Markdown instruction file.
  • Validate every imported row and report all errors at once.
  • Reject unknown item ids, rubric mismatches, duplicate annotation ids, and stale batch hashes.
  • Never export secrets or unredacted sensitive fields.

8.2 Scenario categories

Human-developer scenarios

  • Connect a native CLI agent.
  • Import an HTTP request from cURL.
  • Diagnose missing secret.
  • Correct an output pointer.
  • Import CSV cases with field mapping.
  • Add deterministic output assertion.
  • Add a judge rubric.
  • Diagnose a judge provider error.
  • Compare a candidate run to a baseline.
  • Recover from a stale project hash.
  • Recover an interrupted project transaction.

Domain-expert scenarios

  • Add cases from a table without editing JSON.
  • Describe good behavior and choose a scoring preset.
  • Review a failed output.
  • Correct expected behavior.
  • Complete a blinded review packet.
  • Explain whether a result is deterministic, model-estimated, or human-reviewed.

Coding-agent scenarios

  • Discover command grammar using JSON help only.
  • Initialize a project non-interactively.
  • Inspect schemas.
  • Generate valid command request documents.
  • Dry-run a mutation and apply with project hash.
  • Recover from each stable error stage.
  • Run selected tests and consume JSONL progress.
  • Produce no unsupported direct edits to canonical resource files.

Unattended CI scenarios

  • Run without a TTY.
  • Emit only valid structured stdout.
  • Cancel and produce exit code 130.
  • Distinguish evaluated failure from infrastructure error.
  • Generate JUnit and static report atomically.
  • Respect cost and live-provider policies.

8.3 Deterministic UX metrics

Prefer deterministic checks whenever possible:

  • Command exit code.
  • Time to first real-agent result.
  • Number of prompts.
  • Number of manual file edits.
  • Whether every generated resource validates.
  • Whether all changes were previewed.
  • Whether an unsafe side effect occurred without approval.
  • Whether any secret-like literal appeared in output or files.
  • Whether the operator reached the intended run result.
  • Whether exact recovery command was shown after a seeded failure.
  • Whether machine stdout conforms to the published schema.
  • Whether a coding agent used stale project state.

8.4 LLM-based UX metrics

An LLM may grade qualities that are difficult to encode mechanically:

  • Was the next action clear?
  • Did the error explanation correctly separate configuration, connection, contract, scoring, and persistence?
  • Did the generated test reflect the stated user goal?
  • Did the rubric omit important domain requirements?
  • Did the coding agent choose an unnecessarily complex integration?
  • Did the transcript preserve user agency and disclose side effects?

These graders must themselves be calibrated against human-rated transcripts before becoming release gates.

8.5 Human usability research

Run formative studies in waves:

Wave 1 — before full CLI v2 cutover

  • Five to eight developers with an existing agent.
  • Observe current setup and failure recovery.
  • Use findings to adjust vocabulary, command hierarchy, and diagnostics before they freeze.

Wave 2 — after guided authoring and cURL import

  • Five to eight developers.
  • Five to eight domain or QA participants who do not routinely write code.
  • Tasks use the participant's real or representative agent, not only a sample.

Wave 3 — agent benchmark

  • At least two coding-agent families.
  • Multiple clean-room repetitions per scenario.
  • Same task brief, time limit, command permissions, and success checks.
  • Report completion, invalid operations, recovery quality, total tool calls, elapsed time, and token/cost where available.

Wave 4 — release confirmation

  • Repeat the fixed benchmark after packaging from the actual release artifact.
  • No repository checkout or local source imports.
  • No facilitator intervention on the measured run.

8.6 Research evidence to retain

  • Consent-safe notes or structured observations.
  • Task completion and time.
  • Assistance count.
  • First failure point.
  • Recovery success.
  • Comprehension questions.
  • Accessibility observations.
  • Final participant confidence.
  • Coding-agent transcript and exact tool trace.
  • Artifact hashes and Attest version.

No research artifact containing real secrets, private prompts, or customer data is committed or published.

9.3 Ownership rule

Parallel tracks must own distinct directories or contract seams. Shared dispatchers, public barrels, generated schemas, and the canonical plan are integration-owned files. One integration task lands those changes after child tracks are reviewed; concurrent tasks do not repeatedly rewrite them.

10. Detailed roadmap

Phase 0 — Complete the CLI v2 North Star substrate

Purpose: land the attached CLI experience plan. This phase is the foundation, not the work this roadmap is trying to replace.

Track 0A — Domain and machine contracts

  • 0A.1 — Project and resource schemas

    • Define attest.project, agent, test, dataset metadata, case, and metric schemas.
    • Encode stable ids, display names, versions, hashes, and cross-references.
    • Reject unknown fields.
    • Aggregate every cross-reference and collision error before mutation or execution.
    • Generate JSON Schema from the runtime source of truth.
    • Add valid, invalid, forward-compatible, and adversarial conformance fixtures.
    • Depends on: ratified CLI v2 contract.
    • Gate: Zod/runtime and generated schema validation agree byte-for-byte on golden fixtures.

  • 0A.2 — Command request schemas

    • Give every mutation one versioned request object.
    • Make wizard input, flags, and --from-json normalize into that object.
    • Publish schema ids through JSON help.
    • Define conflict, implication, default, and missing-input behavior.
    • Depends on: 0A.1.
    • Gate: every authored resource can be created without TTY interaction or direct file editing.

  • 0A.3 — Result, event, help, and error schemas

    • Define attest.cli-result/v1.
    • Define attest.cli-event/v1.
    • Define structured help tree.
    • Define error registry with stage, code, path, hint, retryability, details, and exit code.
    • Enforce one JSON document on stdout for non-streaming commands.
    • Enforce one event per line and terminal result event for JSONL.
    • Depends on: 0A.1.
    • Gate: coding agents can discover and recover without parsing human prose.

Track 0B — Project discovery and transactional mutation

  • 0B.1 — Project discovery and load

    • Discover attest.project.json through parents.
    • Honor explicit --project.
    • Stop at mount and Git worktree boundaries unless explicit.
    • Load and hash all indexed resources.
    • Detect missing, extra, duplicate, or hash-mismatched files.
    • Reject v1 config discovery with an explicit v2 message.
    • Depends on: 0A.1.

  • 0B.2 — Semantic diff

    • Model add, update, remove, rename, attach, and detach operations.
    • Include JSON Pointer field changes.
    • Include import counts and dedupe decisions.
    • Redact sensitive literals before rendering.
    • Provide stable human and JSON renderers.
    • Depends on: 0A.1, 0B.1.

  • 0B.3 — Lock, transaction, rollback, and recovery

    • Create identity-aware project locks.
    • Refuse live lock theft.
    • Add explicit stale-lock recovery.
    • Stage complete candidate files and backups.
    • Journal every publish step.
    • Rename manifest last as commit point.
    • Restore after injected failure at each publish boundary.
    • Recover incomplete transactions before future reads.
    • Implement --if-project-hash optimistic concurrency.
    • Depends on: 0B.1, 0B.2.
    • Gate: fault injection proves old-or-new visibility for all cooperating CLI readers.

Track 0C — Resource authoring

  • 0C.1 — Project/list/show/validate commands

Track 0D — Import and transport breadth

  • 0D.1 — CSV/JSON/JSONL import

    • Parse complete input before writing.
    • Support explicit mappings and previews.

    • Implement deterministic stable ids.
    • Implement explicit dedupe and append/upsert policies.

    • Depends on: 0C.3.

  • 0D.2 — Safe cURL and mapped HTTP

    • Parse cURL as data.
    • Reject command substitution, unsafe auth capture, multipart, proxy, and unsupported flags.
    • Convert secrets to references.
    • Map request inputs and response/error/trace pointers.
    • Add bounded probe and extraction preview.
    • Depends on: 0C.2.

  • 0D.3 — Polling and server streams

    • Implement same-origin polling with terminal extraction.
    • Honor bounded Retry-After.
    • Separate submission and poll retry rules.
    • Implement SSE and generic JSONL response streams.
    • Enforce connect, idle, application-idle, and total deadlines.
    • Enforce event and aggregate caps.
    • Depends on: 0C.2.

  • 0D.4 — Background and JSONL process adapters

    • Limit background lifecycle to one eval run.
    • Implement readiness checks and owned shutdown.
    • Support serial and multiplexed correlated JSONL.
    • Add required per-request in-band cancellation.
    • Retain process-termination fallback.
    • Fail all outstanding requests on EOF with distinct evidence.
    • Depends on: 0C.2.

  • 0D.5 — WebSocket adapter

    • Land after the first polling/SSE vertical slice.
    • Support text JSON only.
    • Support per-run multiplexing and per-case fallback.
    • Correlate request ids.
    • Enforce open, idle, ping, attempt, and close deadlines.
    • Avoid post-ack reconnect that risks duplicate side effects.
    • Depends on: 0D.3, shared correlation fixtures from 0D.4.

Parallelization: 0D.1, 0D.2, and 0D.4 are parallel. 0D.3 may proceed beside them. 0D.5 starts only after the polling/SSE contract is proven.

Phase 7 — Local North Star release gate

All mandatory gates must be true:

CLI and project integrity

  • One v2 execution path; no v1 fallback.
  • Every mutation is dry-runnable, atomic, recoverable, and optimistic-concurrency safe.
  • Human and JSON output parity is contract-tested.
  • No structured command prompts unexpectedly.
  • Every error has stage, stable code, retryability, and repair guidance.

Agent integration

  • Native CLI and HTTP pass hostile conformance.
  • cURL import never executes shell text and never persists literal credentials.
  • Polling and SSE vertical slice passes before WebSocket is accepted.
  • Background agents remain run-scoped.
  • JSONL has in-band per-request cancellation and termination fallback.

Evaluation validity

  • Required CI remains deterministic and network-free.
  • Scheduled OpenAI and Anthropic smoke lanes pass within budget.
  • Sanitized provider replay fixtures run in required CI.
  • At least one judge rubric has an accepted human calibration snapshot.
  • Judge status is visible and invalidates correctly.
  • Uncalibrated or stale judge policy is explicit.

Human review

  • Review rubrics, batches, annotations, and adjudication are versioned.
  • Original runs and metric results remain immutable.
  • Blind and pairwise review preserve order provenance.
  • Agreement report and adjudication work.
  • Corrections promote through semantic diff and atomic transaction.
  • CSV/JSONL review exchange is validated and redacted.

Human and agent experience

  • Median time to first real-agent result is under five minutes in the target studies.
  • First meaningful scored test is under ten minutes for the majority of observed participants.
  • At least 90% of frozen coding-agent scenarios complete without prose scraping or direct canonical-file edits.
  • Representative users can correctly identify deterministic, judge, and human-reviewed evidence.
  • Seeded failures are correctly categorized and recovered without source inspection.
  • Keyboard and line-mode review paths pass accessibility acceptance.

Distribution

  • Packed npm and compiled artifacts pass clean-machine smoke.
  • Checksums and SBOM are published.
  • GitHub Action examples pass.
  • Documentation commands match the packed artifact exactly.

Security and privacy

  • Zero known secret values in authored files, diffs, outputs, run bundles, replay fixtures, review exports, telemetry, or published reports.
  • Every process launch, network probe, live judge call, and mutation has an explicit authority path.
  • Review exports are redacted by allowlist.
  • No private study data is published.

14. Research and design principles

The roadmap follows these evidence-backed principles:

  • LLM judges can align with humans on some tasks, but model judgment is not automatically objective.
  • Pairwise evaluation can exhibit position bias; order swapping and consistency measurement belong in the product.
  • Human review systems need explicit rubrics, multiple reviewers, progress, disagreement, and adjudication—not an unstructured comment box.
  • Judge improvement should be measured against human-labeled examples, with disagreements inspected rather than hidden.
  • Deterministic checks should remain preferred where behavior can be verified mechanically.

Primary and official references:

  • Zheng et al., Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena.
  • Shi et al., Judging the Judges: A Systematic Study of Position Bias in LLM-as-a-Judge.
  • Liu et al., G-Eval: NLG Evaluation using GPT-4 with Better Human Alignment.
  • LangSmith, Annotation queues and improving judges using human feedback.
  • Braintrust, Human review.

16. Final definition of success

Attest reaches the local and CLI North Star when all of the following are simultaneously true:

  1. A human can configure and run a real agent without learning Attest's file representation.
  2. A developer can customize every transport, test, dataset, metric, trace, and CI policy without framework lock-in.
  3. A coding agent can discover, preview, apply, verify, and repair the same operations through versioned structured contracts.
  4. An unattended process never encounters an unexpected prompt or ambiguous exit state.
  5. Every mutation is reviewable, atomic, recoverable, and concurrency-safe.
  6. Every result explains its evidence source and limitations.
  7. Live provider compatibility is checked outside required CI with strict budgets and redaction.
  8. Judge quality is measured against human labels, not inferred from a successful API response.
  9. Human disagreement is retained and adjudicated rather than erased.
  10. Corrections improve canonical datasets through explicit transactional promotion.
  11. Attest's onboarding is itself evaluated with deterministic checks, calibrated LLM grading, and observed humans.
  12. The complete experience works from the actual distributed artifact with no cloud or browser-authoring dependency.

That is the local product worth placing underneath a future web and cloud experience.
