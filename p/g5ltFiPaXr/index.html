Seeing the plan, not reading it

Five directions for turning the AI build plan from a wall of markdown into something the user can see, poke, and confirm — plus how they compose and what to ship first.

Where the flow stands today

State 1Prompt + loaderUser asks; canvas shows the floating icon-cluster loader. Canvas is otherwise idle.
State 2Clarifying questionsStructured question cards (1 of 2…) — already a good interactive pattern.
State 3Plan as markdownTrigger + Steps 1–4 as a bulleted list in chat. "Shall I go ahead and build this?"
The core observation: while the plan sits in chat as text, the canvas — the exact surface where the workflow will exist — is empty. The plan describes nodes and edges; the product already knows how to draw nodes and edges. The plan should be rendered in the workflow's own language.
OPTION A

Ghost blueprint on the real canvas

north star

The plan renders directly on the canvas as ghost nodes — dashed, translucent, laid out exactly where the real nodes will land. Chat keeps a one-line summary + confirm. On confirm, ghosts materialize into real nodes one by one as the agent builds. Try it: hit Confirm plan below.

Why it wins
  • "What will be made" is answered literally — you see it, where it will live, before it exists.
  • Reuses the existing canvas node renderer and auto-layout; ghost is a style variant, not a new surface.
  • Loader continuity: the floating icon-cluster can morph into the first ghost node as the plan streams.
  • Click a ghost node → inline "change this step" that prefills the chat input, scoped to that step.
Watch out for
  • Plan steps must map to concrete node types early — the planner has to emit structured steps (it already emits Trigger/Step 1..N, so the data is close).
  • Ghosts need a distinct visual grammar so nobody mistakes them for a built-but-broken workflow.
  • Edit flows on a populated canvas need diff treatment (see the edit-mode section).
OPTION B

Structured plan card in chat

lowest lift

Keep the plan in the chat panel, but replace markdown with a typed card: trigger chip, step rows with app icons and connection badges, expandable detail, and explicit actions. Same pattern family as the existing clarifying-question cards, so it feels native immediately.

Why it wins
  • Cheapest path to structure: no canvas involvement, ships as a chat message type.
  • Forces the planner output into a schema — the prerequisite for every other option here.
  • Step rows can carry real affordances: connection picker inline, per-step "change this".
Watch out for
  • Still a list — flow shape (branches, parallel paths) doesn't read. Fine for linear plans, weak beyond.
  • The canvas stays empty; the "see where it lands" magic never happens.
OPTION C

Flowchart review sheet

A focused overlay above the canvas: auto-laid-out mini flowchart, pan/zoom, click a node for its detail. A dedicated "review mode" moment — the product visibly shifts from chatting to deciding.

Why it wins
  • Undivided attention — a deliberate approval gate, useful when the plan is consequential (deploy rights, external sends).
  • Best fit for edits to large existing workflows: the overlay can show only the delta subgraph without the noise of the full canvas.
  • Independent of canvas internals — could ship from the chat/copilot layer alone.
Watch out for
  • A second flowchart renderer to maintain unless it reuses the canvas engine in a read-only mode.
  • Modal fatigue if it appears for every trivial plan; gate it by plan size/impact.
OPTION D

Synced hybrid: chat stepper ↔ canvas ghosts

A + B combined

The plan card lives in chat (B) and the ghosts live on canvas (A), linked two-way: hover or focus a step and its ghost node spotlights; click a ghost and chat scrolls to that step. Reading and seeing stop being separate activities. Hover the steps below.

Why it wins
  • Chat remains the narrative + approval surface; canvas becomes the truth surface. Each does its job.
  • Spotlight-on-hover teaches the chat↔canvas mapping — users learn the builder while approving the plan.
  • Naturally incremental: ship B, then A, then wire the sync — no throwaway work.
Watch out for

  • Two synced surfaces double the states to test (streaming, partial failure, user edits mid-plan).
OPTION E

Build-along reveal (the confirm → build transition)

Less an alternative, more the third act for A/D: after confirm, the agent narrates each step in chat while its ghost materializes on canvas — border solidifies, icon fills, a subtle settle animation. Errors land on the exact node that failed, with a "fix this step" affordance. The build stops being a black box with a spinner and becomes watching the thing get made.

Why it matters
  • Progress becomes spatial: 3 of 5 nodes solid = 60% done, no progress bar needed.
  • Failure has an address — the broken node, not a paragraph in chat.
  • Streaming-friendly: ghosts can appear one-by-one during planning too, so the plan feels alive as it's being thought.
Watch out for
  • Build order must be honest — don't animate steps that haven't actually been created server-side.
  • Respect reduced-motion; keep the settle subtle or it gets circus-y on 20-step plans.
EDIT FLOWS

When the workflow already exists: plan as a diff

"What will be edited" needs different grammar from "what will be made". On an existing canvas, the plan renders as a diff over the real nodes: untouched nodes dim, added steps appear as ghosts with an add badge, changed nodes get a mod badge with a before/after popover, removed nodes get struck and clay-tinted. Same palette works in the chat card and the review sheet.

Recommended path

  1. Structured plan schema + chat card (B)Planner emits typed steps (id, kind, app, connection, summary, detail). Card replaces markdown. Everything after depends on this schema.
  2. Ghost blueprint (A) for creation flowsGhost style variant on existing node renderer; loader morphs into first ghost as plan streams. Confirm stays in chat.
  3. Sync + build-along (D + E)Shared step IDs wire hover-spotlight both ways; confirm triggers progressive materialization; errors land on nodes.
  4. Diff grammar for edits, review sheet (C) where stakes are highAdd/mod/del badges over existing canvas; sheet reserved for large-delta or high-impact plans.
The ghost grammar is the keystone: one visual idea (dashed = proposed, solid = real, badge = delta) covers planning, building, and editing — and every phase above ships value on its own.
