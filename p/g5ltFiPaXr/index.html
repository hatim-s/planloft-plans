Review & edit with a one-shot build

Ghost blueprint (A) + chat↔canvas sync (D) + reveal (E), redesigned around the real build model: the agent generates the whole workflow in a single shot. No per-node build progress exists — so the reveal becomes choreography that plays after the response lands, and all the interesting interaction moves into review.

What one-shot changes — and what it doesn't

The honesty rule: nothing on the canvas may claim build progress that hasn't happened. One-shot means there is exactly one moment when the workflow becomes real. Everything before it is plan (ghosts — honest, because the plan genuinely exists step by step). Everything after it is presentation (a staged cascade — honest, because by the time it plays, every node is already built). The only forbidden thing is a fake "building step 2 of 5…" ticker.

Consequence: review is where the experience lives. The plan phase streams and is interactive; the build phase is a short, owned transition (~2s of shimmer → cascade); the arrival moment carries the delight. This is arguably better than live per-node building — the reveal is controllable, consistent, and never stalls halfway.

The planner replies with a revised plan; only changed ghosts morph, marked with an "updated" chip — no full re-render, no lost reading position.

If the one-shot fails wholesale
  • Ghosts stay exactly as they were — the plan is never lost.
  • Chat carries the error + a retry CTA; canvas shows no half-built wreckage because nothing was built.
  • This is a hidden strength of one-shot: the failure state is clean by construction.
If the response has per-node issues
  • Everything materializes; offending nodes keep an ! badge.
  • Clicking the badge (or "Fix this" in chat) opens the scoped prompt for that node — same loop as review revisions.
  • Needs the plan-step → built-node ID mapping returned by the build response.

Changes applied · Revert
Why removals must animate a collapse
  • A node vanishing instantly reads as a glitch; a struck node collapsing reads as a decision executing.
  • The collapse also closes the layout gap, so the final graph is the real post-edit graph, not a diagram with holes.
Revert as a first-class citizen
  • One-shot apply = whole-graph replace, so keeping the prior version is nearly free — snapshot before apply.
  • Revert replays the reveal in reverse (adds fade to ghost, removed step re-grows) — the grammar teaches itself.
  • Snackbar times out into version history; nothing is ever lost.

BUILD NOTES

What this needs from the system

Planner contract
  • Typed steps: {id, kind, appId, connectionId?, title, summary, fields, dependsOn[]}.
  • IDs stable across revisions — a revised plan is a patch, so ghosts morph instead of re-rendering.
  • Edit plans emit ops: {op: add|modify|remove, targetNodeId?, step} with field-level before/after for modify.
Build response contract
  • Returns planStepId → builtNodeId mapping — powers the cascade order, error landing, and post-build popovers.
  • Per-node validation issues ride the same mapping.
Canvas layer
  • Ghost = style variant of the existing node renderer; diff badges = decorator layer. No second renderer.
  • Ghost layout must use the same auto-layout as real nodes, so materialization is a style change, not a position change.
  • Reveal respects prefers-reduced-motion: instant solidify, no cascade.
Versioning
  • Snapshot workflow before every one-shot apply → snackbar revert + version history for free.
  • Plan revisions keep their own lineage so "updated" chips can diff against the previous plan iteration.
One grammar, three moments: dashed = proposed, shimmer = in flight, solid = real, badge = delta. Create and edit are the same experience — edit is just a plan whose baseline isn't empty.
