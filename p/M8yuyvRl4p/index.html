What was requested

The request was to classify an order by orderAmount. An orderAmount greater than 1000 should return tier PREMIUM; otherwise it should return STANDARD. For example, an input such as {orderAmount: 1500} should produce {tier: "PREMIUM"}. The prompt called this a webhook, but it also asked for an immediate response, which requires a callable/API-style workflow.

What broke

The current saved definition has two confirmed defects: request orderAmount is a number while response orderAmount is text, and the response node flows to a generic STOP. This does not prove the historical run used this draft.

  1. The request entering the callable has orderId as text and orderAmount as a number.
  2. The saved response definition declares orderAmount as text, and the response node is n_MUPbb.
  3. The graph connects n_MUPbb to generic STOP node n_StoFn instead of ending at the callable response.
  4. No fresh run was made because the available evidence did not provide all required request values, so later runtime behavior was not observed.

  2. Reason B: The request wording selected a webhook pattern instead of a callable pattern.

    • Evidence for it: the prompt says webhook while also asking for a same-call response; the saved graph violates the current callable response rules.
    • Evidence against it or missing: the current rules may not have been loaded at generation time.

  • Test: inspect the generated workflow and require matching request/response types, no generic STOP after n_MUPbb, and a response on every reachable branch.

  • Done when: the corrected inspect artifact shows the exact schema and edges, and a valid callable run returns the expected tier.

  • Risk: Changing the response schema may affect callers that relied on the old string field.

  • Fix B — Workflow prompt/skill routing: Add the exact rule that “webhook response,” “Respond to API request,” and “same-call result” select the callable/API trigger and load the callable response rules before generation.

  • Example: “Return a webhook response containing tier” → callable/API trigger, not a one-way webhook.

  • Test: run the routing check with the row-2 wording and “Respond to API request”; both must select the callable path and reject response-to-STOP.

  • Done when: generation telemetry records the loaded callable rule and inspect shows the correct trigger, types, and terminal response.

  • Test: apply the minimal correction in UAT and compare the submitted and re-fetched definition hashes.

  • Done when: the save response, post-save inspect, and version/hash comparison prove that the correction persisted.

  • Risk: Broadly weakening identity validation could create unrelated save or ownership problems.

Bottom line

The current saved workflow contains a confirmed response-schema and graph problem. The historical failure could also involve prompt classification or a save/deployment problem, but those causes are not proven.
