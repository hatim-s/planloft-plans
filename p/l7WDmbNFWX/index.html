AI FDE → Workflow Planner Handoff Architecture

Goal: AI FDE becomes the single user-facing front door; Workflow Planner owns the whole workflow lifecycle behind it, with platform knowledge flowing FDE → planner → builder/editor.

2. Layer contract

LayerOwnsNever does
AI FDE Conversation, URL/entity resolution, platform knowledge retrieval, non-workflow assets (connections, API Manager, object writes, sharing, exports, activity, dependencies), read-only workflow metadata (summary, run list, counts) Never plans, edits, tests, or deploys a workflow. Never rewrites planner's user-facing text.
Workflow Planner Full workflow lifecycle — build, edit, debug, test, run, deploy, test-cases. Scouting and resolution (connections, objects, called automations, SQL targets). Authors all user-facing workflow prose. Never creates API endpoints. Never creates or mutates Storage objects. Never talks to the user directly — its text is relayed.
Builder / Editor JSON emission unchanged

Keep read-only workflow questions out of the planner hop. "What does this automation do", "how many runs failed yesterday", "who changed this" — FDE answers directly. Routing those through an agent hop costs a full turn and buys nothing.

Tighten the routing rule to: anything that reads a run's internals, mutates, executes, or deploys → planner; anything that reads asset metadata → FDE.

3. Invocation envelope

Replace the freeform query string. A string in / string out contract with a sentinel escape hatch will not survive the added scope.

Request:

{
  intent: "build" | "edit" | "debug" | "test" | "deploy" | "testcase",
  mode: "conversational" | "direct",      // direct = no clarifications, fail instead
  query: "<user's ask, verbatim — do not paraphrase>",
  context: { host, workflowId, workflowName, runId, startTime, endTime,
             selectedNodeIds, selectedEdgeIds, attachments },
  resolved: { objects?, connections?, calledAutomations? },
  knowledge: [ { question, summary, module } ],
  caseId, answerTo?
}

Response:

{
  status: "done" | "needs_input" | "blocked" | "failed",
  userMessage: "<relay verbatim>",
  clarification?: { id, question, options[] },
  result?: { workflowId, version, deployed, runId, diagnosis },
  followUps?: [ { action: "create_api_endpoint" | "create_object" | "fix_connection", payload } ]
}

Why each field earns its place:

  • clarification.options[] — requestClarification renders option chips. Flattened into a relayed string they become prose and every confirmation in the system degrades.
  • followUps — how API-endpoint creation and object creation leave the planner without dead-ending the user.
  • mode: "direct" — lets FDE call the planner for a mechanical deploy inside its own uninterrupted API build, per api-manager-helper.md's "propose once, then build" contract.
  • answerTo — binds a user answer to the clarification that asked for it.

4. Platform knowledge — the core of the change

Push-with-summarisation alone is insufficient. Use push + direct tool grant; delete the sentinel.

Push-only fails because knowledge needs are discovered during scouting, not before it. FDE cannot know the planner will need "does the Slack connector's post_message accept a channel name" until the planner is mid-resolution. Summarisation also destroys exactly the payload that matters — exact enum literals, exact limits, exact field names. "Configure auth on the access profile" is worthless; JWT_TOKEN plus rsaPublicKey-if-RS256 is the whole value.

The sentinel fails because it burns a full agent round-trip per question, hijacks the response channel (planner must emit that line and nothing else, abandoning its turn mid-scout), and is a bare string protocol with no failure mode.

Design

  1. Push a knowledge envelope — FDE passes what it retrieved this turn as knowledge[]. Purpose is deduplication and framing, not completeness: it stops the planner re-asking what the user was already told, and carries constraints that surfaced in the doc conversation.
  2. Copy Ask from knowledge onto the planner — retrieval at point of need, no round-trip, planner writes its own query.
  3. Delete the KNOWLEDGE NEEDED sentinel once (2) lands. Two mechanisms for one job is how drift starts.
  4. Budget it — mirror FDE's existing rule (ai-fde.md:39): at most 2 searches per decision point, no looping.

Precedence rule — write this into the planner prompt

Docs describe capability and semantics. packages/ describes schema. When they disagree, packages/ wins.

  • Feasibility, business meaning, limits, gotchas, "which connector even does this" → knowledge.
  • resourceName, input keys, enum values, required fields, output paths → packages/workflow-nodes/ and the live fetch tools. Never from a doc summary.

Without this rule, a doc paraphrase produces an invented resourceName and the builder emits an unsavable node.

Handoff into the brief

A knowledge-derived fact may enter the brief only after reconciliation with live state — the connector folder exists, the object field exists, the action exists. Survivors become flow-step annotations in the existing style used for [cache: …] and [sql: …]:

4. Send Slack message to #new-leads [doc: channel must be the ID, not the name]

Unreconciled doc facts get dropped, not forwarded. Otherwise you ship hallucination risk one layer deeper, where nobody can see it.

5. Removing the API-publish backpatch

Remove apiConfig from the Deploy Automation shape in callables.md §7 and the endpoint promise at line 159. Revoke API Manager Helper from the planner.

Planner instead reports the gap and emits followUps: [{action: "create_api_endpoint", payload: {workflowId, suggestedPath}}]. FDE picks it up and runs API Manager Helper, which does reuse-first lookup, method consolidation, and client + access profile + auth enum validation.

This is a bug fix, not just a refactor. The planner's apiConfig path created a bare endpoint with no access profile — and per api-manager-helper.md, an endpoint without an access profile returns 401. The backpatch has been producing unreachable endpoints.

6. Deploy ownership — decided: planner only

Deploy existed in both agents: Deploy Automations (FDE, get-workflow-helper.md:32) and Deploy Automation (planner, callables.md §7). Two tools, two consent flows, two failure-reporting styles.

Planner keeps it: deploy is inseparable from the build/test loop (undeployed called-automation check in Step 2.6, deploy-before-callable in callables.md), and planner already owns the consent semantics — deploying promotes someone's draft, never silently.

Remove the FDE copy. Its per-item failure-list warning goes with it, since that caveat exists only because FDE held the tool.

Rewritten API-endpoint flow

  1. FDE confirms the trigger is callables_from_api — the START node's resourceName from Get Workflow Summary, which it already has.
  2. FDE builds the full chain via API Manager Helper: group, endpoint, client, access profile.
  3. FDE calls the planner with {intent: "deploy", mode: "direct"} and relays the result.
  4. FDE returns the invocation URL + curl.

Deploy fails on validation violations, so a failure at step 3 is a real workflow defect — and the planner is the agent that can diagnose it. That is the argument for the placement.

7. Object Manager — planner reads, FDE writes

Split on durability, not on who discovers the need.

  • Resolution / read — planner, unchanged. Step 2.5 already does this and needs no rewrite.
  • Create / mutate / delete — FDE, via Get Object Helpers. When the planner finds an object missing it returns status: "blocked" plus followUps: [{action: "create_object", payload: {proposedName, proposedFields, whyNeeded}}]. FDE runs the object conversation, creates it, then re-invokes the planner with the resolved id in resolved.objects.

Why not let the planner create it

  1. Single writer per asset class. An object is durable and cross-module — apps bind to it, other automations read it. Two agents defining tables with different conventions (naming, primary key, indexes, store type) diverges fast. There is already a third writer in the app path (object-builder via the Create Interface pipeline). Do not make it four.
  2. Object creation is a user conversation, not a resolution step. get-object-helpers.md requires duplicate-name checks with a user decision, an explicit primary-key call-out, index design with a go-ahead, Standard-object refusal, explicit consent before data loss, and post-write verification by re-read. Each is a user round-trip; through a relay each costs double.
  3. Otherwise the planner inherits the JSON-Schema contract — {"type":"integer","format":"date","dateFormat":"epoch"}, nameField, format: secure, the full-replacement semantics of update_schema. That is ~80 lines duplicated into the workflow domain for a rare case.

Fair counter: the round-trip costs latency, and the planner has the richest picture of the fields needed. Mitigation — the create_object followUp carries a complete proposed schema. Planner does the thinking; FDE does the writing and the confirming.

8. Granular capability grants — where this goes

Tools and skills can be copied to an agent independently. That moves the system from "agent owns skills" to "capability registry + per-agent grant matrix". Agent = prompt + grant list. Two compromises dissolve:

  • The object read/write split becomes clean. Copy only Read Object + Read Records to the planner; leave the write and delete tools FDE-only. The boundary is enforced by absence, not by prompt discipline. Prompt-enforced boundaries leak; missing tools do not.
  • Knowledge needs no skill wrapper. Copy the Ask from knowledge tool directly. The usage discipline — search budget, docs-vs-packages/ precedence, reconcile-before-brief, [doc: …] annotation — lives in the planner prompt, because those rules are planner-specific and a skill would be a file with one consumer.

The cost: copy drift

Copies fork silently, and it is already happening in the live inventory:

  • Connection Manager carries three create-connection tools — create a new connection, create a new connection, Create A New Connection.
  • Two Ask from knowledge copies exist with materially different descriptions. The agent-level one reads "Helps to fetch knowledge about the platform." The API-Manager-scoped copy reads "Pass a natural-language question… call it before you settle on a plan… build from it, not from memory." Same capability, different behavior depending on which copy the model reaches.

A tool description is prompt surface, so drifted copies are drifted prompts nobody reviews. Three guards:

  1. One canonical body per capability in the repo — prompts/skills/*.md for skills, a tools manifest for tool descriptions. Platform copies are outputs, never sources.
  2. Grant matrix checked in — agent × capability, with an explicit scopeOverride field when a copy legitimately differs (e.g. planner's Ask from knowledge scoped to connector and node behavior rather than product screens). A copy that differs without a declared override is a drift bug.
  3. tools/workflow-agent-fetch diffs copies against canonical and fails on undeclared divergence. The fetch path already exists from the AI FDE import (--include-content). Without this the registry rots the way agent-config/ did.

Long term this is what lets you add more front doors — an app FDE, a data FDE — composing the same capability set without re-authoring skills. That only holds if the registry stays single-sourced.

11. Consequences of a stateful planner

The planner stays stateful across the session. Two prompt changes that are easy to miss:

  • FDE sends deltas plus answerTo, never a re-sent priorPlan. Re-sending state to a stateful agent is worse than not sending it — it double-anchors the proposal.
  • The planner must be told its state persists. Today it reads Context as if every invocation is fresh. Add a scope-reset rule: when workflowId changes mid-session, or the user starts an unrelated build, drop the prior plan rather than editing it. Stateful agents drift into merging unrelated requests.

13. Risks

  • Double interrogation. If FDE pre-resolves workflow details before dispatching, the user is asked twice. Rule: FDE forwards the ask verbatim and resolves nothing in the workflow domain.
  • Three-hop latency. user → FDE → planner → builder. Every clarification is a full round-trip through two agents. The structured envelope and mode: direct are the mitigations; there is no way to make it free.
  • Failure attribution. A builder error now surfaces two layers up. status and result must survive both relays intact.
  • Trace shape. workflow-trace-analyzer — both the .py and .js, which are sync-locked — assumes a planner-rooted trace. An FDE root changes it.
  • Knowledge cost. Two retrieval surfaces on the same case. Cache per caseId and hold the 2-search budget, or retrieval becomes the dominant token line.
  • Copy drift. Already present in production (three create-connection tools, two divergent knowledge tools). Without a canonical source and a diffing fetcher, granular grants accelerate it.
